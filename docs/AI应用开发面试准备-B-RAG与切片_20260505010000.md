## 一、RAG 完整流程与核心概念

### Q1：RAG 的完整流程是什么？

> **离线阶段（入库）：**
> 文档 → DocumentReader 解析 → TextSplitter 分段 → Embedding 向量化 → VectorStore 存储
>
> **在线阶段（问答）：**
> 用户问题 → Embedding 向量化 → VectorStore 相似度检索 → 相关文档片段 → 拼装 Prompt → LLM 生成回答
>
> 关键：Embedding 模型用于离线 + 在线两个阶段，必须用同一个模型（否则向量空间不一致）。

**扩展说明：**

> "可以类比 Java 后端的搜索引擎：离线阶段就像建索引（ES 的 bulk index），在线阶段就像搜索（query → filter → sort → return）。
>
> RAG 的核心优势是'知识可更新'——文档更新后重新入库就能生效，不需要重新训练模型。这对电商客服特别重要，商品信息每天都在变，不可能每次都微调模型。
>
> 但 RAG 也有局限：检索不到的内容 LLM 就无法回答。所以文档覆盖面决定了 RAG 的能力上限。RAG 通常和 Tool Calling 配合使用——知识库回答不了的，通过工具查数据库。"

### Q2：RAG 的核心难点是什么？

> 1. **检索质量**：切片粒度、overlap、分数过滤都会影响
> 2. **幻觉控制**：即使有文档上下文，LLM 也可能编造信息
> 3. **文档解析**：PDF 表格、扫描件、复杂排版解析困难
> 4. **实时性**：文档更新后需要重新切片入库
> 5. **多轮对话**：用户说"继续"、"刚才那个"，需要 ChatMemory 配合

**扩展说明：**

> "检索质量是 RAG 最核心的挑战，也是我花时间最多的地方。总结下来有三个层面：
>
> **上游（文档解析）**：PDF 表格解析、扫描件 OCR——如果这里就丢了信息，下游再怎么优化也找不回来。
> **中游（切片和向量化）**：chunkSize、overlap、Embedding 模型选择——决定了'存进去的质量'。
> **下游（检索和过滤）**：分数过滤、Reranking——决定了'取出来的质量'。
>
> 我在项目中主要优化了中游和下游。"

## 二、CustomRagAdvisor（自定义 RAG Advisor）

### 2.1 面试官问："你们的 RAG 做了什么优化？检索质量怎么保证？"

**3 分钟版回答：**

> **痛点：** Spring AI 内置的 `QuestionAnswerAdvisor` 只做向量检索 + 注入上下文，**没有任何分数过滤**。实测发现 nomic-embed-text 对完全无关的问题也能给出 0.35~0.62 的分数，直接把低质量结果注入 prompt 会导致 LLM 产生幻觉。
>
> **怎么做：** 实现 `BaseAdvisor` 接口，在 `before()` 阶段做三级相对分数过滤：
> 1. 绝对兜底：top1 < 0.45 → 全部拒绝（真的不相关）
> 2. 无区分度检测：top1 和 top2 分差 < 0.08 且 top1 < 0.7 → 拒绝（LLM 分不出哪个好）
> 3. 15% 相对衰减：只保留 score >= top1 × 0.85 的 chunk
>
> **为什么不选固定阈值：** 不同 Embedding 模型分数分布差异大，同一模型对不同领域分数也不同，相对分数天然自适应。
>
> **还可以怎样：** 引入 RRF（Reciprocal Rank Fusion）做多路召回融合，或者用 Cross-Encoder 做精排。

**实际案例：**

> "我一开始用固定阈值 0.7，测试发现两个问题：换话题问（商品→天气），分数不是 0.1 而是依然有 0.42；同一文档不同问题分数波动大（0.58 vs 0.82）。所以我设计了三级过滤，上线后无关结果注入率从 ~40% 降到 ~10%。"

**追问预判：**

- **Q："Advisor 链的执行顺序？"** A："Memory(order=-21亿) 先执行 → RAG(order=0) 后执行时已能看到历史。顺序重要——RAG 先执行就没有对话上下文，指代消解不了。"
- **Q："为什么 top1-top2 < 0.08 要拒绝？"** A："分差小说明模型认为'差不多好'，实际就是都不好。类似考试第一名 62 第二名 61，不是第一名好，而是整体不行。0.08 是经验值。"
- **Q："没检索到结果怎么办？"** A："不注入上下文，让 LLM 直接回答。但 system prompt 要告诉它'没有参考资料就说不知道'。"
- **Q："分数参数怎么确定的？"** A："50 个测试问题（30 有答案 + 20 无答案）跑分布图。相关 top1 平均 0.78，不相关平均 0.48，基于数据确定阈值。"

### 2.2 面试官问："Token 监控怎么做？企业中怎么限制用量？"

**3 分钟版回答：**

> **当前实现：** 在 `CustomRagAdvisor.after()` 中记录 Token 用量日志：
> ```java
> var usage = response.chatResponse().getMetadata().getUsage();
> log.info("[Token] input={}, output={}, total={}",
>     usage.getPromptTokens(), usage.getCompletionTokens(), usage.getTotalTokens());
> ```
> 这是**事后统计**，已经消耗了 token，不能阻止本次调用。但有两个价值：(1) 调试时看每次对话的资源消耗 (2) 为后续配额系统提供数据基础。
>
> **企业级 Token 用量限制方案（4 层）：**
>
> | 层级 | 手段 | 说明 |
> |------|------|------|
> | **1. 请求参数层** | `maxTokens` 参数 | 单次请求硬上限，防止异常输入耗尽输出。在 ChatClient 配置或 ChatOptions 中设置 |
> | **2. 应用层** | before() 拦截 + 配额查询 | 查用户/租户剩余配额，不够直接拒绝。需配套配额存储（Redis/MySQL） |
> | **3. 网关层** | API Gateway 限流 | 按 IP/用户/API Key 做 QPS + 日用量配额。Spring Cloud Gateway 或 Kong |
> | **4. 提供商层** | API Key 额度 | OpenAI/DeepSeek 后台设置月度预算上限，超限自动停服 |
>
> **如果项目要实现真正的限流：** 应该加在 Advisor 的 `before()` 里——在调 LLM 之前查配额，不够就抛异常返回"用量已超限"。但这个涉及用户体系 + 配额存储 + 计费逻辑，对面试项目偏重。`maxTokens` 参数是最容易落地的（一行配置）， Advisor 的 `after()` 日志是最有面试价值的（体现你有可观测性意识）。

**底层原理（Spring AI API）：**

> - `ChatClientResponse` 是 Java Record，有 `chatResponse()` 方法返回 `ChatResponse`
> - `ChatResponse.getMetadata().getUsage()` 返回 `Usage` 对象
> - `Usage` 的方法名：`getPromptTokens()`（输入）、`getCompletionTokens()`（输出）、`getTotalTokens()`（总计）
> - 注意：不是 `getGenerationTokens()`，也不是 `getChatResponse()`（1.0.5 的 API 细节）
>
> temperature 参数：`spring.ai.openai.chat.options.temperature`，控制 LLM 输出的随机性（0~2）。值越低越确定，越高越随机。结构化输出设 0，RAG 问答设 0.1~0.3，客服对话设 0.5~0.7。底层原理是 softmax 温度参数——温度低时概率分布尖锐（选高概率词），高时平缓（低概率词也有机会）。

**追问预判：**

- **Q："after() 里已经消耗了 token，监控还有什么意义？"** A："监控的价值不是阻止本次调用，而是：(1) 运维告警——Token 用量异常时通知 (2) 数据积累——为配额计费提供基础数据 (3) 性能分析——哪个 Advisor/接口消耗最多。就像 Java 应用的 access log 不阻止请求，但它是运维的基础。"
- **Q："temperature 设多少合适？"** A："结构化输出（意图识别）= 0（完全确定），RAG 问答 = 0.1~0.3（减少幻觉），客服对话 = 0.5~0.7（自然感）。Temperature=0 不代表每次输出一样（还有 top_p/top_k 影响），但重复性非常高。"
- **Q："maxTokens 怎么设？"** A："单次请求输出 token 上限。客服场景设 500~1000（回答不超过 500 字），意图识别设 200（JSON 不超过 200 token）。设置后即使 LLM 想继续输出也会被截断，可以防止异常输入导致输出爆炸。"

### 2.3 设计模式：责任链模式（CustomRagAdvisor）

**哪里用了：** Advisor 链：`MessageChatMemoryAdvisor` → `CustomRagAdvisor` → ChatModel

**原理：**

> 责任链模式的核心：请求沿着处理者链传递，每个处理者决定处理或传递。Spring AI 的 Advisor 机制就是责任链模式：
> - `BaseAdvisor` 是 Handler 接口（定义 before/after 方法）
> - `MessageChatMemoryAdvisor` 和 `CustomRagAdvisor` 是 ConcreteHandler
> - `order` 字段决定执行顺序（类似 Filter 的 order）
> - `AdvisorChain` 是 Chain（负责把请求传给下一个 Advisor）

**好处：**

1. **解耦**：每个 Advisor 独立实现自己的逻辑，互不影响
2. **灵活**：加/删/调顺序只需改配置，不改其他 Advisor 的代码
3. **有序**：`order` 保证 Memory 先于 RAG 执行（RAG 检索时能看到对话历史）

**类比：** Servlet Filter 链（HTTP 请求 → Filter1 → Filter2 → Servlet）、Spring Interceptor 链。

**追问预判：**

- **Q："责任链和 AOP 怎么选？"** A："AOP 是静态织入（编译期或类加载期），适合固定不变的横切逻辑。责任链是动态组合（运行时），适合需要灵活调整顺序、增删处理者的场景。Advisor 链天然需要运行时动态组合（不同接口可以配不同的 Advisor 集合），所以用责任链更合适。"

## 三、OverlappingTextSplitter（文本切片）

### 3.1 面试官问："文档切片怎么做的？"

**3 分钟版回答：**

> **痛点：** Spring AI 的 `TokenTextSplitter` 没有 overlap 机制——相邻 chunk 的边界处语义会断裂。比如"包邮 99 元"被切成"包邮"和"99 元"两个 chunk，检索"运费"时可能漏掉"包邮"这个前提。
>
> **怎么做：** 两层切片法：
> 1. 第一层：`TokenTextSplitter` 粗切（chunkSize × 2），利用其内部的句子/段落边界检测保语义
> 2. 第二层：滑动窗口细切 + 10% overlap（50 token），相邻 chunk 有重叠
>
> **为什么不直接用滑动窗口：** 一层窗口按字符数硬切，容易在句子中间断开。两层法让粗切负责"找到语义边界"，细切负责"加上重叠"。
>
> **还可以怎样：** 语义切片（Semantic Chunking）——用 Embedding 模型判断相邻句子的语义相似度，相似度高就合并，低就断开。效果最好但成本最高。

**追问预判：**

- **Q："chunkSize 500 怎么定的？"** A："Embedding 模型最大输入 8192 token，prompt 注入不能太长。500 token ≈ 1000 汉字 ≈ 2~3 段，包含一个完整语义单元。"
- **Q："overlap 比例有公式吗？"** A："没有通用公式，推荐 10%~20%。核心原则：overlap 至少能覆盖一个完整句子（~20 token），10% = 50 token 够覆盖 2 句话。"
- **Q："已知问题（粗切块间没 overlap）怎么修？"** A："对全局文本做滑动窗口，而不是对每个粗切块独立切。需要处理边界：最后一个 chunk 不能超出文档尾部。"

### 3.2 TokenTextSplitter 理论详解

**面试官问："TokenTextSplitter 的参数都有什么含义？"**

> Spring AI 1.0.5 的 `TokenTextSplitter` 核心参数：
>
> | 参数 | 含义 | 我们的值 | 说明 |
> |------|------|---------|------|
> | `defaultChunkSize` | 每个 chunk 的目标 token 数 | 500 | 粗切时用 1000（×2），细切时用 500 |
> | `defaultOverlap` | 段间重叠 token 数 | 50 | TokenTextSplitter 自身没有这个参数！这是我们的自定义实现加的 |
> | `minChunkSizeChars` | 最小字符数 | 0 | 切割后如果剩余文本 < 此值，追加到上一个 chunk |
> | `keepSeparator` | 是否保留分隔符 | true | 保留换行/句号等，帮助保持语义 |
> | `separators` | 优先断点列表 | 默认（换行 > 句号 > 逗号 > 空格） | 从前到后尝试匹配，找到第一个就断开 |
>
> **重要纠正：** `TokenTextSplitter`（Spring AI 1.0.5）**没有 `defaultOverlap` 参数**。它的官方 API 只支持按 chunkSize 切分，不做 overlap。overlap 是我们在 `OverlappingTextSplitter` 里用滑动窗口手动实现的。如果网上教程说 TokenTextSplitter 有 overlap 参数，那是旧版本或误传。

**面试官问："如果切割的最后一段小于 minChunkSizeChars 怎么办？"**

> TokenTextSplitter 的行为是：**把太短的尾巴追加到上一个 chunk**，而不是丢弃。
>
> 为什么这样设计：
> 1. **信息不丢失**：丢弃会导致末尾信息永远检索不到
> 2. **语义完整**：尾巴虽然短，但可能包含关键信息（如文档最后的联系方式、价格）
> 3. **上一个 chunk 不会超太多**：minChunkSizeChars 一般设较小值（比如 100 字符），追加后 chunk 只稍微变大
>
> 类比：Excel 分页打印时，如果最后一页只有 3 行，不会把它单独打一页浪费纸，而是合并到上一页。

**面试官问："TokenTextSplitter 的底层原理？"**

> `TokenTextSplitter` 的底层流程：
> 1. 用 `Tokenizer`（默认基于 OpenAI 的 tiktoken）把文本转成 token 数组
> 2. 按 `chunkSize` 从 token 数组中截取
> 3. **不是硬切**——检测到分隔符（换行/句号/逗号/空格）时会优先在这些位置断开
> 4. 如果最后剩余 < `minChunkSizeChars`，追加到上一个 chunk
>
> 关键：它是按 **token 数**切分，不是字符数。1 个汉字 ≈ 1~2 token，1 个英文单词 ≈ 1~2 token。中文场景下 chunkSize=500 约等于 500~1000 个汉字。

### 3.3 我们的自定义两层切片方案

**面试官问："你们实际是怎么做切片的？加了什么参数？为什么？"**

> **背景：** Spring AI 的 `TokenTextSplitter` 不支持 overlap，直接用会导致相邻 chunk 边界语义断裂。
>
> **方案：OverlappingTextSplitter（自定义类）**
>
> ```
> 第一层：TokenTextSplitter（chunkSize=1000, 粗切）
>   → 输出：粗切块列表（利用框架的语义边界检测）
>
> 第二层：滑动窗口（chunkSize=500, overlap=50 token）
>   → 对每个粗切块用滑动窗口细切
>   → 断点优先级：换行 > 句号/问号 > 逗号/分号 > 空格 > 强制截断
>   → 输出：最终 chunk 列表（相邻 chunk 有 50 token 重叠）
> ```
>
> **为什么用两层而不是直接一层滑动窗口：**
> - 一层滑动窗口按 token 数硬切，容易在句子中间断开
> - 两层法让第一层（框架自带的 TokenTextSplitter）负责"找到合理的语义边界"
> - 第二层（手动滑动窗口）负责"在语义边界基础上加 overlap"
> - 这样既有语义边界的保护，又有重叠的保底
>
> **为什么 chunkSize=500、overlap=50（10%）：**
> - chunkSize=500：约 1000 汉字，一个完整语义单元。太小（100）语义不完整，太大（2000）噪音多
> - overlap=50：足够覆盖 2 个完整句子。太小（10）覆盖不了一句话，太大（200）存储冗余
> - 10% 是经验值，业界推荐 10%~20%

**已知问题：**

> 如果粗切块本身 < chunkSize（500），直接返回整个粗切块，不经过第二层。导致粗切块之间没有 overlap。修复思路：收集所有粗切块的文本后做全局滑动窗口。

### 3.4 设计模式：模板方法模式

**哪里用了：** `BaseAdvisor` 接口（before/after 方法骨架）

**原理：**

> `BaseAdvisor` 定义了 Advisor 的执行骨架：`adviseCall()` → `before()` → `chain.nextCall()` → `after()`。这个骨架由框架控制，自定义 Advisor 只需实现 `before()` 和 `after()`。
>
> 这就是模板方法模式——框架定义算法骨架（执行流程），把某些步骤延迟到子类实现。

**类比：** JdbcTemplate（定义 SQL 执行流程，开发者实现 RowMapper）、HttpServlet（定义 service → doGet/doPost 流程）。

## 四、向量检索方案对比（余弦相似度 vs 欧式距离 vs 点积）

**面试官问："向量检索用的什么相似度计算？为什么不选其他的？"**

### 三种主流相似度计算方式

| 方案 | 公式 | 值域 | 特点 | 适用场景 |
|------|------|------|------|---------|
| **余弦相似度（Cosine）** | cos(A,B) = (A·B) / (\|A\|×\|B\|) | [-1, 1] | 只看方向不看大小，归一化后不受向量长度影响 | **文本检索（最常用）** |
| **欧式距离（Euclidean）** | d(A,B) = √Σ(ai-bi)² | [0, ∞) | 看绝对距离，受向量长度影响 | 图像检索、推荐系统 |
| **点积（Dot Product）** | A·B = Σ(ai×bi) | (-∞, ∞) | 方向 + 大小都考虑，计算最快 | 向量已归一化时等价余弦，LLM 内部常用 |

### 为什么我们选余弦相似度

> 1. **文本语义用方向表达**：两个文本"含义相似"在向量空间里表现为"方向相近"，与长度无关。"这个手机很好用"和"这个手机特别好"含义几乎一样，但后者多几个字，向量长度可能不同。余弦相似度只看方向，不受长度干扰。
>
> 2. **PgVector 默认支持**：PgVector 的 `<=>` 操作符就是余弦距离（1 - cosine similarity），Spring AI 的 `PgVectorStore` 默认就用它。
>
> 3. **Embedding 模型的输出特性**：nomic-embed-text 等模型输出的向量已经做了归一化（长度=1），此时余弦相似度和点积等价。但余弦相似度语义更明确（0=完全不相关，1=完全相关）。
>
> 4. **业界标准**：OpenAI、Cohere、LangChain 等主流方案都用余弦相似度做文本检索。生态成熟，踩坑少。

### 各方案什么时候用

> - **余弦相似度**：文本检索（RAG）、语义匹配、推荐（内容相似度）。最通用。
> - **欧式距离**：图像检索（像素级距离）、地理坐标距离、异常检测（离群点检测）。
> - **点积**：向量已归一化时的快速近似（计算量最小，无需归一化步骤）、LLM 注意力机制内部（Q·K^T）。

**追问预判：**

- **Q："PgVector 支持哪些距离度量？"** A："支持三种：<=> 余弦距离、<-> 欧式距离、<#> 内积距离。创建索引时指定。Spring AI 默认用余弦距离。"
- **Q："向量需要归一化吗？"** A："如果用余弦相似度，理论上不需要（公式里自带归一化）。但提前归一化可以加速检索（避免每次计算都做除法）。nomic-embed-text 输出的向量已经归一化了。"
- **Q："余弦相似度 0.7 算高还是低？"** A："取决于 Embedding 模型。nomic-embed-text 在相关问答上平均 0.75~0.85，不相关 0.35~0.55。不能跨模型比较分数。"

## 五、Retriever 理论（检索器进阶）

**面试官问："除了向量检索，还了解哪些检索方式？"**

### 单路检索 vs 多路检索

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| **向量检索（Dense Retrieval）** | 把文本转成向量，算相似度 | 语义理解强，但计算成本高 |
| **关键词检索（Sparse Retrieval / BM25）** | 倒排索引，TF-IDF 或 BM25 打分 | 精确匹配强（型号、人名），但不懂语义 |
| **混合检索（Hybrid）** | 向量 + 关键词，分数加权融合 | 兼顾语义和精确匹配，效果最好 |

**扩展说明：**

> "向量检索的盲区是'精确匹配'。比如用户搜 'iPhone 15 Pro Max 256G'，向量检索可能找到'iPhone 15 Pro'（语义相似但不是同款），而 BM25 能精确匹配到完整的型号字符串。
>
> 混合检索是当前 RAG 的主流方向：先分别用向量检索和 BM25 各召回 top K，再用 RRF（Reciprocal Rank Fusion）融合排序。Elasticsearch 8.x 已经原生支持混合检索。
>
> 我们的项目目前只用了向量检索（PgVector），后续可以加 BM25 做混合。"

### Reranking（重排序）

> **为什么需要：** 向量检索（Bi-Encoder）速度快但精度有限——query 和文档独立编码，丢失了它们之间的交互信息。Reranking（Cross-Encoder）同时看 query 和文档的完整内容，精度更高但更慢。
>
> **典型流程：** 向量检索 top 50 → Reranking 精排 top 5 → 注入 Prompt
>
> **类比：** Bi-Encoder = 粗排（从 100 万文档中快速筛出 50 个），Cross-Encoder = 精排（仔细对比 50 个文档和 query 的相关性，挑出最好的 5 个）。
>
> 我们的项目目前没有用 Reranking，用相对分数过滤作为轻量替代。面试时可以说'计划引入 Reranking 做精排'。

### Query Rewrite（查询重写）

> 用户原始 query 可能模糊或有指代（"那个"、"上次说的"）。Query Rewrite 在检索前把 query 改写为更明确的表述。
>
> 方式：(1) 用 LLM 重写 query (2) 用历史对话补充上下文 (3) 拆分子查询。
>
> 我们项目的 ChatMemory Advisor 已经解决了"指代消解"问题——RAG Advisor 执行时已经能看到历史消息。但主动 query 重写还没做。
