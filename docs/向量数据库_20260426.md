# 向量数据库原理与企业实践（2026-04-26）

> 以关系型数据库（MySQL）为对照，理解向量数据库的核心原理、适用场景和企业选型。

---

## 一、从 MySQL 出发——为什么需要向量数据库？

### 1.1 MySQL 能做什么

```sql
-- 精确查询
SELECT * FROM products WHERE name = 'iPhone 16';

-- 模糊查询（LIKE，只匹配字符）
SELECT * FROM products WHERE name LIKE '%iPhone%';

-- 全文检索（MATCH AGAINST，基于关键词匹配）
SELECT * FROM articles WHERE MATCH(content) AGAINST('Java并发编程');

-- 范围查询
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
```

**MySQL 擅长的**：精确匹配、范围查询、结构化数据过滤、事务（ACID）

**MySQL 做不了的**：语义相似度搜索

```
用户搜索："怎么治疗感冒鼻塞流涕"
MySQL LIKE：只能匹配包含"感冒"或"鼻塞"的文本
            找不到"上呼吸道感染的缓解方法"（语义相同，用词不同）

向量数据库：能把"感冒鼻塞"和"上呼吸道感染"理解为语义相近 → 能找到
```

### 1.2 本质区别

| 维度 | 关系型数据库（MySQL） | 向量数据库 |
|------|----------------------|------------|
| **存储数据类型** | 行和列（结构化） | 向量（浮点数数组） |
| **查询方式** | SQL，精确匹配/范围查询 | 相似度计算（余弦/欧氏距离） |
| **查询结果** | 匹配或不匹配（布尔） | 相似度分数（0~1 连续值） |
| **索引结构** | B+Tree | HNSW / IVF / ANN（近似最近邻） |
| **适合场景** | 订单、用户、财务等业务数据 | 文档检索、推荐、图像识别等 AI 场景 |
| **事务支持** | 完整 ACID | 大部分不支持或有限支持 |

## 二、向量的本质——把语义变成数字

### 2.1 什么是向量

向量就是一串数字，比如 768 个浮点数。文本被 Embedding 模型转换后，**语义相近的文本向量也相近**。

```
文本                              → Embedding 模型 → 768 维向量
"Java是面向对象的语言"             →              → [0.12, -0.34, 0.56, ..., 0.78]
"Java是一门面向对象的编程语言"      →              → [0.11, -0.33, 0.55, ..., 0.79]  ← 很接近
"Python适合数据分析"               →              → [0.45, 0.22, -0.18, ..., 0.33]  ← 有距离
"今天深圳天气很好"                 →              → [0.89, 0.12, -0.67, ..., 0.01]  ← 差很远
```

### 2.2 维度是什么意思

"768 维"意味着用 **768 个数字** 来描述一段文本的语义特征。

| 维度数 | 对比 | 直观理解 |
|--------|------|----------|
| 128 维 | 低精度 | 用 128 个特征描述一个人（大致轮廓） |
| 384 维 | 中精度 | 用 384 个特征（加了面部细节） |
| 768 维 | 标准精度 | nomic-embed-text 的维度，够用 |
| 1536 维 | 高精度 | OpenAI text-embedding-3-small |
| 2048 维 | 超高精度 | 智谱AI embedding-3 |
| 3072 维 | 极高精度 | OpenAI text-embedding-3-large |

**维度越高**：语义表达越精确，但计算量越大、存储空间越大。

### 2.3 一条向量数据占多少空间

```
768 维 float32 向量：
768 × 4 bytes = 3,072 bytes ≈ 3 KB / 条

100 万条文档：
100万 × 3 KB = 3 GB（纯向量数据，不含原始文本）

对比 MySQL：
100 万条订单记录（10个字段）≈ 200 MB
```

**结论**：向量数据天然比结构化数据大 10-50 倍。

## 三、相似度计算——怎么判断"像不像"

### 3.1 余弦相似度（最常用）

```java
// 两个向量 A 和 B 的余弦相似度
cosineSimilarity(A, B) = (A·B) / (|A| × |B|)

// A·B = A1×B1 + A2×B2 + ... + A768×B768  （点积）
// |A| = √(A1² + A2² + ... + A768²)       （向量的模/长度）
```

**直觉理解**：不看向量的长度，只看方向。方向越接近，相似度越高。

```
结果范围：-1 到 1
  1.0  → 完全相同方向（语义完全相同）
  0.8  → 非常相似
  0.5  → 有点相关
  0.0  → 完全无关
 -1.0  → 完全相反
```

### 3.2 欧氏距离（另一种方式）

```java
euclideanDistance(A, B) = √((A1-B1)² + (A2-B2)² + ... + (A768-B768)²)
```

**直觉理解**：两个向量在空间中的直线距离。距离越小越相似。

### 3.3 100 万条数据的暴力搜索

```
如果对 MySQL 100 万条数据做 LIKE '%关键词%'：
  → B+Tree 索引失效，全表扫描，毫秒级（MySQL 在内存中扫描也很快）

如果对 100 万条 768 维向量做暴力搜索（逐一计算余弦相似度）：
  → 100万 × 768次乘加运算 = 7.68 亿次浮点运算
  → CPU 单线程约需 3-5 秒 ❌ 太慢！
```

**这就是为什么需要向量数据库**——它不是暴力搜索，而是用近似最近邻（ANN）算法加速。

## 四、ANN 索引算法——向量数据库的核心

### 4.1 暴力搜索 vs ANN

| 方式 | 精度 | 速度 | 100万条耗时 |
|------|------|------|------------|
| 暴力搜索（KNN） | 100% 精确 | 慢 | 3-5 秒 |
| HNSW（ANN） | 99%+ 近似 | 快 | 1-5 毫秒 |
| IVF（ANN） | 95-99% 近似 | 更快 | <1 毫秒 |

**ANN = Approximate Nearest Neighbor（近似最近邻）**
牺牲一点点精度（99% 变 95%），换取 100-1000 倍的速度提升。

### 4.2 HNSW 算法（最主流）

```
HNSW = Hierarchical Navigable Small World（分层可导航小世界图）

类比：社会关系网
  ┌─────────────────────────────────┐
  │  Layer 2（高管层）                 │  每层是一个图
  │    张三 ──── 李四                │  节点=向量，边=相近关系
  │                                  │  高层连接少（远距离跳转）
  ├─────────────────────────────────┤  低层连接多（精细搜索）
  │  Layer 1（经理层）                 │
  │    张三 ──── 李四 ──── 王五      │
  │     │          │          │       │
  │    赵六 ──── 钱七 ──── 孙八      │
  ├─────────────────────────────────┤
  │  Layer 0（基层，所有人）           │
  │    张三 ──── 赵六 ──── 周九      │
  │     │    ╲   │     ╲    │         │
  │    钱七 ──── 王五 ──── 孙八 ── 吴十│
  └─────────────────────────────────┘

搜索过程：
1. 从最高层（Layer 2）的入口节点开始
2. 每层内沿最近的边跳转，找到该层最近的节点
3. 下到下一层，以上一层的结果为起点继续搜索
4. 到达最底层（Layer 0），精确找到最近的 K 个节点
```

**为什么快**：高层"大步跳"快速缩小范围，底层"小步走"精确匹配。类似先坐飞机到城市，再打车到小区。

## 五、MySQL vs 向量数据库——企业级对比

### 5.1 存储结构对比

```
┌─ MySQL 表（orders）────────────────────────────┐
│ id | user_id | amount | status | create_time  │
│  1 |   101   | 299.00 | paid   | 2026-04-26  │
│  2 |   102   | 150.00 | paid   | 2026-04-26  │
│ ...                                           │
│ 索引：B+Tree on (user_id), (create_time)       │
└───────────────────────────────────────────────┘

┌─ 向量数据库表（documents）────────────────────┐
│ id | content                    | embedding                    │
│  1 | "Spring AI 是..."          | [0.12, -0.34, 0.56, ...768个]│
│  2 | "DeepSeek 是..."           | [0.45, 0.22, -0.18, ...768个]│
│ ...                                                       │
│ 索引：HNSW on (embedding)                                 │
└──────────────────────────────────────────────────────────┘
```

### 5.2 查询方式对比

```sql
-- MySQL：精确查询
SELECT * FROM products WHERE category = '手机' AND price < 5000;

-- 向量数据库：相似度查询
SELECT id, content, cosine_similarity(embedding, [0.12, -0.34, ...]) AS score
FROM documents
ORDER BY score DESC
LIMIT 5;
```

### 5.3 企业使用场景对比

| 场景 | 用 MySQL | 用向量数据库 | 混合使用 |
|------|----------|-------------|----------|
| 用户登录/注册 | ✅ | ❌ | — |
| 订单/支付 | ✅ | ❌ | — |
| 关键词搜索 | ✅ LIKE/FULLTEXT | △ 不擅长 | — |
| 语义搜索（"怎么治感冒"） | ❌ | ✅ | — |
| 智能客服（RAG） | ❌ | ✅ | ✅ 向量库检索 + MySQL 存会话记录 |
| 商品推荐 | △ 基于标签 | ✅ 基于用户行为向量 | ✅ MySQL 存商品信息 + 向量库做推荐 |
| 图片搜索 | ❌ | ✅ 图片转向量 | ✅ MySQL 存图片元数据 + 向量库做搜索 |
| 风控 | ✅ 规则引擎 | ✅ 异常行为向量 | ✅ 两者互补 |

## 六、企业向量数据库选型——为什么是 pgvector

> **⚠️ 选型变更说明（2026-04-26 增补）**
>
> 上一版以 Milvus 为企业首选。结合实际求职分析后调整：
> - 深圳中小企业 / SaaS / 跨境电商方向，**pgvector 覆盖面更广**
> - pgvector 兼容 SQL，学习成本最低，与 Java 后端背景最匹配
> - 面试中更能体现"工程务实"思维（不是什么高大上都上，而是选最合适的）
> - Milvus 作为"了解即可"，遇到数据量到亿级再考虑

### 6.1 选型决策树（5 个问题定位）

```
数据规模超过 1 亿条向量？
  ├── 是 → 原生向量数据库（Milvus / Pinecone）
  └── 否 ↓

需要强事务一致性（ACID）？
  ├── 是 → 传统数据库 + 向量扩展（PostgreSQL + pgvector）
  └── 否 ↓

需要同时做复杂条件过滤（JOIN 多表）？
  ├── 是 → 传统数据库 + 向量扩展（pgvector）
  └── 否 ↓

团队有专职 DBA/运维？没有向量检索经验？
  ├── 有 → 可以考虑原生向量数据库（Milvus）
  └── 没有或不确定 → pgvector（复用现有 DBA 知识）

───────────────────────────────────
结论：大多数中小企业 → pgvector
     大型/金融/十亿级 → Milvus
```

### 6.2 市场格局（2025-2026）

| 数据库 | 类型 | 数据规模 | 部署方式 | 代表用户 | 适合我的程度 |
|--------|------|----------|----------|----------|------------|
| **pgvector** | PG 扩展 | **百万级** | **随 PG 部署** | 中小企业、电商、SaaS | **★★★★★ 主力** |
| Milvus | 开源分布式 | 十亿+级 | 私有化/Docker | 搜狐、小米、Shopee | ★★★☆☆ 了解 |
| Qdrant | 开源 | 百万~千万级 | 私有化 | 电商推荐 | ★★☆☆☆ 知道 |
| Pinecone | 商业 SaaS | 亿级 | 全托管 | 海外企业 | ★☆☆☆☆ 不用 |
| 腾讯云 VectorDB | 商业云服务 | 千亿级 | 云服务 | 金融、政务 | ★★★☆☆ 了解 |

### 6.3 pgvector 为什么是中小企业的首选

**1. 零额外运维成本**
- 不需要独立的数据库组件，只是 PostgreSQL 的一个扩展（`CREATE EXTENSION vector`）
- 已有 PostgreSQL 的团队直接升级即可
- 没有 Milvus 那种需要 etcd + MinIO + Milvus 三个组件的部署负担

**2. SQL 生态无缝融合**
- 向量列和普通列在同一张表里，支持混合查询
- 事务支持（ACID）：向量数据和业务数据可以一起事务提交
- DBA 不需要学新技术，用现有的 PostgreSQL 监控、备份工具就行

**3. 中小规模性能够用**
- 百万级数据 + HNSW 索引 → 毫秒级检索
- 对于大多数 RAG 知识库、电商商品推荐场景，百万级完全够用

**4. Spring AI 官方支持**
- `spring-ai-starter-vector-store-pgvector` 稳定可用
- 切换成本低：改 pom.xml + yml 即可，Java 代码零改动

**5. 大厂也在用**
- OpenAI、Netflix、Shopify 已全面转向 pgvector
- 国内越来越多中小企业选择 pgvector 作为 RAG 向量存储

### 6.4 pgvector 的局限性（面试能说）

| 局限 | 说明 | 什么时候需要换 Milvus |
|------|------|----------------------|
| 数据规模天花板 | 百万级性能好，千万级开始衰减 | 向量数据 > 1000 万条 |
| 横向扩展困难 | 主要靠单机（可读写分离） | 单机扛不住 QPS |
| 索引算法有限 | 只有 IVFFlat 和 HNSW | 需要特殊索引（如 GPU 加速） |
| 不支持多模态 | 纯向量，没有图片/音频处理 | 需要图片+文本混合检索 |

**面试回答模板**：
> "我们选 pgvector 是基于当前业务阶段判断——数据量百万级以内，团队熟悉 PostgreSQL，不需要额外运维成本。如果未来数据量到千万级以上，会评估 Milvus 做水平拆分。选型不是追求技术最先进，而是选最合适的。"

### 6.5 跨境电商场景的适配性

pgvector 在跨境电商场景有天然优势——**混合查询**：

```sql
-- 跨境电商：找到与搜索词语义相似的手机配件，同时过滤价格和库存
SELECT p.id, p.name, p.price,
       1 - (p.embedding <=> '[问题向量]') AS similarity
FROM products p
WHERE p.category = '手机配件'           -- 结构化过滤
  AND p.stock > 0                      -- 库存过滤
  AND p.price BETWEEN 10 AND 200       -- 价格区间
ORDER BY p.embedding <=> '[问题向量]'  -- 语义相似度排序
LIMIT 10;
```

这在 Milvus 中做不到（或需要额外步骤），在 pgvector 中一行 SQL 搞定。

## 七、pgvector——MySQL 程序员的最小迁移路径

### 7.1 为什么 pgvector 值得关注

如果你的团队只熟悉 MySQL，不想引入新的数据库组件，**pgvector 是最平滑的过渡方案**。

但注意：MySQL 8.0 目前**没有**原生向量搜索支持。MySQL 9.0 开始实验性支持 HeatWave Vector Store，但还不够成熟。所以实际选型通常是 **PostgreSQL + pgvector** 而不是 MySQL。

**好消息是：PostgreSQL 和 MySQL 的 SQL 语法 90% 以上是通用的**，Java 后端转 PG 几乎零成本。

### 7.2 pgvector 与 MySQL 的语法对比

```sql
-- ============ MySQL 常规操作 ============

-- 建表
CREATE TABLE products (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(255),
    price DECIMAL(10,2),
    category VARCHAR(100),
    INDEX idx_category (category)
);

-- 插入
INSERT INTO products (name, price, category) VALUES ('iPhone 16', 7999, '手机');

-- 查询
SELECT * FROM products WHERE category = '手机' AND price < 5000;

-- ============ PostgreSQL + pgvector 向量操作 ============

-- 启用扩展
CREATE EXTENSION vector;

-- 建表（多了 embedding 列，类型是 vector(768)）
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    embedding vector(768),           -- 768维向量
    metadata JSONB                    -- 元数据（灵活的 JSON 字段）
);

-- 创建向量索引（HNSW 算法）
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);

-- 插入（向量通常由应用层通过 Embedding 模型生成）
INSERT INTO documents (content, embedding)
VALUES ('Spring AI 是 Java 的 AI 框架', '[0.12, -0.34, 0.56, ...768个]');

-- 向量相似度查询
SELECT id, content,
       1 - (embedding <=> '[0.11, -0.33, 0.55, ...]') AS similarity  -- <=> 是余弦距离
FROM documents
ORDER BY embedding <=> '[0.11, -0.33, 0.55, ...]'   -- 按距离排序（越小越相似）
LIMIT 5;

-- 混合查询（向量相似度 + 结构化条件）
SELECT id, content,
       1 - (embedding <=> '[0.11, -0.33, 0.55, ...]') AS similarity
FROM documents
WHERE metadata->>'source' = 'product_manual'    -- JSONB 过滤
ORDER BY embedding <=> '[0.11, -0.33, 0.55, ...]'
LIMIT 5;
```

### 7.3 SQL 语法对照表

| 操作 | MySQL | PostgreSQL + pgvector |
|------|-------|----------------------|
| 建表 | `CREATE TABLE` | `CREATE TABLE ... (embedding vector(768))` |
| 自增主键 | `AUTO_INCREMENT` | `SERIAL` / `BIGSERIAL` |
| 创建索引 | `CREATE INDEX` | `CREATE INDEX USING hnsw (embedding vector_cosine_ops)` |
| 精确查询 | `WHERE col = '值'` | `WHERE col = '值'`（一样） |
| 向量查询 | ❌ 不支持 | `ORDER BY embedding <=> '[...]' LIMIT 5` |
| 混合查询 | `WHERE category = '手机'` | `WHERE metadata->>'category' = '手机' ORDER BY embedding <=> '[...]'` |
| JSON 字段 | `JSON`（5.7+） | `JSONB`（更高效，支持索引） |

### 7.4 距离运算符速查

pgvector 提供 3 种距离运算符：

| 运算符 | 距离类型 | 用途 | 值域 |
|--------|----------|------|------|
| `<=>` | 余弦距离 | **最常用**，文本语义相似度 | 0（相同）~ 2（完全相反） |
| `<->` | 欧氏距离 (L2) | 图像/音频向量 | 0（相同）~ ∞ |
| `<#>` | 内积距离 | 归一化后的向量 | 越小越相似 |

```sql
-- 余弦相似度 = 1 - 余弦距离
SELECT 1 - (embedding <=> '[...]) AS cosine_similarity;
```

## 八、Milvus——大规模场景的备选方案

> 以下为原文档内容，Milvus 作为"知道有这个东西、理解区别"的储备知识。

### 8.1 Milvus 是什么

Milvus 是 LF AI & Data 基金会的开源分布式向量数据库，专为**十亿级以上**的向量检索设计。

**适合场景**：大型互联网公司、金融、政务、多模态检索（图片+视频+文本）

### 8.2 Milvus 的优势

**1. 国产开源，信创合规**
- 国内大厂广泛使用（搜狐、小米、宜信等）

**2. 性能天花板最高**
- 分布式架构，支持横向扩展
- 十亿级向量毫秒级查询
- QPS 超百万级

**3. 索引算法丰富**

| 索引类型 | 适合场景 | 内存占用 | 查询速度 |
|----------|----------|----------|----------|
| FLAT（暴力） | 小数据量（<10万） | 中 | 慢 |
| IVF_FLAT | 中等规模 | 中 | 中等 |
| IVF_PQ | 大规模，内存受限 | 低 | 中等 |
| HNSW | 通用，平衡精度和速度 | 高 | 快 |
| DISKANN | 超大规模，磁盘存储 | 极低 | 中等 |

**4. Spring AI 支持**
- `spring-ai-starter-vector-store-milvus`

### 8.3 Milvus 架构简图

```
┌──────────────────────────────────────────────────┐
│                    客户端 SDK                      │
│          Java / Python / Go / REST API            │
└──────────────────────┬───────────────────────────┘
                       │
```

### 8.4 pgvector vs Milvus 深度对比

| 对比维度 | **pgvector** | **Milvus** |
|----------|-------------|------------|
| 定位 | PostgreSQL 扩展 | 独立分布式向量数据库 |
| 部署复杂度 | **极低**（装 PG 扩展即可） | **高**（etcd + MinIO + Milvus 三个组件） |
| 运维成本 | **复用 DBA** | **需专职向量数据库运维** |
| 数据规模 | 百万级（推荐） | 十亿级+ |
| 事务支持 | **完整 ACID** | 弱一致性 |
| SQL 支持 | **完整 SQL**，混合查询强 | 需专用 SDK/API |
| Java 接入 | Spring Data JPA + pgvector | Milvus Java SDK |
| 适合团队 | 中小企业、Java 后端转 AI | 大型公司、有专职 DBA |

## 九、Spring AI 中接入向量数据库

### 9.1 当前项目（SimpleVectorStore）

```java
// 内存存储，重启数据丢失
@Bean
public VectorStore vectorStore(OllamaEmbeddingModel embeddingModel) {
    return SimpleVectorStore.builder(embeddingModel).build();
}
```

**适合**：学习、Demo、临时验证

### 9.2 接入 PGVector（⭐ 推荐中小企业，我们的下一步）

**pom.xml**：
```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-pgvector</artifactId>
</dependency>
```

**application.yml**：
```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/ai_db
    username: postgres
    password: 123456
  ai:
    vectorstore:
      pgvector:
        initialize-schema: true    # 自动创建向量表
```

**代码**：不需要写！Spring AI 自动配置会创建 `PgVectorStore` Bean，替代 `SimpleVectorStore`。

**前提条件**：
1. 安装 PostgreSQL（Win11 推荐 Installer 或 Docker）
2. 执行 `CREATE EXTENSION vector;` 启用向量扩展
3. 创建数据库 `CREATE DATABASE ai_db;`

### 9.3 接入 Milvus（大规模场景备选）

**pom.xml**：
```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-vector-store-milvus</artifactId>
</dependency>
```

**application.yml**：
```yaml
spring:
  ai:
    vectorstore:
      milvus:
        client:
          host: localhost
          port: 19530
        databaseName: ai_db
        collectionName: documents
        initialize-schema: true
```

**代码**：同样不需要写，自动配置。

## 十、企业实战建议

### 10.1 从 Demo 到生产的升级路径

```
阶段1（当前）: SimpleVectorStore（内存）
    ↓ 理解原理后
阶段2（⭐ 下一步）: PGVector（单机持久化，百万级够用）
    ↓ 数据量到千万级 / 公司有专职 DBA
阶段3: Milvus（分布式、高性能）
```

### 10.2 代码改动量

从 SimpleVectorStore 切换到 PGVector 或 Milvus：
- **Java 代码改动：0 行**（都是实现 VectorStore 接口）
- **只改**：pom.xml 加依赖 + application.yml 加配置
- 这就是 Spring AI 抽象层的价值

### 10.3 生产环境必须考虑的问题

| 问题 | 说明 | 解决方案 |
|------|------|----------|
| 数据持久化 | SimpleVectorStore 重启丢失 | 换 PGVector/Milvus |
| 向量维度对齐 | 换 Embedding 模型后维度变化 | 所有数据需重新向量化 |
| 检索性能 | 百万级以上暴力搜索太慢 | 使用 HNSW 索引（pgvector 和 Milvus 都支持） |
| 混合检索 | 关键词+语义同时搜索 | pgvector：SQL WHERE + ORDER BY 混合 |
| 数据同步 | 业务数据变化后向量需更新 | 写入时同步更新向量 |
| 监控 | 检索质量、延迟监控 | 记录相似度分数、检索耗时 |

## 十一、一句话总结

> **MySQL 存的是"是什么"，向量数据库存的是"像什么"。**
> 
> 关系型数据库回答"精确匹配"问题，向量数据库回答"语义相似"问题。
> 企业中两者不是替代关系，而是互补——业务数据用 MySQL，AI 检索用向量数据库，通过关联 ID 打通。
>
> 对于中小企业和 Java 后端工程师来说，**pgvector 是最务实的选择**——用 SQL 的方式做向量检索，学习成本最低，运维成本最低。
