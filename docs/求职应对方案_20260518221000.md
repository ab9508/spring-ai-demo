## 一、现状诊断

### 投递漏斗（5/13 - 5/18，4个工作日）

```
打招呼  250 人
   ↓  回应率 < 50%（约 ≤125 人）
有回应  ~125 人
   ↓  简历转化率 62/125 ≈ 50%
发出简历  62 份
   ↓  面试转化率 1/62 = 1.6%   ← 核心断层（正常应 10~20%）
获得面试  1 场
   ↓  被更优秀候选人录取
录用  0
```

### 结论

- **量不是问题**，打招呼 250 个已经足够
- **核心断层**：62 份简历只换 1 场面试（1.6% vs 正常 10~20%）
- 说明问题在于：简历没有精准命中 AI 岗 HR 的筛选关键词 + 岗位选择存在偏差

## 三、简历改造方案

### 3.1 AI 项目描述改造（最高 ROI）

**改造前（弱）：**
> 基于 Spring AI 实现了 RAG 知识库问答功能，接入 DeepSeek 模型

**改造后（强）：**
> 自研 RAG Advisor（PgVector + 相对分数过滤），解决多轮追问场景下向量召回语义断层问题，领域问答准确率较 Baseline 提升约 35%；手写 Redis ChatMemory 组件，实现跨会话多轮记忆，支持 Redis 故障降级；基于 Tool Calling 构建 Agent 自动化流程，支持意图识别 → 工具路由 → 结构化输出全链路

## 五、面试准备重点

### 5.1 AI 专项（必须会讲的 3 个核心故事）

**故事 1：RAG 系统设计**
- 核心点：为什么用相对分数过滤 + Advisor 链顺序设计（Memory 先于 RAG）
- 关键数据：topK=5，top1<0.45 拦截，top1-top2<0.08 拦截
- 踩坑：绝对 threshold 不稳定，领域外问题分数 0.35~0.62

**故事 2：Redis ChatMemory 自研**
- 核心点：为什么不用原生（不支持 Redis）+ 如何容灾（Redis 挂了双写 SQLite/文件降级）
- 关键数据：maxMessages=20，Redis List 存储，JSON 序列化
- 踩坑：Spring AI Alibaba Redis ChatMemory 与 Boot 3.4.5 版本冲突

**故事 3：结构化输出 + Tool Calling 冲突问题**
- 核心点：ChatClient.Builder 是可变对象，同一 builder 被污染
- 解决：`ChatClient.builder(chatModel)` 工厂方法每次创建全新 Builder
- 底层原因：带 tools 字段 vs 不带 tools 字段的 HTTP 请求体差异

### 5.2 Java 基础必背（AI 岗也会问）

| 考点 | 一句话核心 |
|------|----------|
| HashMap | 数组+链表+红黑树，扩容 2 倍，JDK8 链表长度>8 树化 |
| 线程池 7 参数 | 核心线程/最大线程/存活时间/队列/线程工厂/拒绝策略 |
| synchronized vs Lock | synchronized JVM 级，Lock API 级可中断可超时 |
| Redis 缓存三问 | 穿透=布隆过滤器，击穿=互斥锁，雪崩=TTL 随机+多级缓存 |
| 分布式锁 | Redisson = SET NX PX + 看门狗续期 + Hash 可重入 |

### 5.3 系统设计题（必备）

**智能客服系统设计**（完美融合 Java + AI 能力）：
- 前端接入 → 网关（Sentinel 限流）→ Spring Boot
- 意图识别（LLM 分类）→ Tool Calling（调业务 API）
- RAG 知识库兜底 → Redis ChatMemory 多轮对话
- MQ 异步推送（RocketMQ）→ 监控告警

### 5.4 薪资谈判策略

- 报价：先说 25K，接受 22K，底线 20K
- 话术：「我了解到深圳同类岗位行情在 22-28K，结合我的 AI 实战经验，我期望在 22-25K 区间」
