## 一、项目概述（30 秒电梯演讲）

**正确说法：**

> "我用 Spring AI 搭建了一个电商智能客服系统，集成了多项核心能力：
> 1. RAG 知识库：支持多格式文档（PDF/Word/Excel/PPT），自动切片向量化，基于 PgVector 持久化存储，带三级相对分数过滤控制检索质量
> 2. Tool Calling：让 AI 自主调用订单查询、库存查询、售后工单等业务接口，使用 1.0.x 新写法 @Tool 注解
> 3. 对话记忆：自研 Redis ChatMemory + 摘要压缩，用装饰器模式实现三层存储
> 4. 意图识别：双 Client 架构隔离结构化输出和 Agent 对话，解决 LLM 工具调用优先级问题
>
> 技术选型：Chat 用 DeepSeek API，Embedding 用 Ollama 本地部署（nomic-embed-text），向量存储用 PgVectorStore。"

**核心亮点（简历可写）：**

- 自研 6 个组件增强 Spring AI 基础能力
- 三层相对分数过滤替代固定阈值
- 装饰器模式实现对话记忆摘要压缩
- Jackson DTO 中转方案解决 Spring AI Message 无参构造问题

## 二、RedisChatMemoryRepository（对话记忆存储）

### 2.1 面试官问："你的对话记忆怎么做的？为什么不用 Spring AI 原生的？"

**3 分钟版回答：**

> **痛点：** Spring AI 1.0.x 原生只支持 InMemory / JDBC / Cassandra / Neo4j 四种 ChatMemory 存储，**没有 Redis 实现**。Spring AI Alibaba 的 Redis 实现要求 Spring Boot 3.5.x，和我们的 3.4.5 版本冲突。
>
> **怎么做：** 自己实现 `ChatMemoryRepository` 接口，用 Redis List 存储每个 conversationId 的消息列表。`MessageWindowChatMemory.builder().chatMemoryRepository(myRepo).maxMessages(20).build()` 注入进去，框架自动调用我们的 `saveAll()` 和 `findByConversationId()`，对上层 Advisor 完全透明。
>
> **为什么不选其他方案：** JDBC 高并发压力大、Cassandra/Neo4j 运维成本高、InMemory 重启丢失。
>
> **还可以怎样：** 升级到 Boot 3.5.x 后切回官方 Redis 实现，因为 ChatMemoryRepository 只是一个接口，替换实现零成本。

**底层原理：**

> `ChatMemoryRepository` 是策略接口，4 个方法：`findConversationIds()` / `findByConversationId()` / `saveAll()` / `deleteByConversationId()`。`MessageWindowChatMemory` 内部持有它，负责加载消息 + 窗口裁剪。持久化由 Repository 负责，窗口裁剪由框架自动做，职责分离。

**追问预判：**

- **Q："MessageWindowChatMemory 和你的 Repository 怎么配合？"**
  A：策略模式。`MessageWindowChatMemory.builder().chatMemoryRepository(repository).maxMessages(20).build()` 注册为 Bean，Advisor 自动拿到，框架全自动。

- **Q："Redis 数据格式变了怎么迁移？"**
  A：加 `schemaVersion` 字段，读取时根据版本号兼容处理，类似 Flyway 迁移。当前快速迭代阶段没做，列在后续优化点里。

### 2.2 面试官问："Redis 存储对话消息，序列化怎么处理？"

**3 分钟版回答：**

> **痛点：** `AssistantMessage` 和 `ToolResponseMessage` 没有无参构造方法，Jackson 直接反序列化会抛异常。
>
> **初版（已废弃）：** 手动 JSON 拼接（escapeJson/unescapeJson），零依赖但嵌套 JSON 转义容易出 bug，代码量 ~120 行。
>
> **最终方案（v3，Jackson + DTO 中转）：** 定义 `MessageDto` / `ToolCallDto` / `ToolResponseDto` 三个 @Data POJO。序列化：Message → DTO → objectMapper.writeValueAsString()。反序列化：objectMapper.readValue(json, MessageDto.class) → DTO → Message（手动调带参构造）。
>
> **为什么选 Jackson：** spring-boot-starter-web 传递依赖了 jackson-databind，零引入成本。FastJSON 有安全漏洞历史，Gson 需额外引入。

**实际案例：**

> "初版手动拼接 JSON，toolCalls 参数本身是 JSON 字符串时转义嵌套出 bug。改用 Jackson DTO 中转，代码从 359 行降到 234 行，再没出过转义问题。"

**底层原理：**

> Jackson 反序列化要求无参构造 + setter。Message 子类没有无参构造（不可变对象设计），所以用 DTO 做中间层——DTO 有无参构造给 Jackson 用，Message 保持不可变。这是企业级标准做法（Spring MVC @RequestBody 也常用 DTO）。

**追问预判：**

- **Q："DTO 转换手写不麻烦？"** A：写一次 30 行，Message 字段稳定。比手动拼接 120 行易出 bug 的代码强。且编译器能发现字段不匹配。
- **Q："Message 加了新字段怎么办？"** A：DTO 也加，Jackson 默认忽略多余/缺失字段。

---

### 2.3 面试官问："Tool Calling 的消息能正确存取吗？"

**3 分钟版回答：**

> **痛点：** Tool Calling 产生两类特殊消息（AssistantMessage 含 toolCalls + ToolResponseMessage 含 toolResponses），序列化处理不好会导致上下文断裂。
>
> **怎么做：** DTO 中有 `toolCalls` 和 `toolResponses` 字段。序列化时把 Message 的工具信息映射到 DTO 字段（Jackson 自动处理 JSON 字符串化），反序列化时从 DTO 还原 Message（手动调带参构造）。三类消息都完整存取。
>
> **关键：** 如果只存 UserMessage 和普通 AssistantMessage，Agent 对话上下文断了，LLM 会重复调工具。

**追问预判：**

- **Q："一个请求调 5 个工具，Redis 能处理吗？"** A：能。产生 11 条消息，几 KB。但注意 maxMessages 窗口，调太多工具后早期上下文会被截断。
- **Q："嵌套 JSON 参数怎么处理？"** A：toolCalls.arguments 本身就是 JSON 字符串，Jackson 当普通字符串序列化/反序列化即可。

---

### 2.4 面试官问："为什么全量删除再写入，不追加？删完写入失败数据不就丢失了？"

**3 分钟版回答：**

> **为什么全量写：** `MessageWindowChatMemory.saveAll()` 传入的是完整窗口列表（最近 20 条），不是增量。框架设计如此——ChatMemory 的职责是"保存完整对话状态"。追加模式需要自己维护"哪些消息已写入"的状态，复杂度更高。
>
> **删完写入失败怎么办（当前有此风险）：**
> 1. **Redis Pipeline**：DELETE + RPUSH 放同一个 Pipeline，减少网络往返，但不保证原子性
> 2. **Lua 脚本（推荐）**：把"删除 + 写入"包装成原子操作，要么全成功要么全失败。集群模式用 Hash Tag 保证同 slot
> 3. **Write-First 模式**：先写临时 Key → 确认成功 → 删旧 Key → RENAME 临时 Key 为正式 Key。RENAME 原子，最终状态只有"新数据"或"旧数据"
>
> **为什么当前没做：** MVP 阶段，影响范围可控。金融/医疗场景必须用 Lua 脚本。

**实际案例：**

> "压测时 Redis 连不上，删除成功写入失败，对话历史全丢。简化方案：saveAll() 里先把旧数据 range 出来备份，再删除写入，写入失败用备份恢复。"

**追问预判：**

- **Q："集群模式 Lua 脚本 key 不在同一 slot 怎么办？"** A：Hash Tag。Key 格式 `chat:memory:{conversationId}`，花括号内为 Hash Tag，Redis 保证同 tag 的 key 落同 slot。
- **Q："考虑过 Redis Stream 吗？"** A：考虑过。Stream 天然追加、支持 Consumer Group、每条消息有唯一 ID。但我们的场景是全量覆盖写，List 更简单。未来做多端同步时 Stream 更合适。

### 2.5 设计模式：策略模式（RedisChatMemoryRepository）

**哪里用了：** `ChatMemoryRepository` 接口 + `RedisChatMemoryRepository` 实现类

**类结构：**

```
MessageWindowChatMemory（持有 ChatMemoryRepository）
  └── ChatMemoryRepository（策略接口）
        ├── InMemoryChatMemoryRepository（框架内置）
        ├── JdbcChatMemoryRepository（框架内置）
        └── RedisChatMemoryRepository（我们自研）
```

**原理：**

> 策略模式的核心是"面向接口编程"。`MessageWindowChatMemory` 只关心 `saveAll()` / `findByConversationId()` 的行为，不关心数据存在 Redis 还是 JDBC 还是内存。切换存储只需替换实现类，上层代码（Advisor、Controller）零改动。

**好处：**

1. **开闭原则**：新增存储方式（如 MongoDB）只需新增一个实现类，不修改 MessageWindowChatMemory
2. **可测试性**：单元测试可以用 InMemoryRepository，不依赖 Redis
3. **可替换性**：等 Spring AI Alibaba 升级兼容后，直接换实现类即可

**面试怎么说：**

> "Spring AI 的 `ChatMemoryRepository` 本身就是策略模式的体现。框架提供了 InMemory/JDBC/Cassandra/Neo4j 四种内置实现，但没有 Redis。我只需要实现这个接口的 4 个方法，就能把存储从内存换成 Redis。上层 Advisor 和 Controller 完全不感知变化——这就是策略模式的价值：**算法可替换，使用者不感知**。"

**追问预判：**

- **Q："策略模式和简单工厂怎么选？"** A：策略模式强调"运行时替换同一个行为的不同实现"，工厂模式强调"创建对象的逻辑封装"。我们的场景是运行时注入不同 Repository，所以是策略模式。如果将来需要根据配置动态选择存储方式，可以加一个简单工厂来创建对应的 Repository 实例。

## 三、SummarizingChatMemory（摘要压缩）

### 3.1 面试官问："长对话怎么处理？消息太多怎么办？"

**3 分钟版回答：**

> **痛点：** `MessageWindowChatMemory` 只做滑动窗口裁剪——超过 20 条就扔掉旧消息。用户聊了半小时后 AI "忘了"之前说的，体验很差。
>
> **怎么做：** 装饰器模式，三层结构：
> - `SummarizingChatMemory`（装饰器层） → 负责触发压缩
> - `MessageWindowChatMemory`（窗口管理层） → 负责消息条数限制
> - `RedisChatMemoryRepository`（存储层） → 负责 Redis 读写
>
> 当消息数超过 20 条时，把前半段消息发给**纯净 ChatClient**（无工具绑定），用 LLM 压缩成一条 100 字以内的 SystemMessage 摘要，然后重建消息列表：摘要（1条） + 最近 10 条原始消息。
>
> **为什么不选其他方案：**
> - 不压缩（无限窗口）：Token 成本线性增长，很快吃满上下文窗口
> - 简单滑动窗口：丢信息，AI 前后矛盾
> - 异步压缩：有竞态条件，LLM 可能在摘要生成完之前读到旧数据
>
> **还可以怎样：** 压缩后做**增量摘要**（不每次全部重新压缩，而是在上次摘要基础上追加新信息），降低 LLM 调用成本。

**实际案例：**

> "最开始用简单滑动窗口 maxMessages=20，用户反映'聊久了 AI 就忘了前面说的'。比如用户先问了订单号 A 的问题，聊了 20 多轮之后再说'刚才那个订单呢'，AI 已经不知道是哪个订单了。后来加了摘要压缩，超过 20 条时把前 10 条喂给 LLM 生成摘要。同步执行，用户要等额外 2~3 秒，但数据一致性有保障。"

**追问预判：**

- **Q："为什么压缩要用纯净 ChatClient？"** A："带 Tool Calling 的 Client 会优先调工具而不是生成文本。这是 OpenAI 协议 tools > system > user 的优先级规则。"
- **Q："摘要质量怎么保证？"** A："压缩 prompt 明确约束保留订单号、商品名、关键状态。后续可以加'摘要校验'步骤——压缩后问 LLM '是否遗漏关键信息'，但会增加一次调用成本。"
- **Q："Token 成本影响？"** A："正面。50 轮原始消息约 5000 token → 压缩后 1 条摘要(200) + 10 条(1000) = 1200 token，节省 76%。代价是每次压缩一次额外 LLM 调用(~2200 token)。"
- **Q："用户刷新页面后摘要还在吗？"** A："在。摘要也是 SystemMessage，存在 Redis 里，conversationId 不变就能恢复。"

### 3.2 设计模式：装饰器模式（SummarizingChatMemory）

**哪里用了：** `SummarizingChatMemory` 装饰 `MessageWindowChatMemory`

**类结构：**

```
ChatMemory（接口）
  ├── MessageWindowChatMemory（被装饰者，持有 RedisChatMemoryRepository）
  └── SummarizingChatMemory（装饰器，持有 MessageWindowChatMemory 作为 delegate）
```

**原理：**

> 装饰器模式的核心：**在不修改被装饰对象的前提下，动态扩展它的行为**。`SummarizingChatMemory` 也实现了 `ChatMemory` 接口，内部持有一个 `delegate`（被装饰的 `MessageWindowChatMemory`）。
>
> `get()` 方法被重写：先调底层 `delegate.get()` 拿到消息列表 → 检查是否需要压缩 → 需要就调 LLM 生成摘要 → 返回压缩后的列表。对上层调用者（Advisor）来说，完全感知不到装饰层的存在。
>
> `add()` 方法也被重写：先调 `delegate.add()` 写入 → 再检查是否需要压缩 → 需要就触发。

**好处：**

1. **开闭原则**：不修改 `MessageWindowChatMemory` 的任何代码，就给它加了摘要压缩能力
2. **可组合**：可以叠加多个装饰器（比如再加一个"敏感词过滤"装饰器）
3. **可插拔**：去掉摘要压缩？不注册 `SummarizingChatMemory` Bean，直接用 `MessageWindowChatMemory` 即可

**和继承的区别：**

> 如果用继承，`SummarizingMemory extends MessageWindowChatMemory`，耦合太紧——必须继承具体实现类，不能换底层存储。装饰器组合的是接口，灵活得多。

**面试怎么说：**

> "我用装饰器模式实现了摘要压缩。`SummarizingChatMemory` 也实现了 `ChatMemory` 接口，内部持有一个 `delegate`。 Advisor 只知道自己拿到的类型是 `ChatMemory`，不知道底下有几层装饰。这种'透明增强'是装饰器模式的核心价值——**扩展功能但不改接口契约**。Spring 框架里大量使用了装饰器模式，比如 `HttpServletRequestWrapper` 就是对 `HttpServletRequest` 的装饰。"

**追问预判：**

- **Q："为什么不用 AOP 做压缩？"** A："AOP 适合横切关注点（日志、事务），不适合这种需要修改返回值的场景——装饰器可以完全替换 `get()` 的返回值（原始列表 → 压缩后列表），AOP 的 Around Advice 虽然也能做到，但语义不如装饰器清晰，而且 AOP 要处理返回值类型的匹配问题。"
- **Q："装饰器会不会影响性能？"** A："只有在消息数超过阈值时才触发压缩（一次额外 LLM 调用约 2~3 秒），正常对话没有额外开销。而且我加了 `MAX_MESSAGES` 检查，不超阈值直接透传 delegate，不走装饰逻辑。"

## 四、设计模式汇总（跨模块概述）

> 面试官问："你的项目里用了哪些设计模式？为什么用它们？"

### 策略模式（Strategy Pattern）

**定义：** 定义一系列算法，把它们封装起来，并且使它们可以相互替换。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | `ChatMemoryRepository` 接口 → `RedisChatMemoryRepository` 实现 |
| **意图** | 存储方式可替换（InMemory/JDBC/Redis），上层 Advisor 不感知 |
| **结构** | Context(MessageWindowChatMemory) → Strategy(ChatMemoryRepository) → ConcreteStrategy(RedisChatMemoryRepository) |
| **好处** | 开闭原则（加存储方式只加实现类）、可测试（单测用 InMemory）、可替换（框架内置实现可随时切换） |
| **类比 Java 后端** | `PlatformTransactionManager` → `DataSourceTransactionManager` / `JpaTransactionManager` |

### 装饰器模式（Decorator Pattern）

**定义：** 动态地给一个对象添加一些额外的职责，不修改对象本身。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | `SummarizingChatMemory` 装饰 `MessageWindowChatMemory` |
| **意图** | 不改底层存储代码，给 ChatMemory 加摘要压缩能力 |
| **结构** | Component(ChatMemory) → ConcreteComponent(MessageWindowChatMemory) → Decorator(SummarizingChatMemory) |
| **好处** | 可组合（叠加多个装饰器）、可插拔（去掉装饰只保留底层）、透明增强（上层无感知） |
| **类比 Java 后端** | `InputStream` → `BufferedInputStream` → `GZIPInputStream`；Spring `BeanWrapper` |

### 责任链模式（Chain of Responsibility）

**定义：** 将请求沿着处理者链传递，每个处理者决定处理或传递给下一个。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | Advisor 链：`MessageChatMemoryAdvisor` → `CustomRagAdvisor` → ChatModel |
| **意图** | LLM 调用前后插入多个处理逻辑（记忆加载 → RAG 检索 → LLM 调用 → Token 日志） |
| **结构** | Handler(BaseAdvisor) → ConcreteHandler(MemoryAdvisor / RagAdvisor)，通过 `order` 控制顺序 |
| **好处** | 解耦（每个 Advisor 独立）、灵活（增删 Advisor 不改其他代码）、有序（order 控制执行顺序） |
| **类比 Java 后端** | Servlet Filter 链、Spring Interceptor 链 |

### 建造者模式（Builder Pattern）

**定义：** 将复杂对象的构建与表示分离，使得同样的构建过程可以创建不同的表示。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | `ChatClient.Builder`、`MessageWindowChatMemory.builder()`、`SearchRequest.builder()` |
| **意图** | 配置项多（system prompt + tools + advisors + memory），Builder 提供流式 API |
| **注意点** | `ChatClient.Builder` 是可变 Builder（.defaultTools() 修改自身 return this），不是 Effective Java 推荐的不可变 Builder |
| **类比 Java 后端** | `StringBuilder`、`Lombok @Builder` |

### 观察者模式（Observer Pattern）

**定义：** 定义对象间一对多的依赖，当一个对象状态改变时，所有依赖它的对象都会被通知。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | WebFlux SSE（`Flux<String>` 流式推送）、Spring 事件机制 |
| **意图** | LLM 生成 token 后实时推送给前端（EventSource.onmessage），前端逐字渲染打字机效果 |
| **结构** | Subject(Flux publisher) → Observer(EventSource subscriber)，WebFlux 自动处理背压和线程切换 |
| **好处** | 响应式、实时性、前端无需轮询 |
| **类比 Java 后端** | `ApplicationEventPublisher` / `@EventListener`、MQ 的 Pub/Sub |

### 工厂方法模式（Factory Method）

**定义：** 定义创建对象的接口，让子类决定实例化哪个类。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | `ChatClient.builder(chatModel)` 工厂方法创建全新 Builder |
| **意图** | 每次调用返回全新 Builder（不受之前配置影响），解决双 Client 隔离问题 |
| **关键踩坑** | `ChatClient.builder(chatModel)` 是**工厂方法**（每次新对象），而 builder 自身的 `.defaultTools()` 是**可变 Builder**（修改自身）。两者是不同层次的 Builder 模式 |
| **类比 Java 后端** | `Calendar.getInstance()`、`Collections.unmodifiableList()` |

### 模板方法模式（Template Method）

**定义：** 定义算法的骨架，将某些步骤延迟到子类。

| 维度 | 说明 |
|------|------|
| **项目中用在哪** | `BaseAdvisor` 接口（before/after 方法骨架）→ `CustomRagAdvisor` / `MessageChatMemoryAdvisor` 具体实现 |
| **意图** | Spring AI 框架定义了 Advisor 的执行骨架（adviseCall → before → chain.nextCall → after），自定义 Advisor 只需实现 before/after |
| **好处** | 框架控制执行流程（比如 order 排序、异常处理），开发者只关注业务逻辑 |
| **类比 Java 后端** | `JdbcTemplate`（定义 SQL 执行流程，子类实现 RowMapper） |

### 面试总结话术

> "项目里主要用了 7 个设计模式。最核心的是**策略模式**（ChatMemoryRepository 多存储实现切换）和**装饰器模式**（SummarizingChatMemory 给 ChatMemory 加摘要能力）。**责任链模式**体现在 Advisor 链的执行机制上（类似 Servlet Filter 链）。
> 这些模式不是刻意用的，而是 Spring AI 框架本身的设计就采用了这些模式，我在理解框架原理的基础上自然用到了。比如 `ChatMemoryRepository` 就是框架定义的策略接口，我只是加了一个 Redis 实现。
> 如果说'以后可以落地的'，**策略模式**可以进一步用在工具路由上——不同意图调用不同的工具集（查询类工具 vs 操作类工具），通过策略模式切换工具集，比一个大类里塞所有 @Tool 方法更清晰。"
