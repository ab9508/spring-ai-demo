## Day 1：Java基础 + Spring框架

### 上午（2.5h）：Java核心高频题

#### 1. HashMap（必考TOP1，准备5分钟口述）

**必须能说的点：**
```
【结构】JDK8 = 数组 + 链表 + 红黑树，默认初始容量16，负载因子0.75
【扩容】size > capacity × 0.75 → 2倍扩容，rehash
【链表→红黑树】链表长度≥8 且 数组长度≥64 → 转红黑树；≤6 → 退回链表
【哈希扰动】hash = h ^ (h >>> 16)，高16位参与运算减少碰撞
【线程安全】HashMap非线程安全 → ConcurrentHashMap / Collections.synchronizedMap
【ConcurrentHashMap】JDK8 = CAS + synchronized分段锁（锁头节点），JDK7 = Segment分段锁
```

**结合AI项目的回答加分：**
> "我在Spring AI项目的RAG模块中，知识库元数据管理用HashMap缓存documentId到向量记录的映射，ConcurrentHashMap做多线程文档入库的计数器。"

#### 2. 线程池（必考TOP2，准备5分钟口述）

**必须能说的点：**
```
【7参数】corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler
【执行流程】核心线程满 → 入队列 → 非核心线程满 → 拒绝策略
【4种拒绝策略】AbortPolicy(抛异常) / CallerRunsPolicy(调用线程执行) / DiscardPolicy(丢弃) / DiscardOldestPolicy(丢队首)
【队列选择】
  - LinkedBlockingQueue：无界（慎用，可能OOM）或固定大小
  - ArrayBlockingQueue：有界，固定大小
  - SynchronousQueue：不存储，直接交给线程
```

**结合AI项目：**
> "AI对话接口的请求处理用线程池，核心线程数=CPU核数，队列用ArrayBlockingQueue(200)，拒绝策略CallerRunsPolicy——保证请求不丢，只是变慢。LLM调用本身就是慢操作，线程池防止把服务器拖垮。"

#### 3. JVM内存模型 + GC（准备3分钟口述）

```
【堆分区】新生代(Eden + S0 + S1 = 8:1:1) + 老年代（默认比例 新:老 = 1:2）
【GC算法】Minor GC(新生代，复制算法) / Major GC(老年代，标记-清除/整理)
【常见收集器】G1(默认JDK9+) / ZGC(JDK15+，亚毫秒停顿)
【OOM排查】jmap -heap → jmap -dump → MAT分析 / Arthas在线诊断
【类加载】双亲委派：Bootstrap → Extension → Application
```

**一句话回答策略：**
> "线上用G1收集器，JVM参数-Xms和-Xmx设一样避免运行时扩容。遇到过一次Full GC频繁，用jstat和Arthas排查发现大对象直接进老年代，调整大对象阈值后解决。"

#### 4. 其他高频题（每题30秒速记答案）

| 题 | 30秒答案 |
|---|---------|
| ArrayList vs LinkedList | ArrayList底层Object[]，随机访问O(1)，扩容1.5倍；LinkedList双向链表，插入删除O(1)，随机访问O(n)。实际场景ArrayList + 批量插入更好（CPU缓存友好） |
| synchronized vs ReentrantLock | sync是JVM层面，自动释放；Lock是API层面，可公平/可中断/可超时。Lock更灵活但需手动unlock，推荐finally中释放 |
| volatile | 保证可见性（强制读主内存）+ 禁止指令重排。不保证原子性（i++还是线程不安全）。DCL单例中volatile防止对象初始化重排 |
| CAS | Compare-And-Swap，乐观锁底层。ABA问题用版本号解决。LongAdder比AtomicLong性能好（分段CAS） |
| ThreadLocal | 线程本地变量，内存泄漏风险（ThreadLocalMap的key是弱引用但value是强引用），用完后必须remove() |

### 下午（2.5h）：Spring框架深度

#### 1. Spring IOC原理（准备3分钟口述）

```
【核心】BeanFactory（基础容器） vs ApplicationContext（高级容器，加了事件/国际化/AOP）
【Bean生命周期】
  实例化（反射创建） → 属性注入（@Autowired/@Value） → 
  Aware回调（BeanNameAware等） → BeanPostProcessor.postProcessBeforeInitialization →
  @PostConstruct → InitializingBean.afterPropertiesSet → 自定义init-method →
  BeanPostProcessor.postProcessAfterInitialization → 就绪使用 → 
  @PreDestroy → DisposableBean.destroy → 销毁
【循环依赖】三级缓存解决：
  singletonObjects（一级，完整Bean） → earlySingletonObjects（二级，早期引用） → 
  singletonFactories（三级，ObjectFactory，AOP在这里提前创建代理）
  构造器注入无法解决！只能用@Lazy
【自动注入】@Autowired（byType） vs @Resource（byName） → Spring Boot推荐构造器注入
```

**一句话回答：**
> "Spring IOC本质是Map<String, BeanDefinition> + 反射创建实例 + 三级缓存解决循环依赖。构造器注入的循环依赖无解，只能@Lazy。"

#### 2. Spring AOP原理（准备2分钟口述）

```
【实现】JDK动态代理（接口） vs CGLIB（继承，Spring Boot 2.x默认）
【核心概念】切面(Aspect) / 切点(Pointcut) / 通知(Advice) / 连接点(JoinPoint)
【5种通知】Before / After / AfterReturning / AfterThrowing / Around
【执行顺序】环绕通知 → 前置通知 → 方法执行 → 后置通知/异常通知/返回通知
```

**结合AI项目加分：**
> "Spring AI的Advisor链本质上就是AOP思想——MessageChatMemoryAdvisor在LLM调用前加载历史消息，CustomRagAdvisor在调用前做向量检索，通过order控制执行顺序。理解AOP就理解了Advisor的设计模式。"

#### 3. Spring Boot自动配置（准备2分钟口述）

```
【核心注解】@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
【自动配置原理】
  @EnableAutoConfiguration → Import(AutoConfigurationImportSelector) → 
  加载META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（2.7+）
  或 META-INF/spring.factories（2.7以下）
  → @Conditional系列条件注解判断是否加载
【常用条件注解】@ConditionalOnClass / @ConditionalOnMissingBean / @ConditionalOnProperty
```

**结合项目：**
> "我的双模型配置就用@ConditionalOnProperty，通过app.chat.provider属性决定注入OllamaChatModel还是OpenAiChatModel。exclude OpenAiEmbeddingAutoConfiguration避免Embedding冲突。这就是Spring Boot自动配置的条件装配机制。"

#### 4. Spring Cloud核心组件（准备2分钟口述）

| 组件 | 作用 | 我的项目经验 |
|------|------|-------------|
| Nacos/Eureka | 服务注册发现 | Nacos做注册中心+配置中心，金融催收系统生产使用 |
| Feign/OpenFeign | 声明式HTTP客户端 | 微服务间RPC调用，替代RestTemplate |
| Gateway | API网关 | 路由转发+限流+鉴权 |
| Sentinel | 限流熔断 | 金融系统核心接口保护 |
| Seata | 分布式事务 | 电商订单跨库事务 |

**一句话总结：**
> "电商B2B2C项目用Spring Cloud Alibaba全家桶，Nacos注册+配置、OpenFeign RPC、Gateway网关、Sentinel限流。金融催收系统也用Nacos做服务治理。"

## Day 2：中间件(Redis/MQ/锁) + 架构设计

### 上午（2.5h）：Redis深度

#### 1. Redis数据结构（必考，准备3分钟口述）

```
【5种基础】
  String：最常用，底层SDS（Simple Dynamic String），二进制安全
  List：快速列表(quicklist) = 双向链表 + 压缩列表
  Hash：哈希表，适合存对象字段
  Set：哈希表，去重+交集/并集
  ZSet：跳表(skiplist) + 哈希表，排行榜/延迟队列

【3种高级】
  HyperLogLog：基数统计（UV），12KB固定内存
  Bitmap：位操作，签到/在线状态
  Stream：消息队列，消费组，ACK机制
```

**结合AI项目（强烈建议说）：**
> "我的Spring AI项目中Redis有3个用途：
> 1. ChatMemory存储——Redis List，RPUSH追加对话，LRANGE读取最近N条
> 2. 会话TTL——每个会话Key设24h过期，自动清理不活跃会话
> 3. 分布式锁——Redisson实现，防止并发请求重复创建对话上下文
> 选Redis List而不是Hash的原因：追加(O(1))和读取最近N条(O(N))刚好匹配对话场景，且RPUSH+LTRIM天然实现滑动窗口。"

#### 2. Redis缓存问题（必考，准备3分钟口述）

```
【缓存穿透】查不存在的数据 → 缓存+DB都没有
  解决：布隆过滤器 / 缓存空值(null) + 短TTL
  
【缓存击穿】热点Key过期 → 大量请求打到DB
  解决：互斥锁(setnx) / 永不过期(逻辑过期，异步更新)
  
【缓存雪崩】大量Key同时过期 → DB压力暴增
  解决：TTL加随机值 / 多级缓存(本地+Redis) / 永不过期
  
【缓存一致性】先更新DB还是先删缓存？
  方案1：Cache Aside Pattern — 先更新DB，再删缓存（推荐）
  方案2：延迟双删 — 更新DB前删一次，更新后延迟几百毫秒再删一次
  方案3：订阅Binlog — Canal监听MySQL变更，异步更新缓存
```

**结合AI项目：**
> "RAG知识库的元数据用Redis缓存，文档ID到分块信息的映射。采用Cache Aside模式——文档入库时先写PgVector再删缓存，查询时缓存miss才查库。TTL设1小时，知识库更新后通过应用层主动删缓存保证一致性。"

#### 3. Redis持久化 + 高可用（准备2分钟口述）

```
【RDB】快照，fork子进程写磁盘。恢复快但可能丢数据（最后一次快照之后的）
【AOF】追加日志，每秒fsync。数据安全但文件大，恢复慢
【混合持久化】RDB + AOF增量（Redis 4.0+，推荐）
【主从】读写分离，主写从读，异步同步
【哨兵】自动故障转移，监控主节点，选举新主
【集群】数据分片(16384槽)，水平扩展，每个节点负责部分槽
```

### 下午（2h）：MQ + 分布式锁

#### 1. RocketMQ vs RabbitMQ（必考对比，准备3分钟口述）

| 维度 | RocketMQ | RabbitMQ |
|------|----------|----------|
| 语言 | Java | Erlang |
| 吞吐量 | 10万级/秒 | 万级/秒 |
| 延迟 | ms级 | μs级 |
| 消息可靠性 | 同步刷盘+主从 | 持久化+镜像队列 |
| 事务消息 | 支持 | 不支持（Confirm模式） |
| 延迟消息 | 原生支持18个延迟级别 | 插件/死信队列 |
| 适用场景 | 金融/电商/大数据 | 中小项目/低延迟 |

**结合项目经验（背下来）：**
> "电商B2B2C项目用RocketMQ，金融催收系统用RabbitMQ。
>
> 电商场景：
> - 订单创建 → 发消息 → 库存扣减、物流通知异步处理
> - 延迟消息实现超时未支付自动取消（30分钟延迟级别）
> - 事务消息保证订单创建和消息发送的一致性
>
> 金融催收场景：
> - 催收任务分配 → RabbitMQ Fanout广播给多个催收员
> - 死信队列处理催收失败的case
> - 消息确认机制（ACK）保证不漏催

> 如果让我选：金融场景选RocketMQ（事务消息+高可靠），轻量异步选RabbitMQ。"

#### 2. 消息可靠性三要素（必考，准备2分钟口述）

```
【生产端不丢】
  - 发送确认：RocketMQ用sendMessageInTransaction / RabbitMQ用publisher confirms
  - 本地消息表：先写DB+MQ消息状态，定时补偿未发送的

【MQ不丢】
  - 同步刷盘（flushDiskType=SYNC_FLUSH）
  - 同步复制到从节点（flushDiskType=SYNC_MASTER）

【消费端不丢】
  - 手动ACK（关闭自动确认）
  - 幂等消费：唯一ID + Redis/DB去重
  - 重试机制：RocketMQ默认16次重试，指数退避
```

#### 3. 分布式锁（必考，准备3分钟口述）

```
【Redis实现（Redisson）】
  - 加锁：SET key value NX PX 30000（原子操作）
  - 看门狗（Watchdog）：默认30s过期，每10s续期（防止业务没执行完锁就过期）
  - 可重入：Hash结构，field=线程ID，value=重入次数
  - 红锁（RedLock）：多节点，解决单点故障

【对比】
  - Redis：性能高，AP倾向，锁过期自动释放
  - ZooKeeper：CP倾向，临时顺序节点+Watch，可靠性高但性能低
  - MySQL：SELECT FOR UPDATE，简单但性能差

【使用场景】
  - 防止重复下单（用户维度锁）
  - 定时任务防并发（分布式环境下只允许一个节点执行）
  - 库存扣减（商品维度锁）
```

**结合AI项目：**
> "Spring AI项目中用Redisson做分布式锁，场景：用户发起对话时加锁(userId + ':chat')，防止快速双击创建两个对话上下文。锁超时60s（远超LLM一次调用的30s），看门狗自动续期。"

**1. RAG全链路**
```
文档入库：上传 → Tika/PDF解析 → OverlappingTextSplitter分块 → nomic-embed-text向量化 → PgVector存储
检索链路：用户提问 → embedding → PgVector Top-K → 相对分数过滤 → 注入prompt → LLM生成
```
追问：为什么不用固定阈值？→ 分数飘0.35~0.62，域外问题表现不可预测
追问：overlap 10%？→ 防边界语义断裂
追问：相对分数过滤逻辑？→ Top1<0.45拦截（整体不相关），Top1-Top2<0.08拦截（没有明显最佳匹配）

**2. Redis ChatMemory**
```
1. 自研原因：1.0.x不支持Redis，Spring AI Alibaba版本冲突
2. 数据结构：Redis List，RPUSH追加，LRANGE读取
3. 防膨胀：maxMessages=20 + TTL 24h + LTRIM裁剪
4. 序列化：@JsonTypeInfo保留Message子类型信息
```

**3. Tool Calling + MCP**
```
【踩坑1】ChatClient.Builder是可变对象！defaultTools()修改自身
  → ChatClient.builder(model)工厂方法每次创建全新Builder

【踩坑2】有Tomcat必须用webmvc版Starter
  → webflux版SSE路由在Tomcat下不注册→404
  → Client url只填根地址，不加/sse

【Tool Calling vs MCP】
  Tool Calling = 同进程直接调（LLM→Java方法）
  MCP = 跨进程JSON-RPC（LLM→Client→SSE→Server→Java方法）
  MCP适合工具服务独立部署、多语言共享
```

**4. 双模型配置**
```
ConditionalOnProperty切换ChatModel
Embedding固定nomic-embed-text（维度不一致，不能随ChatModel切换）
exclude OpenAiEmbeddingAutoConfiguration避免冲突
```

**5. 结构化输出踩坑**
```
1.0.5没有entity(Class) API → prompt要求返回JSON + Jackson反序列化
关键踩坑：挂载了Tool Calling时，DeepSeek优先调工具而非返回JSON
解决：纯净jsonOnlyClient，不挂任何工具/Advisor
```

**6. 框架对比**
```
LangChain = Python通用（Chain/Agent/Memory/Retriever）
LlamaIndex = 专精RAG（Index/QueryEngine/Node）
Spring AI = Java生态原生（ChatClient/Advisor/Tool/VectorStore）
Dify = 低代码可视化（拖拽编排/内置RAG/Docker一键部署）

话术："LangChain核心概念和Spring AI一一对应，只是API写法不同。
Spring AI优势：原生Java生态，事务/监控/配置中心直接复用。"
```
