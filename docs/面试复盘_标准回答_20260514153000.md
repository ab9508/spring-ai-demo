## Q1. 为什么选 PgVector？相对分数过滤怎么解决固定阈值不稳定？

**结论先行（10秒）：**
> 选 PgVector 主要是生产可维护性考量；相对分数过滤是把"绝对打分"改成"比较排名差距"，从根源上规避了不同问题下分数基线漂移的问题。

**展开（90秒）：**

关于 PgVector 选型，我主要考虑了三点：

第一，**运维成本**。我的项目面向中小企业场景，PgVector 是 PostgreSQL 的扩展，DBA 团队本来就维护 PG，不需要引入新的存储中间件，Milvus 虽然性能更强，但需要额外部署 etcd + MinIO，运维链路更重。

第二，**事务一致性**。业务数据和向量数据可以在同一个 PG 实例里做事务关联，比如文档入库和向量写入可以在一个事务里完成，用 Milvus 就必须自己做两阶段补偿。

第三，**Spring AI 原生支持**。Spring AI 提供了 `PgVectorStore` 的开箱即用 Starter，集成成本极低。

---

关于相对分数过滤，背景是这样的：我用的是 `nomic-embed-text` 本地向量模型，发现它对领域外问题给出的相似度分数非常飘，同样是"不相关的问题"，有时候打 0.35，有时候打 0.62。如果设固定阈值，比如 0.5，就会出现一会儿拦住、一会儿放过的情况，导致 RAG 检索结果不可信。

所以我改成了**相对分数过滤策略**，逻辑如下：

- **条件一**：Top1 相似度分数 < 0.45，说明最佳匹配本身就很弱，直接拦截不进 RAG 上下文。
- **条件二**：Top1 - Top2 的分数差 < 0.08，说明最佳匹配和第二名几乎一样，LLM 没有清晰的信号，这种情况容易"张冠李戴"，也拦截。

这样做的本质是：**不再依赖绝对分数的校准，而是用排名结构来判断检索质量**，对向量模型的域外表现更鲁棒。实际效果是显著减少了"答非所问"的幻觉输出。

**收尾：** 这个方案不是看文档来的，是我观察到检索结果异常后，自己分析日志打出分数分布，才摸索出来的。

## Q2. 多维度检索是怎么实现的？遇到了哪些技术挑战？

**结论先行（10秒）：**
> 我实现的是"向量检索 + 关键词过滤"两阶段检索，核心挑战是 overlap 文本切片和阈值策略，解决了语义断裂和召回率不稳定两个问题。

**展开（90秒）：**

我的检索链路分两层：

**第一层：向量语义检索**
用 `PgVectorStore` 做 Top-K 余弦相似度检索，返回候选文档块。Embedding 用本地 `nomic-embed-text` 模型，避免调用外部 API 带来的延迟和费用。

**第二层：相对分数过滤**（即 Q1 描述的策略）
对候选结果按质量排名做二次过滤，过滤掉低质量或模糊的候选块，只保留信噪比高的上下文注入给 LLM。

**文本切片策略**是另一个关键点。我用了自定义的 `OverlappingTextSplitter`，设置了 10% 的 overlap（500 token chunk，50 token 重叠）。原因是如果不加 overlap，一个完整的语义单元可能被切割在两个 chunk 的边界，向量检索时两个 chunk 都检索到，但各自只有半段内容，拼起来逻辑断裂，LLM 生成的答案就会出现上下文矛盾。

**主要挑战有两个：**

1. **阈值不稳定问题**：已用相对分数过滤解决，上题讲过。

2. **Advisor 执行顺序问题**：我用了自定义的 `CustomRagAdvisor`，它需要在 ChatMemory 加载历史消息之后再执行，这样 RAG 检索时才能看到完整的对话上下文。Spring AI 里 Advisor 的执行顺序由 `order` 值控制，我把 `MessageChatMemoryAdvisor` 的 order 设为 `Integer.MIN_VALUE + 1000`（先执行），`CustomRagAdvisor` 的 order 设为 0（后执行）。这个顺序如果搞反，检索质量会明显下降。

**收尾：** 整个检索链路是"切片质量 → 向量召回 → 分数过滤 → 上下文注入"四步串联，每一步都影响最终答案质量。

## Q3. Redis ChatMemory 设计思路是什么？遇到了哪些性能挑战？

**结论先行（10秒）：**
> 核心设计是用 Redis List 存储消息序列，实现了 Spring AI 的 `ChatMemoryRepository` 接口，主要挑战是 JSON 序列化兼容性和消息窗口控制。

**展开（90秒）：**

**为什么要自研？**
Spring AI 1.0.x 原生只支持 InMemory、JDBC、Cassandra、Neo4j 四种存储，不支持 Redis。而 InMemory 在服务重启后会话记忆全部丢失，不适合生产环境。Spring AI Alibaba 的 Redis ChatMemory 方案又要求 Spring Boot 3.5.x，和我的 3.4.5 版本冲突，所以只能自己实现。

**数据结构选择：**
用 Redis List（`RPUSH` 追加，`LRANGE` 全量读取）存储每个 conversationId 对应的消息列表。Key 格式是 `chat:memory:{conversationId}`，Value 是 JSON 序列化后的消息对象。

**接口实现：**
实现了 `ChatMemoryRepository` 的三个方法：
- `save(conversationId, messages)`：RPUSH 追加
- `findByConversationId(conversationId)`：LRANGE 0 -1 读全部，反序列化回 Message 列表
- `deleteByConversationId(conversationId)`：DEL 删除整个 Key

然后通过 `MessageWindowChatMemory.builder().chatMemoryRepository(repository).maxMessages(20).build()` 接入，控制窗口大小为最近 20 条消息。

**主要挑战：**

1. **JSON 序列化兼容性**：Spring AI 的 `Message` 是接口，子类有 `UserMessage`、`AssistantMessage`、`SystemMessage` 等，Jackson 反序列化时不知道目标类型。我用了带类型信息的序列化方案（`@JsonTypeInfo`），在 JSON 里记录完整类名，反序列化时自动还原子类型。

2. **消息膨胀问题**：如果不控制窗口，长对话会导致 Redis 里的 List 无限增长，每次请求都要发送大量 Token 给 LLM，既慢又贵。用 `MessageWindowChatMemory` 的 maxMessages=20 做了截断，只保留最近的消息。

**收尾：** 这个组件实现后，自定义 Bean 会自动覆盖 Spring AI 的 InMemory 自动配置，Controller 层不需要任何改动，接入成本为零。

## Q4. 多轮对话记忆持久化是怎么设计的？遇到了哪些性能挑战？

> 这题和 Q3 高度重叠，建议回答时侧重"设计决策"而不是重复实现细节。

**结论先行：**
> 持久化设计的核心决策是"以 conversationId 为分区键、List 为时序结构、消息窗口截断为容量控制"，三者组合解决了持久化、隔离性、膨胀三个问题。

**展开（90秒）：**

**设计三要素：**

| 要素 | 决策 | 原因 |
|------|------|------|
| 分区键 | conversationId（通常=userId+sessionId） | 每个会话独立存储，互不干扰 |
| 数据结构 | Redis List（有序，支持追加和范围读取） | 对话天然是时序的，List 语义最匹配 |
| 容量控制 | maxMessages=20 滑动窗口 | 防止 Token 爆炸，同时保留足够上下文 |

**持久化的边界：**
Redis 是内存数据库，重启会丢数据，这是一个明确的设计取舍。对于对话记忆场景，我认为可以接受：大多数用户的会话时效性在当天，Redis 配置 AOF 持久化后基本不会丢，即使丢了也只是需要重新建立上下文，不影响核心业务。如果要求更强的持久化保证，可以换成 JDBC 存储，代价是读写延迟更高。

**性能挑战：**

1. **每次请求都全量读取历史消息**：`LRANGE 0 -1` 在消息多的时候有 O(N) 的网络传输开销。解决方案是 maxMessages 限制，加上 Redis 本身的读写速度（毫秒级），实际影响可控。

2. **序列化反序列化开销**：每条消息都要 JSON 化，对话记忆一次请求可能要序列化/反序列化 20 条消息。我用的是 Jackson，速度够快，实测单次解析 20 条消息在 5ms 以内，可接受。

**收尾：** 这个设计的本质是"用 Redis 的读写性能换 InMemory 的持久化能力"，适合中低并发场景，如果并发量很大还需要考虑 Redis Cluster 分片。

## Q5. RedisChatMemory 过期策略是怎么设计的？怎么避免内存膨胀？

**结论先行：**
> 两层防线：消息窗口截断控制单条会话大小，Key TTL 控制总会话数量，合力防止内存无限膨胀。

**展开（90秒）：**

**第一层：消息窗口（单会话内容控制）**

通过 `MessageWindowChatMemory.maxMessages=20` 实现滑动窗口，每次写入新消息后，超出窗口的旧消息不再被读取（注意：我的实现是写入时不删除，读取时截取最新 N 条，这样历史数据还在，只是不发给 LLM）。

如果要更严格控制存储大小，可以在 save 时额外调用 `LTRIM` 裁剪 List，只保留最新 20 条。

**第二层：Key TTL（会话级别过期）**

在 save 方法里，每次写入消息后调用 `expire(key, 24h)` 刷新过期时间。这样：
- 活跃会话：每次对话都刷新 TTL，24小时内不过期
- 非活跃会话：24小时无交互后自动删除，释放内存

这个策略模拟了"会话超时"语义，和 Web Session 的处理方式一致，用户容易理解。

**为什么不用 LRU 淘汰？**

Redis 有 `maxmemory-policy allkeys-lru` 可以自动淘汰，但这是被动防御，内存真的满了才淘汰，可能会导致偶发性的写入失败。TTL 是主动清理，更可控。

**额外的 SummarizingChatMemory 方案：**

我还做了一个 `SummarizingChatMemory` 组件，思路是当历史消息超过阈值时，调用 LLM 把旧消息压缩成一段摘要，用这段摘要替换旧消息，既保留了语义信息，又大幅压缩了 Token 数量。这是 LLM 应用里比较标准的长对话压缩策略。

**收尾：** 滑动窗口 + TTL + 摘要压缩三者可以按需组合，轻量场景用前两个就够，对话上下文要求高的场景加上摘要压缩。

## Q6. 双模型配置与 Tool Calling Agent 集成，怎么协调两个模型输出和工具调用准确性？

**结论先行：**
> 双模型通过 `@ConditionalOnProperty` 条件注入实现切换，Tool Calling 准确性的核心是"把工具挂载和结构化输出严格隔离"，避免 LLM 在工具调用模式下忽略 prompt 指令。

**展开（90秒）：**

**双模型架构：**

我用一个配置项 `app.chat.provider`（值为 `ollama` 或 `openai`）控制注入哪个 ChatModel：
- `@ConditionalOnProperty(name="app.chat.provider", havingValue="ollama")` → 注入 `OllamaChatModel`（本地 deepseek-r1:8b）
- `@ConditionalOnProperty(name="app.chat.provider", havingValue="openai")` → 注入 `OpenAiChatModel`（DeepSeek API，OpenAI 兼容协议）

Embedding 模型始终用本地 `nomic-embed-text`，不随配置切换，因为向量一旦入库就固定了，切换 embedding 模型会导致向量空间不兼容。

**Tool Calling 准确性的关键踩坑：**

这里有一个非常重要的问题我踩过：**ChatClient.Builder 是可变对象**。如果在同一个 Builder 上先 `defaultTools(toolInstance)` 构建了一个带工具的 ChatClient，再从同一个 Builder 上 `build()` 想得到一个不带工具的"纯净" ChatClient，实际上第二个 build 出来的也是带工具的，因为 `defaultTools` 修改的是 Builder 自身状态。

后果是：结构化输出的请求体里含有 `tools` 字段，LLM 会进入工具调用模式，完全忽略"只返回 JSON"的 prompt 指令，导致结构化输出失败。

**解决方案：** 用 `ChatClient.builder(chatModel)` 工厂方法每次创建全新的 Builder，完全隔离：
- `agentChatClient`：挂载 `@Tool` 工具，用于 Agent 场景
- `jsonOnlyClient`：全新 Builder 构建，无任何工具，用于结构化输出场景

**工具调用准确性保障：**

1. `@Tool(description)` 描述要精确，让 LLM 能准确判断何时调用哪个工具
2. 工具参数设计要简单，减少 LLM 填参数出错的概率
3. 对工具返回结果做格式校验，防止 LLM 错误解析工具输出

**收尾：** 这个双模型 + 工具隔离的设计，是我在实际踩了"结构化输出失败"的坑之后才摸清楚的，核心是理解 ChatClient Builder 的可变性和 HTTP 请求体的差异。

## Q7. 金融级核心系统架构设计：怎么平衡高并发、一致性、可用性？

**结论先行：**
> CAP 理论下没有银弹，我的做法是"分级一致性"：核心交易用强一致性（分布式锁+数据库事务），边缘功能用最终一致性（MQ异步），结合限流熔断保可用性。

**展开（90秒）：**

**实际案例：贷后催收系统的还款记录模块**

并发场景：多个催收员同时操作同一个借款人的还款记录，可能出现双写冲突。

**高并发处理：**
- 数据库层：还款记录按借款人 ID 分库分表，减少热点
- 缓存层：查询类接口走 Redis 缓存，TTL 设 5 分钟，降低 DB 压力
- 接口层：Nginx 限流 + Sentinel 熔断，防止突发流量打穿

**一致性保障：**
- 还款记录写入：使用 `SELECT FOR UPDATE` 悲观锁，同一借款人的写操作串行化
- 账单状态变更：通过 RocketMQ 发送状态变更消息，消费端幂等处理（消息 ID 去重），保证最终一致
- 分布式场景：涉及跨服务调用用 Seata AT 模式做分布式事务（仅核心链路，不滥用）

**可用性保障：**
- 核心服务（还款记录）：3副本部署，Nacos 健康检查，故障节点自动摘除
- 非核心服务（短信通知、报表）：异步降级，主流程失败不影响
- 数据库：主从读写分离，写主库、读从库，主库故障时从库提升

**收尾：** 核心思路是"强一致性用在钱的地方，最终一致性用在非核心的地方"，可用性通过冗余和降级来保障。

## Q8. 全链路性能调优方法论，结合实际案例说说

**结论先行：**
> 调优的顺序是"先找瓶颈再动手"，工具链是 SkyWalking 全链路追踪 + 慢查询日志 + JVM 监控，绝不凭感觉优化。

**展开（90秒）：**

**方法论四步：**
1. **量化基线**：先压测，确认 TPS/RT/错误率的基准值
2. **定位瓶颈**：SkyWalking 找最慢的调用链路，Arthas 热点分析，DB 慢查询日志
3. **针对性优化**：SQL 加索引/Redis 缓存/异步化，哪里慢改哪里
4. **回归验证**：优化后再压测，对比数据，确认有效

**实际案例：电商订单列表接口优化**

问题：订单列表接口 P99 延迟 2.8 秒，用户反馈慢。

排查过程：
- SkyWalking 看到 80% 时间消耗在 DB 查询
- 慢查询日志发现：`WHERE user_id=? AND status=? ORDER BY create_time DESC` 没有联合索引
- EXPLAIN 发现全表扫描，数据量 500 万行

优化步骤：
1. 加联合索引 `(user_id, status, create_time DESC)`，查询时间从 800ms → 12ms
2. 加 Redis 缓存，订单列表缓存 2 分钟，命中率 85%，DB QPS 降低 6 倍
3. 订单详情接口拆出来单独调用（原来一次查所有字段），按需加载

**优化结果：** P99 从 2.8s 降到 180ms，QPS 从 200 提升到 1200。

**收尾：** 调优没有万能模板，但找瓶颈的工具链是固定的，量化驱动、数据说话是核心原则。

## Q9. 怎么推动技术规范建设、提升团队整体效能？举例说说（STAR法则）

**S（情境）：**
电商项目团队 6 人，代码风格不统一，CR 效率低，新人上手慢，每次版本发布都有因为代码格式/命名问题引发的 Bug。

**T（任务）：**
主导建立统一的代码规范和 CR 流程，目标是减少低级错误、缩短 CR 时间。

**A（行动）：**
1. 整理了一份《Java 编码规范》文档，基于阿里巴巴 Java 开发手册裁剪，覆盖命名、异常处理、日志规范、接口设计四个模块
2. 在 IDEA 里统一推了 Checkstyle 插件配置，提交前自动检查，不符合规范的代码直接卡本地
3. 在 GitLab CI 里加了 SonarQube 静态扫描，PR 合并前必须通过扫描
4. 每两周一次 Code Review 会，把典型问题截图出来，集体讨论，形成案例库
5. 新人入职时安排技术规范培训，第一周 CR 由老人 pair 做

**R（结果）：**
- Code Review 时间从平均 3 天缩短到 1 天
- 因代码问题引发的生产 Bug 减少约 60%
- 新人从入职到独立完成 PR 的时间从 3 周缩短到 1.5 周

**收尾：** 规范建设不是写文档，而是把规范嵌入到工具链和流程里，让遵守规范成为最省力的路径。

## Q10. 设计企业级智能客服系统（多轮对话+知识库检索+工单生成）

**结论先行：**
> 整体是"接入层 → 意图路由 → RAG检索 → LLM生成 → 工单输出"五层架构，核心挑战在检索质量和工单生成的准确性。

**整体架构：**

```
用户消息
   ↓
[接入层] Spring Boot Gateway - 鉴权、限流、会话管理
   ↓
[意图路由] LLM意图分类 - FAQ闲聊/知识库检索/工单创建/人工转接
   ↓
[记忆层] Redis ChatMemory - 多轮对话历史，conversationId隔离
   ↓
[RAG层] PgVector语义检索 → 相对分数过滤 → 上下文注入
   ↓
[生成层] DeepSeek API / 本地LLM → 生成回复 / 提取工单字段
   ↓
[工单层] 结构化输出 → 工单系统写入（Jira/自研）
```

**开源组件选型：**

| 组件 | 选型 | 理由 |
|------|------|------|
| AI框架 | Spring AI | Java生态，对接成本低 |
| 向量数据库 | PgVector | 中小规模，运维简单，事务一致 |
| 向量模型 | nomic-embed-text（Ollama本地） | 免费，无网络延迟 |
| LLM | DeepSeek API + Ollama备用 | 性价比高，支持工具调用 |
| 会话记忆 | Redis | 低延迟，TTL天然支持会话过期 |
| 文档处理 | Apache Tika + PagePdfDocumentReader | 多格式文档统一处理 |

**性能瓶颈及解决：**

| 瓶颈 | 解决方案 |
|------|---------|
| LLM 首 Token 延迟 3-5s | 流式输出（SSE），让用户感知到"正在回答" |
| 向量检索慢（数据量大） | PgVector 建 IVFFlat 索引（100万以内），或升级 HNSW |
| 知识库冷更新 | 文档变更后异步重新 Embedding，不影响在线服务 |
| 工单字段提取不准 | 专门用无工具的纯净 ChatClient + JSON Schema 提示词 |

**收尾：** 系统的核心价值是减少人工客服的重复工作量，关键指标是"自动解决率"，不是响应速度。

## Q11. 主流大模型框架了解？Spring AI 的优劣势？

**结论先行：**
> LangChain 是 Python 生态老大，灵活但过度封装；LlamaIndex 专精 RAG；Spring AI 是 Java 生态的标准化整合层，生产可维护性强但生态还不够成熟。

**框架对比：**

| 维度 | LangChain | LlamaIndex | Spring AI |
|------|-----------|------------|-----------|
| 语言 | Python/JS | Python | Java |
| 定位 | 通用AI应用链路 | 专精RAG/检索 | Java生态AI整合 |
| 生态成熟度 | 最成熟 | 中等 | 还在快速迭代 |
| 学习曲线 | 高（抽象层多） | 中 | 中（Spring背景易上手） |
| 生产维护性 | 一般（版本变化快） | 一般 | 好（Spring标准化） |

**Spring AI 优势：**
1. **Java 生态原生**：无缝集成 Spring Boot 全家桶（事务、监控、配置中心），不需要 Python 微服务
2. **标准化接口**：`ChatModel`、`VectorStore`、`ChatMemory` 等接口设计清晰，可插拔
3. **企业级生产能力**：天然继承 Spring 的健康检查、Actuator 监控、配置管理

**Spring AI 劣势：**
1. **版本迭代快、Breaking Change 多**：我用 1.0.5 版本时，`BeanOutputConverter`、`entity(Class)` 这些 API 在 1.1.0 才有，文档和实际代码经常对不上
2. **生态不如 Python 丰富**：LangChain 有几百个 integrations，Spring AI 还差很多
3. **社区资料少**：遇到问题很难搜到中文解决方案，大多要看 GitHub Issues 或源码

**收尾：** 如果团队是 Java 栈、在做企业级应用，Spring AI 是最合适的选择；如果做快速原型验证或研究，LangChain + Python 更灵活。

## Q12. 如何解决向量检索召回率与延迟之间的矛盾？

**结论先行：**
> 两者本质是 Top-K 数量和索引类型的权衡，我的策略是"先宽召回再严过滤"，用相对分数过滤做二次筛选，在不牺牲质量的前提下控制送入 LLM 的上下文量。

**展开（90秒）：**

**矛盾的根源：**
- 提高召回率 → 要加大 Top-K → 更多候选块 → 更长上下文 → LLM 处理延迟增加 + 费用上升
- 降低延迟 → 要减小 Top-K → 候选块少 → 可能漏掉关键信息 → 回答质量下降

**我的解决方案：**

1. **索引选型**：PgVector 支持 IVFFlat 和 HNSW 两种索引。
   - IVFFlat：构建快，适合数据量 < 100 万，查询延迟 10-50ms
   - HNSW：查询延迟更低（1-5ms），但构建慢、内存占用大，适合高并发场景
   - 我的场景数据量中等，用 IVFFlat 够用

2. **分阶段检索**：
   - 第一阶段：Top-K=5 宽召回（保证覆盖面）
   - 第二阶段：相对分数过滤，实际送进 LLM 的通常只剩 2-3 条高质量块
   - 效果：上下文 Token 数减少约 40%，LLM 生成速度提升，同时避免了无关信息干扰

3. **文本切片与 Embedding 质量**：
   - overlap 切片保证语义完整性，减少"检索到半段内容"的情况
   - 切片大小 500 token 是在"语义完整"和"Embedding 精度"之间的平衡点

4. **缓存热点查询**：
   - 对高频相同问题的向量检索结果做 Redis 缓存，TTL 1小时
   - 命中缓存时直接返回候选块，跳过向量计算，延迟从 30ms 降到 2ms

**收尾：** 召回率和延迟不是非此即彼，通过分阶段过滤和缓存可以在两者之间找到较好的平衡点。

## Q13. 如何评估大模型应用的效果和性能？关注哪些指标？

**结论先行：**
> 分两个维度：效果评估看"回答对不对"（准确率、幻觉率、相关性），性能评估看"回答快不快贵不贵"（延迟、Token消耗、吞吐量）。

**效果指标：**

| 指标 | 说明 | 评估方式 |
|------|------|---------|
| 答案相关性 | 回答是否切题 | 人工抽样 or LLM-as-Judge |
| 幻觉率 | 回答了不存在于知识库的内容 | 构建"无答案"测试集，检测是否无中生有 |
| 检索命中率 | RAG 检索到的文档块是否包含正确答案 | 标注测试集，计算 MRR/Recall@K |
| 意图识别准确率 | 意图路由是否正确分类 | 分类测试集 + 混淆矩阵 |

**性能指标：**

| 指标 | 说明 | 目标值 |
|------|------|--------|
| TTFT（首Token延迟） | 用户发消息到第一个字出来的时间 | < 1s（流式体验） |
| 端到端延迟 | 完整回答生成时间 | < 5s（P95） |
| Token消耗/次 | 平均每次对话的输入+输出Token | 控制成本 |
| QPS | 系统支持的并发请求量 | 按业务需求设定 |

**线上线下评估方式：**

- **线下**：构建 Golden Dataset（标注问答对），定期跑回归测试，观察指标变化，发现模型/检索效果退化
- **线上**：埋点收集用户"点赞/踩"反馈，统计自动解决率（对话不转人工的比例），作为效果代理指标
- **A/B测试**：切换不同 prompt 版本或检索策略时，用 A/B 测试对比效果，避免主观判断

**我在项目里的实际做法：**
构建了一个 20 个问题的测试集，覆盖"知识库内有答案"、"知识库内无答案"、"领域外问题"三类，每次修改检索逻辑后跑一遍，检查相关性和幻觉率是否有退化。

**收尾：** 评估体系的核心是"可量化、可复现"，有了数据才能做有依据的优化，而不是凭感觉改来改去。
