## 未完成任务

### Tool Calling 消息序列化修复（优先级 P0）

**发现日期**：2026-04-30

**现状问题**：当前 `RedisChatMemoryRepository` 的序列化方案只存 `messageType` + `text` 两个字段，Tool Calling 场景下存在严重信息丢失：

| 消息类型 | 当前处理 | 丢失的信息 |
|---------|---------|-----------|
| AssistantMessage（含 tool_calls） | `getText()` 返回空字符串，只存空 text | **tool_calls 的函数名、参数全部丢失** |
| ToolResponseMessage | 降级为 `AssistantMessage(text)` | **Tool 名称、调用 ID、响应数据格式丢失** |

**实际后果**：当 maxMessages 窗口内包含 Tool Calling 历史时，AI 看不到之前调过哪个 Tool、传了什么参数，可能产生混乱或重复调用。

**修复方案**：

序列化时增加 `toolCalls` 和 `toolName`/`id` 字段：

```json
// AssistantMessage（含 tool_calls）
{"messageType":"ASSISTANT","text":"","toolCalls":[{"name":"queryOrder","arguments":"{\"orderId\":\"ORD-001\"}"}]}

// ToolResponseMessage
{"messageType":"TOOL","text":"{\"status\":\"已发货\"}","toolName":"queryOrder","id":"call_abc123"}
```

**涉及文件**：`RedisChatMemoryRepository.java`（serializeMessage + deserializeMessage）

**面试价值**：这是企业级 ChatMemory 必须解决的问题——生产环境 Tool Calling 是高频场景，记忆不完整会导致 AI 行为异常。

### Tool 数据真实化（优先级 P1，企业级核心能力）

**现状问题**：3个 @Tool 方法全部返回硬编码数据：
- `queryOrder`：只认 ORD-001，其他订单返回"未找到"
- `queryStock`：固定返回 Java高级编程，stock=156
- `submitAftersale`：只生成工单号，不实际存储

**企业落地必须改进**：
1. **查真实 DB**：Tool 方法注入 Mapper/Service，查 MySQL 的订单表、商品表
2. **售后工单入库**：`submitAftersale` 的结果写回数据库
3. **多 Tool 联动**：查询订单后，AI 能基于订单数据决定下一步操作

**建议方案**（渐进式）：
- 阶段1：在 MySQL 中建 t_order / t_product 表，灌入测试数据，Tool 改为查 DB
- 阶段2：售后工单写回 DB，实现完整的"查询→处理→记录"闭环
- 阶段3（可选）：加入 Redis 缓存热点商品库存数据

**面试价值**：Tool Calling + 真实 DB = 企业级 AI 应用落地的标准能力，面试核心卖点。

### RAG 参数调优（优先级 P1，影响回答准确度）

**现状**：`TokenTextSplitter` 使用默认参数（chunkSize=800），回答效果不佳。

**优化内容**：

```java
// 1. TokenTextSplitter 参数调整（RagService.java）
TokenTextSplitter splitter = new TokenTextSplitter(
    300,     // chunkSize：默认800太大，中文场景300更合适
    50,      // minChunkSizeChars
    5,       // minChunkLengthToEmbed
    10000,   // maxNumChunks
    true     // keepSeparator
);

// 2. SearchRequest 加相似度阈值（AgentController + RagController）
SearchRequest.builder()
    .query(question)
    .topK(3)
    .similarityThreshold(0.7)   // 过滤噪音片段
    .build();
```

**注意**：调优后需要**重新上传文档**使新的切分参数生效（已有的向量数据是基于旧参数切的）。

**详细分析**：见 `踩坑记录_202604281903.md` → TODO-1

### Agent 融合 RAG（优先级 P1，架构优化）

**现状**：AgentController 中手动调用 `vectorStore.similaritySearch()` 然后拼 System Prompt，RAG 逻辑和 Controller 耦合。

**目标**：用 `QuestionAnswerAdvisor` 替代手动 RAG，与 `MessageChatMemoryAdvisor` 组成 Advisor 链：

```java
this.chatClient = chatClientBuilder
        .defaultTools(orderTools)
        .defaultAdvisors(
                MessageChatMemoryAdvisor.builder(chatMemory).build(),
                QuestionAnswerAdvisor.builder(vectorStore)
                        .searchRequest(SearchRequest.builder()
                                .topK(3)
                                .similarityThreshold(0.7)
                                .build())
                        .build()
        )
        .build();
```

**收益**：Controller 代码简化（删掉手动 vectorStore 调用），RAG 和 Memory 自动协同工作。

**前置依赖**：RAG 参数调优完成后再做（Advisor 中统一配置参数）
