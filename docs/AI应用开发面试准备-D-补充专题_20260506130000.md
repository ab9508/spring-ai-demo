## 一、QuestionAnswerAdvisor vs CustomRagAdvisor

### 面试官问："Spring AI 自带 QuestionAnswerAdvisor，你为什么还要自己写 CustomRagAdvisor？"

**3 分钟版回答：**

> **核心差异：QuestionAnswerAdvisor 没有分数过滤能力。**
>
> QuestionAnswerAdvisor 是 Spring AI 内置的 RAG Advisor，它的流程是：
> 1. 把用户问题做向量检索（调 VectorStore.similaritySearch）
> 2. 把检索到的文档注入 system prompt
> 3. 调 LLM 生成回答
>
> 看起来功能完整，但它有一个致命缺陷：**不做分数过滤**。检索到的文档不管相关性多低都会注入 prompt。
>
> **实测数据：** 我用 nomic-embed-text 模型测试，即使问完全不相关的问题（比如电商知识库里问"明天天气"），top1 分数也有 0.35~0.62。这些低质量片段注入 prompt 后，LLM 会基于错误信息"一本正经地胡说八道"，比直接回答更糟糕（幻觉更难被发现）。
>
> **CustomRagAdvisor 加了什么：**
> | 能力 | QuestionAnswerAdvisor | CustomRagAdvisor |
> |------|----------------------|-----------------|
> | 向量检索 | ✅ | ✅ |
> | 注入上下文 | ✅ | ✅ |
> | 绝对阈值过滤 | ❌ | ✅ top1<0.45 拒绝 |
> | 相对分数过滤 | ❌ | ✅ 无区分度检测+15%衰减 |
> | Token 用量监控 | ❌ | ✅ after() 日志 |
> | 上下文注入方式 | 替换 system message | 追加到 system message |
>
> **一句话总结：** QuestionAnswerAdvisor 是"有就注入"的简单模式，CustomRagAdvisor 是"注入前先判断质量"的增强模式。企业级应用必须做质量过滤。

**追问预判：**

- **Q："QuestionAnswerAdvisor 不能通过 SearchRequest 设置 threshold 吗？"** A："可以设绝对阈值，但那只是入门级过滤。我测过固定阈值 0.7，换话题问分数不是 0.1 而是 0.42——说明阈值不稳定。相对分数过滤是自适应的，不依赖绝对值。"
- **Q："为什么不继承 QuestionAnswerAdvisor 加逻辑？"** A："QuestionAnswerAdvisor 的内部实现耦合了 ETL 文档处理逻辑，不适合扩展。直接实现 BaseAdvisor 更干净，只关心'检索+过滤+注入'三件事。"
- **Q："以后 QuestionAnswerAdvisor 加了过滤能力，你的 CustomRagAdvisor 还有价值吗？"** A："有。CustomRagAdvisor 的相对分数过滤逻辑是业务经验积累的（三级过滤规则），不太可能成为框架通用功能。即使框架加了，也只会是简单阈值，我们的相对过滤仍然更精细。"

## 二、关键参数标准

### 面试官问："你简历里提到的各种参数是怎么确定的？"

| 参数 | 值 | 怎么定的 | 面试怎么说 |
|------|---|---------|-----------|
| **置信度 Confidence** | 0~1 浮点数 | LLM 自己输出的，不是我们算的 | "置信度是 DeepSeek 在意图识别时自行评估的，通过 prompt 约束返回 0~1 的数字。实际测试中，真正有意图的请求置信度普遍 >0.7，模糊请求在 0.4~0.7，完全无关 <0.4。这个值作为参考，不作为硬判断依据。" |
| **余弦相似度 Cosine Similarity** | 0~1 | 由 Embedding 模型和 PgVector 计算得出 | "余弦相似度衡量两个向量方向的接近程度。PgVector 用 <=> 操作符计算，Spring AI 封装了 similaritySearch API。nomic-embed-text 在相关问答上平均 0.75~0.85，不相关 0.35~0.55。" |
| **top1 绝对阈值** | 0.45 | 50个测试问题跑分布图 | "准备了30个有答案+20个无答案的测试问题，跑出分数分布。不相关问题的 top1 平均 0.48，相关平均 0.78，取中间值偏下 0.45 作为兜底。" |
| **top1-top2 分差阈值** | 0.08 | 经验值+测试验证 | "分差小说明模型'分不出好坏'。测试中发现相关问题的 top1-top2 平均 0.15，不相关问题平均 0.03。取 0.08 能有效区分。可以类比为'考试第一名62分第二名61分，不是第一名好，是整体不行'。" |
| **15% 相对衰减** | top1×0.85 | 经验值 | "保留与 top1 分差 15% 以内的 chunk。太松（30%）会引入噪音，太紧（5%）可能丢掉有效片段。15% 是测试后取的平衡值。" |
| **chunkSize** | 500 token | 业界推荐值 | "500 token ≈ 1000汉字 ≈ 2~3段，包含一个完整语义单元。太小语义不完整，太大噪音多。业界 RAG 实践普遍用 300~800 token。" |
| **overlap** | 50 token（10%） | 业界推荐 10%~20% | "50 token 能覆盖约2个完整句子，防止边界语义断裂。10% 是经验值，RAG 最佳实践普遍推荐 10%~20%。" |
| **maxMessages** | 20 条 | 平衡成本和效果 | "20条 = 10轮对话。Token 成本约 4000~6000，在 DeepSeek API 成本可控范围内。太多（50条）成本高且可能超出上下文窗口。" |
| **temperature** | 0.7（对话）/ 0（结构化输出） | 场景决定 | "对话场景 0.7 保持自然感；意图识别 0 确保输出稳定；RAG 问答 0.1~0.3 减少幻觉。" |
| **Embedding 维度** | 768 | nomic-embed-text 模型固定输出 | "nomic-embed-text 输出 768 维向量。这是模型架构决定的，不是我们配的。PgVector 的 dimensions 参数必须和模型输出一致，否则报错。" |

## 三、analyzeIntent 场景深度分析 + Tool>systemPrompt 冲突

### 3.1 面试官问："你的 /analyzeIntent 端点只做了意图识别，企业实际可能需要既调用工具又返回结构化JSON，你怎么处理？"

**3 分钟版回答：**

> **这是两个不同场景，用不同架构解决：**
>
> **场景A：只识别意图，不调工具 → 当前方案（jsonOnlyClient）**
> - 目的：路由分发——识别出用户意图后，由业务代码决定走哪个流程
> - 实现：纯净 ChatClient（无工具挂载），prompt 约束只返回 JSON
> - 优势：响应快（1次LLM调用）、结构化输出可控
>
> **场景B：调工具 + 返回结构化结果 → 企业常见需求**
> - 目的：用户问"查一下订单 12345 的状态"，既要调订单查询接口，又要返回结构化 JSON 给上游系统
> - **冲突点：** DeepSeek 看到工具定义后会优先调工具，不返回 JSON。调完工具后返回的是自然语言（"您的订单已发货"），不是 JSON
> - **解决方案：两步法**
>   1. 第一步：Agent ChatClient（带工具）→ DeepSeek 调用工具 → 拿到工具返回结果
>   2. 第二步：jsonOnlyClient（无工具）→ 把工具返回结果 + 用户原始请求喂给 LLM → 约束返回 JSON 格式
>
> **伪代码：**
> ```java
> // 第一步：Agent 调工具
> ChatResponse agentResult = chatClient.prompt()
>     .user("查一下订单 12345 的状态")
>     .call()
>     .chatResponse();
> String toolResult = extractToolCallResult(agentResult);
>
> // 第二步：纯净 Client 结构化输出
> String json = jsonOnlyClient.prompt()
>     .system("根据工具返回结果，输出JSON格式：{\"orderNo\":\"\",\"status\":\"\",\"logistics\":\"\"}")
>     .user("工具返回：" + toolResult)
>     .call()
>     .content();
> ```
>
> **本质：** Tool Calling 和结构化输出在同一个 ChatClient 上是互斥的（OpenAI 协议 tools > system > user 优先级），用两个 Client 各司其职是最干净的解法。

**追问预判：**

- **Q："两步法多了一次 LLM 调用，不增加延迟和成本吗？"** A："是的，多 1~2 秒和多 200~500 token。但如果业务确实需要结构化结果，这是必须的。也可以让工具方法直接返回结构化数据（而非自然语言），LLM 拿到结构化数据后格式化输出，这样质量更高。"
- **Q："DeepSeek 有没有 Function Calling 返回 JSON 的模式？"** A："DeepSeek 的 Tool Calling 返回的是 AssistantMessage + toolCalls，不是 JSON。这是 OpenAI 协议标准行为。要拿 JSON，必须在工具调用完成后再做一次结构化输出。"

### 3.2 Tool > systemPrompt 冲突详解

**面试官问："你说 Tool Calling 优先级高于 system prompt，具体是什么意思？"

> **OpenAI 协议优先级：tools > system > user**
>
> 当 HTTP 请求体中包含 `tools` 字段时，模型进入"工具调用模式"：
> - 模型会先判断"用户的请求是否可以由某个工具处理"
> - 如果可以 → 返回 tool_calls（函数调用请求），不生成文本
> - 如果不可以 → 才按 system prompt + user message 生成文本
>
> **实际踩坑：**
> 我用带 Tool Calling 的 ChatClient 发意图识别请求，prompt 里明确说"只返回 JSON，不要调用任何工具"，但 DeepSeek 依然返回了 tool_calls——因为它看到 tools 字段后进入了工具调用模式，system prompt 的"禁止调用工具"指令被忽略了。
>
> **根因：** 这是协议层面的设计。tools 是 API 级别的强制行为，system prompt 是文本级别的"建议"。LLM 被训练为优先响应 API 级别的指令。
>
> **底层区别 = HTTP 请求体不同：**
> - 带 Tool Calling 的请求：
> ```json
> {"model":"deepseek-chat","messages":[...],"tools":[{"type":"function","function":{"name":"queryOrder",...}}]}
> ```
> - 不带 Tool Calling 的请求：
> ```json
> {"model":"deepseek-chat","messages":[...]}
> ```
> 模型看到 `tools` 字段 → 进入工具调用模式；没有 `tools` 字段 → 纯文本生成模式。
>
> **解法：** ChatClient.builder(chatModel) 工厂方法每次创建全新 Builder，构建的 ChatClient 不继承任何工具配置。

## 四、ChatClient 是什么、有什么用

### 面试官问："ChatClient 是什么？和 ChatModel 有什么区别？"

**3 分钟版回答：**

> **ChatModel = 底层模型调用器（类比 JDBC Connection）**
> - 职责：发送 HTTP 请求给 LLM API，返回 ChatResponse
> - 一个 ChatModel 对应一个模型实例（Ollama 或 DeepSeek）
> - 是低级 API，只管"调一次模型"
>
> **ChatClient = 高级对话构建器（类比 MyBatis SqlSession）**
> - 职责：构建完整的对话流程（system prompt + 用户消息 + 工具 + 记忆 + Advisor 链）
> - 由 ChatClient.builder(chatModel).build() 创建
> - 是高级 API，封装了对话编排的所有细节
>
> **关系：ChatClient 内部持有一个 ChatModel，ChatClient 的所有调用最终都是调 ChatModel。**
>
> **ChatClient 能做什么：**
> ```java
> ChatClient client = ChatClient.builder(chatModel)
>     .defaultSystem("你是电商客服")     // 默认 system prompt
>     .defaultTools(orderTools)          // 默认挂载工具
>     .defaultAdvisors(memoryAdvisor)    // 默认 Advisor 链
>     .build();
>
> // 调用
> String answer = client.prompt()
>     .user("你好")
>     .call()
>     .content();
> ```
>
> **为什么需要两个 Client：**
> - `chatClient`（带工具+记忆）：用于 Agent 对话场景
> - `jsonOnlyClient`（纯净无工具）：用于结构化输出场景
> - 两者底层共享同一个 ChatModel，但对话配置完全隔离

**追问预判：**

- **Q："ChatClient.Builder 是单例还是多例？"** A："默认不是单例。`ChatClient.builder(chatModel)` 是工厂方法，每次返回全新 Builder。我们项目中通过 @Bean 注入了一个 ChatClient.Builder，Controller 拿到的是同一个 Builder，可以 build 出不同的 ChatClient。"
- **Q："ChatClient 线程安全吗？"** A："ChatClient 本身是线程安全的（不可变对象，build 后配置不变）。ChatClient.Builder 是可变的（.defaultTools() 修改自身），不是线程安全的，build 后就没问题了。"
- **Q："和 RestTemplate/WebClient 调 OpenAI API 有什么区别？"** A："ChatClient 封装了：(1) HTTP 请求构建（自动拼装 messages/tools）(2) 响应解析（自动转成 Java 对象）(3) 重试/超时 (4) 流式输出 (5) Advisor 链编排。手动调 RestTemplate 需要自己处理这些，工作量巨大且容易出错。"

## 六、RAG 相对分数过滤：好处与不足

### 面试官问："相对分数过滤有什么好处？有什么不足？"

#### 好处

1. **自适应性强**：不依赖固定阈值，不同领域/不同问题的分数分布差异大，相对分数天然适配
2. **减少幻觉**：低质量片段不注入 prompt，LLM 不基于错误信息编造
3. **三重保障**：绝对兜底 + 无区分度检测 + 相对衰减，层层过滤
4. **可解释**：每条过滤规则都有明确的业务含义（"top1太低=不相关"、"分差太小=不确定"）

#### 不足（面试必准备的追问）

| 不足 | 说明 | 改进方向 |
|------|------|---------|
| **参数是经验值** | 0.45/0.08/15% 都是我用50个测试问题跑出来的，不是理论最优解 | 做更多测试（200+样本），用统计方法（如 ROC 曲线）确定最优阈值 |
| **对中文长文本效果待验证** | 测试数据以短问答为主，长文档（5000字+商品说明）的分数分布可能有差异 | 补充长文档测试用例 |
| **没有 Reranking** | 只用了 Bi-Encoder（Embedding 模型），精度有限 | 引入 Cross-Encoder 做精排（向量检索 top50 → Reranking top5） |
| **没有混合检索** | 只用了向量检索，没有 BM25 关键词检索 | 加 ES/ElasticSearch 做 BM25 召回，RRF 融合排序 |
| **单模型 Embedding** | 只用了 nomic-embed-text 一个模型做 Embedding | 多模型 Embedding + 投票/平均，提高鲁棒性 |
| **过滤后无结果时体验差** | 相对过滤可能把所有结果都过滤掉，LLM 只能说"我不知道" | 降级策略：严格过滤无结果 → 放宽条件重试 → 最终返回"建议人工客服" |

**面试怎么说：**

> "相对分数过滤解决了最核心的问题——无关结果注入导致幻觉。但它也有不足：参数是经验值，不够精确；没有 Reranking 精排；没有混合检索。
>
> 如果有更多时间，我会优先做两件事：一是引入 Reranking（Cross-Encoder 精排），这是性价比最高的改进；二是做混合检索（向量+BM25），弥补向量检索在精确匹配上的弱点。
>
> 这些不足不影响系统可用性，因为我们有三重过滤兜底——最坏情况就是'没有检索到结果，LLM 直接回答'，不会注入错误信息。"

## 七、双模型配置踩坑记录

### 面试官问："双模型配置遇到过什么问题？"

**3 分钟版回答：**

> **坑1：Bean 歧义问题**
> - Ollama 自动配置注入 `ollamaChatModel`，DeepSeek（OpenAI兼容）自动配置注入 `openAiChatModel`
> - Controller 里注入 `ChatModel` 时，Spring 不知道用哪个 → `NoUniqueBeanDefinitionException`
> - **解法：** 自定义 `ChatClientConfig`，用 `@Qualifier` 指定 + `@Primary` 标注动态选择的 `selectedChatModel`
>
> **坑2：Embedding 自动配置冲突**
> - DeepSeek 的 OpenAI 兼容配置会尝试创建 OpenAI EmbeddingModel
> - 但 Embedding 我们用 Ollama 本地（免费），两个 EmbeddingModel Bean 冲突
> - **解法：** `@SpringBootApplication(exclude = OpenAiEmbeddingAutoConfiguration.class)` 排除冲突的自动配置
>
> **坑3：OpenAiApi 的 embeddingsPath 不能以 "/" 开头**
> - 自定义 `OpenAiApi` 时，`embeddingsPath` 设为 `/v1/embeddings`，发现 RestClient 把它拼成 `https://api.deepseek.com//v1/embeddings`（双斜杠）→ 404
> - **解法：** 去掉前导 `/`，写成 `v1/embeddings`。RestClient 会自动拼接。
>
> **坑4：ChatClient.Builder 可变性问题**
> - `ChatClient.Builder` 是可变对象，`.defaultTools()` 修改自身（return this），不是创建新对象
> - 如果同一个 Builder 先 build 带 tools 的 Client，再 build 不带 tools 的 → 第二个也被污染
> - **解法：** `ChatClient.builder(chatModel)` 是工厂方法，每次创建全新 Builder，完全隔离
>
> **好处总结：**
> 1. **成本优化：** Embedding 用 Ollama 本地（免费），Chat 用 DeepSeek API（按量付费），合理分配成本
> 2. **离线可用：** 本地 Ollama 挂了只影响 Embedding，不影响对话（如果 Chat 也切 Ollama 则完全离线可用）
> 3. **灵活切换：** 配置文件改 `app.chat.provider=openai` 即可切换模型，代码零改动

## 九、LangChain4j 基础知识

### 面试官问："了解 LangChain4j 吗？和 Spring AI 有什么区别？"

**3 分钟版回答：**

> **LangChain4j 是和 Spring AI 同维度的 Java AI 应用框架，但功能更丰富、生态更成熟。**
>
> **核心定位对比：**
>
> | 维度 | Spring AI | LangChain4j |
> |------|-----------|------------|
> | 定位 | Spring 生态的 AI 集成层 | 独立的 Java AI 框架 |
> | 发布时间 | 2024年5月（1.0.0 GA） | 2023年 |
> | 核心优势 | 和 Spring Boot 无缝集成，自动配置 | 功能丰富，社区活跃，文档完善 |
> | RAG 支持 | 基础（VectorStore + 简单 Advisor） | 成熟（多种 DocumentSplitter、EmbeddingStore、Retriever） |
> | ChatMemory | 1.0.x 只有4种存储实现 | 内置多种：内存、Redis、Cassandra、MongoDB、PostgreSQL 等 |
> | Tool Calling | @Tool 注解（1.0.x 新写法） | @Tool 注解（类似），支持更多参数类型 |
> | 结构化输出 | 1.0.x 较弱（需手动解析） | AiServices + @Description 原生支持 |
> | 流式输出 | WebFlux Flux | SSE + StreamingResponseHandler |
> | AI Services | 无（自己封装 Controller） | 核心功能（声明式 AI 服务接口，类似 Feign） |
> | 模型支持 | OpenAI/Ollama/Anthropic/阿里通义等 | OpenAI/Ollama/HuggingFace/更多 |
>
> **LangChain4j 的核心亮点——AI Services：**
> ```java
> // LangChain4j 的声明式 AI 服务（类似 Feign 调用 AI）
> interface CustomerSupport {
>     @SystemMessage("你是电商客服")
>     String answer(@UserMessage String question);
>     @SystemMessage("分析意图")
>     IntentRecord analyze(@UserMessage String message);
> }
> ```
> 不用自己写 Controller、自己管理 ChatClient、自己解析 JSON——框架全包了。
>
> **我为什么选 Spring AI：**
> 1. 技术栈一致性——项目本身就是 Spring Boot，Spring AI 集成零成本
> 2. 学习价值——Spring AI 底层更透明（自己写 Advisor、自己管理 ChatClient），能深入理解 AI 应用架构
> 3. 求职差异化——多数人用 LangChain4j（教程多），Spring AI 实战的人少，反而更有亮点
>
> **但如果进公司要求用 LangChain4j，我能快速上手：** 核心概念完全一样（ChatMemory = Memory、Advisor = Chain、Tool Calling = Tools），只是 API 不同。RAG 流程、Prompt Engineering、Agent 架构这些知识是跨框架通用的。

**追问预判：**

- **Q："LangChain4j 的 RAG 和 Spring AI 有什么区别？"** A："概念一样，API 不同。LangChain4j 的 RAG 用 EmbeddingStore + EmbeddingModel + DocumentSplitter + Retriever 四个组件组合，Spring AI 用 VectorStore + TextSplitter + Advisor 链。LangChain4j 的组件更丰富（如 TikaDocumentParser、DocumentByParagraphSplitter），Spring AI 更简洁。"
- **Q："LangChain4j 的 ChatMemory 支持更好？"** A："是的，LangChain4j 内置了 Redis/PostgreSQL/MongoDB/Cassandra 等多种 ChatMemory 实现。Spring AI 1.0.x 只有4种，Redis 需要自己写（我们就是这么做的）。这是 Spring AI 1.0.x 的短板，后续版本应该会补。"
- **Q："企业选型建议？"** A："如果公司是 Spring 技术栈 + AI 是辅助功能 → Spring AI；如果公司要做重度 AI 应用（多模型、复杂 Agent、多模态）→ LangChain4j。两者可以共存（Spring AI 做 API 层，LangChain4j 做核心 AI 逻辑），但一般选一个就够了。"

## 十、SpringAiDemo 快速介绍（1分钟版 + 3分钟版）

### 1 分钟版（电梯演讲 / HR 面）

> "我用 Spring AI 搭建了一个电商智能客服系统。核心做了三件事：
>
> 第一，**RAG 知识库检索**——上传文档自动切片向量化，基于 PgVector 存储。我自己写了一个 RAG Advisor，加了相对分数过滤，解决固定阈值不稳定的问题。
>
> 第二，**多轮对话记忆**——Spring AI 原生不支持 Redis，我手写了一个 RedisChatMemoryRepository，实现了对话记忆持久化。
>
> 第三，**Tool Calling 智能体**——AI 可以自主调用订单查询、物流追踪等业务接口。另外发现模型挂载工具后会忽略返回JSON的指令，用双 Client 隔离解决了这个问题。
>
> 技术选型上，Chat 用 DeepSeek API，Embedding 用 Ollama 本地模型，向量存储用 PgVector。"

### 3 分钟版（技术面 / 架构面）

> "这是一个基于 Spring AI 1.0 + Spring Boot 3.4 的电商智能客服系统。我从头搭建了整套架构，主要包含四个核心模块：
>
> **模块一：双模型配置。**
> Chat 用 DeepSeek API（按量付费，效果好），Embedding 用 Ollama 本地部署的 nomic-embed-text（免费）。通过 @Qualifier + @Primary 解决双 ChatModel 的 Bean 歧义问题，配置文件一个开关就能切换模型。过程中踩了几个坑：OpenAiApi 的 embeddingsPath 不能以 / 开头导致 404；Embedding 自动配置冲突需要排除。
>
> **模块二：RAG 知识库检索。**
> Spring AI 内置的 QuestionAnswerAdvisor 不做分数过滤，实测发现 nomic-embed-text 对不相关问题也有 0.35~0.62 的分数。所以我实现了一个 CustomRagAdvisor（BaseAdvisor），加了三级相对分数过滤：top1 绝对兜底（<0.45 拒绝）、无区分度检测（top1-top2 <0.08 拒绝）、15% 相对衰减（只保留和 top1 分差 15% 以内的 chunk）。Advisor 链的编排也很关键：MessageChatMemoryAdvisor 先于 CustomRagAdvisor 执行，这样 RAG 检索时能看到对话上下文，能处理'刚才那个订单'这种指代。
>
> **模块三：对话记忆。**
> Spring AI 1.0.x 原生只支持 InMemory/JDBC/Cassandra/Neo4j，没有 Redis 实现。我手写了 RedisChatMemoryRepository 实现 ChatMemoryRepository 接口，用 Redis List 存储，Jackson DTO 中转解决 Message 子类无参构造问题。另外还做了摘要压缩——超过 20 条消息时用 LLM 把前半段压缩成摘要，用装饰器模式实现，对上层透明。
>
> **模块四：Tool Calling Agent。**
> 用 @Tool 注解声明式定义工具方法（订单查询、物流追踪），DeepSeek 自动识别意图并调用。遇到一个经典问题：模型挂载了工具后，即使 prompt 说'只返回 JSON 不要调工具'，模型还是会优先调工具——因为 OpenAI 协议的 tools > system > user 优先级。解决方案是用 ChatClient.builder(chatModel) 工厂方法创建一个纯净的 ChatClient（无工具），专门用于结构化输出场景。
>
> 整个项目我自研了 6 个组件来增强 Spring AI 基础能力，通过实际踩坑深入理解了 AI 应用的核心架构。"
