## 二、核心概念解析

### 2.1 ChatClient——对话客户端

**是什么**：Spring AI 对话功能的统一入口，封装了大模型 API 调用的细节。

**项目中的用法**：

```java
// ChatController.java
public ChatController(ChatClient.Builder chatClientBuilder) {
    this.chatClient = chatClientBuilder.build();
}
```

**原理**：
1. `spring-ai-starter-model-openai` 自动配置读取 `application.yml` 中的 `spring.ai.openai.*`
2. 创建 `OpenAiChatModel` Bean（底层是 `OpenAiApi`，通过 RestClient 调用 HTTP 接口）
3. `ChatClient.Builder` 自动注入 `OpenAiChatModel`，`.build()` 生成 `ChatClient`

**调用链路**：
```
chatClient.prompt()
    .system("角色设定")       ← System Message
    .user("用户问题")         ← User Message
    .call()                  ← 发送 HTTP 请求到 DeepSeek API
    .content()               ← 提取回复文本
```

**底层 HTTP 请求**（实际发给 DeepSeek 的）：
```
POST https://api.deepseek.com/v1/chat/completions
Authorization: Bearer sk-xxx

{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "角色设定"},
    {"role": "user", "content": "用户问题"}
  ],
  "temperature": 0.7
}
```

**关键点**：ChatClient 本身不包含模型配置，它只是一个壳。真正的模型配置（API Key、Base URL、model name）在 `OpenAiChatModel` 里。

### 2.2 EmbeddingModel——文本向量化

**是什么**：把一段文本转换成一个固定长度的浮点数数组（向量），语义相近的文本向量也相近。

**项目中的用法**：

```java
// SpringAiDemoApplication.java（手动创建，不走自动配置）
@Bean
public OllamaEmbeddingModel ollamaEmbeddingModel() {
    OllamaApi ollamaApi = OllamaApi.builder().build();  // 默认 localhost:11434
    return new OllamaEmbeddingModel(
        ollamaApi,
        OllamaOptions.builder().model("nomic-embed-text").build(),
        ObservationRegistry.NOOP,
        ModelManagementOptions.builder().build()
    );
}
```

**原理**：
```
"Java是一门面向对象的语言"  ──→ OllamaEmbeddingModel.embed() ──→ [0.12, -0.34, 0.56, ..., 0.78]
                                  │
                                  ▼
                          POST http://localhost:11434/api/embed
                          {"model":"nomic-embed-text","prompt":"Java是一门面向对象的语言"}
                                  │
                                  ▼
                          返回 [0.12, -0.34, 0.56, ..., 0.78]  （768个浮点数）
```

**模型对比**：

| 模型 | 维度 | 来源 | 特点 |
|------|------|------|------|
| nomic-embed-text | 768 | Ollama 本地 | 轻量、免费、延迟低 |
| text-embedding-3-small | 1536 | OpenAI | 效果好、收费 |
| embedding-3 | 2048 | 智谱AI | 中文效果好、收费 |

### 2.3 Document——文档对象

**是什么**：Spring AI 中表示一段文本及其元数据的载体。

**结构**：
```java
public class Document {
    private String text;              // 文本内容
    private Map<String, Object> metadata;  // 元数据
    private String id;                // 唯一标识
    private float[] embedding;        // 向量（可选）
}
```

**在 RAG 流程中的生命周期**：

```
PDF 文件
  → PagePdfDocumentReader.get()     → List<Document>（每页一个）
    → TokenTextSplitter.apply()     → List<Document>（每段一个，metadata 保留页码信息）
      → VectorStore.add()           → Document.embedding 被填上 768 维向量
        → similaritySearch()        → 按相似度返回匹配的 Document
```

### 2.4 TokenTextSplitter——文本切分器

**是什么**：把长文本按 Token 数量切成小段，用于 Embedding 和检索。

**为什么需要切分**：
- Embedding 模型有最大输入长度限制（通常 512-8192 Token）
- 太长的文本向量会"稀释"关键信息
- 切分后检索更精准（只返回最相关的片段，而不是整篇文档）

**默认参数**（项目当前用的）：

| 参数 | 默认值 | 含义 | 影响 |
|------|--------|------|------|
| defaultChunkSize | 800 | 每段最大 Token 数 | 越大保留的上下文越多，但噪声也越多 |
| defaultOverlap | **0** | 段间重叠 Token 数 | **0 会导致上下文断裂** |
| minChunkSizeChars | 350 | 最小字符数 | 防止产生太短的片段 |
| maxNumChunks | 10000 | 最大分片数 | 防止超大文档内存溢出 |

**切分示意**（overlap=0 vs overlap=200）：

```
原文（1200 Token）：
[═════════════════════════════════════════════════════════════]
[A段: 800 Token][B段: 400 Token]

overlap=0（当前）：
[════════════════════════════════════]    ← chunk1
                    [════════════════════] ← chunk2（在800处截断，可能切断句子）

overlap=200（推荐）：
[════════════════════════════════════]    ← chunk1
                [════════════════════════] ← chunk2（200 Token 重叠，上下文连续）
                        [════════════════] ← chunk3
```

### 2.5 VectorStore——向量存储

**是什么**：存储文档向量并提供相似度检索的接口。

**类层次**：
```
                    <<interface>>
                    VectorStore
                        │
        ┌───────────────┼───────────────┐
        │               │               │
  SimpleVectorStore  PGVectorStore   MilvusVectorStore
  （内存 Map）        （PostgreSQL）    （分布式）
```

**核心方法**：

```java
public interface VectorStore {
    // 添加文档（自动调 EmbeddingModel 转向量后存储）
    void add(List<Document> documents);

    // 相似度检索
    List<Document> similaritySearch(SearchRequest request);
}
```

**SimpleVectorStore 底层原理**：

```java
// Spring AI 源码简化版
public class SimpleVectorStore implements VectorStore {
    private EmbeddingModel embeddingModel;
    private Map<String, Document> store = new ConcurrentHashMap<>();  // 就是一个 Map！

    @Override
    public void add(List<Document> documents) {
        for (Document doc : documents) {
            // 1. 文本转向量
            float[] embedding = embeddingModel.embed(doc.getText());
            doc.setEmbedding(embedding);
            // 2. 存入 Map
            store.put(doc.getId(), doc);
        }
    }

    @Override
    public List<Document> similaritySearch(SearchRequest request) {
        // 1. 问题转向量
        float[] queryEmbedding = embeddingModel.embed(request.getQuery());
        // 2. 遍历所有文档，计算余弦相似度
        return store.values().stream()
            .map(doc -> new Similarity(doc, cosineSimilarity(queryEmbedding, doc.getEmbedding())))
            .sorted(Comparator.comparingDouble(Similarity::score).reversed())
            .limit(request.getTopK())
            .map(Similarity::document)
            .collect(Collectors.toList());
    }
}
```

**余弦相似度**（向量检索的核心算法）：

```java
// 两个向量 A 和 B 的余弦相似度
cosineSimilarity(A, B) = (A·B) / (|A| × |B|)
// 结果范围：-1 到 1，越接近 1 越相似

// 举例
"Java面向对象" 和 "Java面向对象的编程语言" → 0.95（很相似）
"Java面向对象" 和 "今天天气真好"         → 0.02（几乎不相关）
```

### 3.1 离线阶段——上传 PDF

```
用户 POST /rag/upload (file=xxx.pdf)
       │
       ▼
RagController.upload()
       │
       ▼
RagService.uploadDocument()
       │
       ├── 1. 保存 PDF 到 D:\test\{timestamp}_xxx.pdf
       │
       ├── 2. PagePdfDocumentReader.get()
       │      └── 按 Apache PDFBox 逐页解析文本
       │      └── 返回 List<Document>（每页一个 Document）
       │      └── Document.text = 页面文本
       │      └── Document.metadata = {pdf.resource.name, page.number, ...}
       │
       ├── 3. TokenTextSplitter.apply(documents)
       │      └── 按 800 Token 切分，overlap=0
       │      └── 返回 List<Document>（更多更小的 Document）
       │
       └── 4. vectorStore.add(chunks)
              └── 遍历每个 chunk：
                    ├── OllamaEmbeddingModel.embed(chunk.text)
                    │     └── POST http://localhost:11434/api/embed
                    │     └── 返回 768 维 float[]
                    ├── chunk.setEmbedding(float[])
                    └── store.put(chunk.id, chunk)  → 存入内存 Map
```

### 3.2 在线阶段——问答

```
用户 GET /rag/ask?question=什么是Spring AI
       │
       ▼
RagController.ask()
       │
       ├── 1. vectorStore.similaritySearch(SearchRequest)
       │      ├── OllamaEmbeddingModel.embed("什么是Spring AI")
       │      │     └── 返回 768 维问题向量
       │      ├── 遍历内存中所有文档向量
       │      │     └── 计算余弦相似度

       │
       ├── 2. 拼装 context
       │      └── relevantDocs.stream()
       │            .map(Document::getText)
       │            .collect(joining("\n\n---\n\n"))
       │
       └── 3. chatClient.prompt()
              ├── .system("严格基于参考资料回答...\n参考资料：\n" + context)
              ├── .user(question)
              └── .call().content()
                    │
                    ▼
              POST https://api.deepseek.com/v1/chat/completions
                    │
                    ▼
              返回 DeepSeek 的回答
```

## 四、Spring AI 版本注意点

### 4.1 GA 版命名变更（重要）

| 阶段 | 旧命名（M1-M6） | 新命名（GA 1.0+） |
|------|----------------|-------------------|
| OpenAI Starter | `spring-ai-openai-spring-boot-starter` | `spring-ai-starter-model-openai` |
| Ollama Starter | `spring-ai-ollama-spring-boot-starter` | `spring-ai-starter-model-ollama` |
| 选项类 | `OllamaOptions`（统一） | 拆分为 `OllamaChatOptions` + `OllamaEmbeddingOptions`（1.1+） |

⚠️ 网上很多博客和视频用的是 M1-M6 版本的命名，直接照抄会找不到依赖。

### 4.2 BOM 的作用

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>1.0.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

BOM（Bill of Materials）只管版本号，不引入依赖。好处是：所有 Spring AI 组件版本一致，不会出现 A 用 1.0.3、B 用 1.0.5 的冲突。

### 4.3 自动配置的"双刃剑"

Spring AI 的 starter 会自动创建 Bean（`ChatModel`、`EmbeddingModel` 等），方便但危险：

| 场景 | 自动配置行为 | 风险 |
|------|-------------|------|
| 单一模型 | 自动创建 1 个 ChatModel Bean | 安全 |
| 多模型（Chat=A, Embedding=B） | 自动创建 2 个 ChatModel Bean | ❌ 冲突 |
| 只需要 Embedding 不需要 Chat | 自动创建 ChatModel Bean | ❌ 多余 |

**对策**：需要多模型时，至少一个用核心 jar（非 starter）+ 手动 @Bean。

## 六、Tool Calling 完整调用流程（2026-04-28 补充）

### 6.1 什么是 Tool Calling

让大模型能**调用你写的 Java 方法**，这是 Agent（智能体）的核心能力。

```
用户："帮我查一下订单 ORD-001 的状态"
      ↓
 AI 自主判断：这个问题需要调用订单查询工具
      ↓
 AI 调用：queryOrder("ORD-001")  ← 你写的 Java 方法
      ↓
 AI 回答：订单 ORD-001 已发货，顺丰速运 SF1234567890，预计明天送达
```

### 6.2 Spring AI 底层完整调用链（两次 HTTP 请求）

**核心结论：Spring AI 会向 DeepSeek 发两次 HTTP 请求。**

```
用户: "帮我查一下订单ORD-001的物流"
       │
       ▼
┌─ AgentController.chat() ──────────────────────────────────────┐
│                                                                │
│  ① chatClient.prompt()                                         │
│     .system("你是电商智能客服...")                              │
│     .user("帮我查一下订单ORD-001的物流")                        │
│     .call()                                                    │
│                                                                │
│     Spring AI 内部自动完成：                                    │
│                                                                │
│  ② 把 OrderTools 的 @Tool 方法信息 → 转成 JSON Schema          │
│     发给 DeepSeek，告诉它"你有这些工具可用"                      │
│                                                                │
│  ┌─ DeepSeek API 请求 #1 ───────────────────────────────┐     │
│  │ {                                                     │     │
│  │   "model": "deepseek-chat",                           │     │
│  │   "messages": [...],                                  │     │
│  │   "tools": [{                                         │     │
│  │     "type": "function",                               │     │
│  │     "function": {                                     │     │
│  │       "name": "queryOrder",                           │     │
│  │       "description": "根据订单号查询订单...",           │     │
│  │       "parameters": { "orderId": "string" }           │     │
│  │     }                                                 │     │
│  │   }]                                                  │     │
│  │ }                                                     │     │
│  └──────────────────────────────────────────────────────┘     │
│       │                                                        │
│       ▼  DeepSeek 语义分析后，返回 tool_calls（不是文本回答）    │
│                                                                │
│  ┌─ DeepSeek API 响应 ──────────────────────────────────┐     │
│  │ {                                                     │     │
│  │   "choices": [{                                       │     │
│  │     "finish_reason": "tool_calls",   ← 关键标识       │     │
│  │     "message": {                                       │     │
```

## 七、ChatMemory 多轮对话记忆（2026-04-28 补充）

### 7.1 为什么需要 ChatMemory

**大模型是无状态的**——每次 API 调用都是全新的，不会记住之前的对话。

```
无记忆（当前项目现状）：
  第1次：chatClient.prompt().user("查ORD-001").call()  → "ORD-001已发货"
  第2次：chatClient.prompt().user("到哪了？").call()    → "请问您想查什么？" ← AI 不知道你在说 ORD-001

有记忆（加了 ChatMemory）：
  第1次："查ORD-001" → "ORD-001已发货"
  第2次："到哪了？"   → "您刚才查的ORD-001，顺丰速运SF1234567890，预计明天送达" ← 理解上下文
```

### 7.2 Spring AI 提供的实现

| 实现 | 存储 | 适用场景 |
|------|------|----------|
| `InMemoryChatMemory` | 内存 ConcurrentHashMap | Demo/学习/单机 |
| `JdbcChatMemory` | 关系型数据库（MySQL/PG） | 生产环境，重启不丢 |

**基本用法**（InMemoryChatMemory）：

```java
// 1. 创建 ChatMemory
ChatMemory chatMemory = new InMemoryChatMemory();

// 2. 每次请求前把历史对话加载到 prompt
List<Message> history = chatMemory.get("conversationId", ChatClient.DEFAULT_CALL_OPTIONS.maxTokens());
chatClient.prompt()
    .system("你是电商客服...")
    .messages(history)          // ← 加载历史消息
    .user(message)              // ← 当前用户消息
    .call()
    .content();

// 3. 请求完成后保存本次对话到 memory
chatMemory.add("conversationId", userMessage);
chatMemory.add("conversationId", assistantMessage);
```

### 7.3 核心原理（面试必问）

**ChatMemory 本质就是消息列表的 CRUD**：

```
conversationId = "user-123"（区分不同用户的对话）
  │
  ├── Message(role=system,  content="你是客服...")
  ├── Message(role=user,    content="查ORD-001")
  ├── Message(role=assistant, content="ORD-001已发货")
  ├── Message(role=user,    content="到哪了？")        ← 当前问题
  │
  └── 每次请求把这些消息全部发给 DeepSeek
      AI 看到完整上下文，所以能理解"到哪了"指 ORD-001
```

**优化点**（面试加分）：
- 消息太多会超出 Token 限制 → 需要做消息截断/摘要（保留最近 N 轮）
- `conversationId` 区分用户 → 多用户并发时各自的对话互不干扰
- 生产环境用 `JdbcChatMemory` → 数据持久化，重启不丢

## 八、Advisor 顾问链机制（2026-04-28 补充）

### 8.1 Advisor 是什么

Advisor 是 Spring AI 的**请求拦截器/增强器**，类似 Servlet Filter 或 Spring Interceptor。

```
用户请求 → Advisor 1（日志）→ Advisor 2（RAG 自动检索）→ ChatClient → AI 回答
                                                                    ↓
           ← Advisor 2（保存记忆）← Advisor 1（记录耗时）←───────────
```

**常用 Advisor**：

| Advisor | 功能 | 说明 |
|---------|------|------|
| `MessageChatMemoryAdvisor` | 自动管理对话记忆 | 不用手动加载/保存历史消息 |
| `QuestionAnswerAdvisor` | 自动 RAG 检索 | 每次提问自动做向量检索，拼接 context |
| `SafeGuardAdvisor` | 安全拦截 | 过滤敏感内容 |

### 8.2 Agent 融合 RAG 的思路

**当前项目的 Agent 和 RAG 是割裂的**（两个独立 Controller：`/agent/chat` 和 `/rag/ask`）。

**融合方案**：用 `QuestionAnswerAdvisor` + `MessageChatMemoryAdvisor` 组成 Advisor 链：

```java
// 目标架构（Day 6）
ChatClient chatClient = chatClientBuilder
    .defaultTools(orderTools)
    .defaultAdvisors(
        new MessageChatMemoryAdvisor(chatMemory),  // 自动记忆
        new QuestionAnswerAdvisor(vectorStore)       // 自动 RAG 检索
    )
    .build();

// 使用时不需要手动检索、不需要手动拼 context
chatClient.prompt()
    .system("你是电商客服...")
    .user("这个商品怎么退换货？")  // Advisor 自动检索相关文档
    .call()
    .content();
```

**对比**：

| 维度 | 当前手动方式 | Advisor 自动方式 |
|------|-------------|-----------------|
| RAG 检索 | 手动调 vectorStore.similaritySearch() | QuestionAnswerAdvisor 自动完成 |
| 上下文拼接 | 手动拼 system prompt + context | Advisor 自动注入到请求 |
| 对话记忆 | 无 | MessageChatMemoryAdvisor 自动管理 |
| 代码量 | 每个接口都要写检索逻辑 | 一次配置，全局生效 |
