## AI 核心名词速查

> 面试必知，被问到要用白话解释清楚。

| 名词 | 全称 | 一句话解释 |
|------|------|-----------|
| **LLM** | Large Language Model | 大语言模型。本质是概率模型，根据输入文本预测下一个 token。本项目用 DeepSeek-V3（通过 API 调用） |
| **Token** | - | LLM 处理文本的最小单位。中文约 1~2 个汉字 = 1 token。API 计费按 token 数量 |
| **Embedding** | - | 文本转向量。把一段话变成一组数字（如768维），语义相近的文本向量距离也近。本项目用 Ollama nomic-embed-text（768维） |
| **Vector** | - | 向量，就是一组数字。`[0.12, -0.34, 0.56, ...]` 共768个数字代表一段文本的语义 |
| **VectorStore** | - | 向量数据库，存储文本向量并支持相似度检索。本项目用 PgVectorStore（PostgreSQL + pgvector 扩展） |
| **RAG** | Retrieval-Augmented Generation | 检索增强生成。先从知识库检索相关文档，再让 LLM 基于文档回答。解决 LLM 不懂私有数据的问题 |
| **Prompt** | - | 提示词。发给 LLM 的文本指令，包含系统角色、用户问题、参考资料等 |
| **System Prompt** | - | 系统提示词。定义 LLM 的角色和行为规则，优先级高于 User Prompt |
| **Tool Calling** | - | LLM 调用 Java 方法。LLM 返回"调用某个函数"的指令，框架自动反射调用，结果喂回 LLM 继续生成 |
| **意图识别（Intent）** | - | 识别用户想做什么。如"查订单"→ query_order，"退货"→ after_sale。是路由分发的依据 |
| **置信度（Confidence）** | - | LLM 对自己判断的把握程度，0~1 的浮点数。0.95 = 很确定，0.3 = 不太确定。生产中低于阈值走兜底逻辑 |
| **Advisor** | - | Spring AI 的拦截器，类似 Servlet Filter。在 LLM 调用前后插入逻辑（如加载历史、保存回复） |
| **ChatMemory** | - | 对话记忆。存储多轮对话的历史消息，让 LLM 理解上下文。本项目用 Redis + 自定义 Repository |
| **Temperature** | - | 温度参数，0~2。越高输出越随机（有创意），越低越确定（适合结构化输出） |
| **余弦相似度** | Cosine Similarity | 衡量两个向量方向的相似程度，0~1。1=完全相同，0=完全不相关。向量检索的核心算法 |

## ⚠️ 环境必检（最重要！项目启动不了99%是这个问题）

### 你的ASUS电脑当前环境状态

| 项目 | 当前值 | Spring AI要求 | 状态 |
|------|--------|--------------|------|
| JDK | 17.0.12（java命令）/ 1.8.0_111（Maven实际使用的） | 17+ | ❌ Maven用的JDK8 |
| Maven | 3.6.3 | 3.8.6+ | ❌ 版本太旧 |
| Spring Boot | 需新建项目 | 3.4.x | ⬜ 待创建 |

### 第一步：升级Maven（必须）

你本地有3.6.0和3.6.3，都不够。下载最新版：

1. 访问 https://maven.apache.org/download.cgi
2. 下载 `apache-maven-3.9.9-bin.zip`（或最新版）
3. 解压到 `C:\software\apache-maven-3.9.9`
4. 修改环境变量 `MAVEN_HOME` → `C:\software\apache-maven-3.9.9`
5. 修改环境变量 `Path`，把maven路径指向新版本
6. 打开**新的**PowerShell窗口，验证：`mvn -version`，确认Java version显示17.x

### 第二步：确认Maven用对JDK（必须）

升级Maven后还需要确认 `JAVA_HOME` 指向JDK 17而不是JDK 8：

```powershell
# 验证
$env:JAVA_HOME
java -version
mvn -version   # 这里显示的Java version必须是17.x
```

如果 `mvn -version` 显示的Java版本还是1.8：
- 检查 `JAVA_HOME` 环境变量是否指向 `C:\software\Java\jdk1.8.0_111`
- 如果是，需要改成JDK 17的路径（你自己知道JDK 17装在哪）
- 如果不确定JDK 17路径，运行：`Get-ChildItem -Path "C:\Program Files\Java","C:\software" -Filter "jdk*17*" -Directory -Recurse -ErrorAction SilentlyContinue`

### 第三步：Maven镜像配置（国内必改）

你大概率配了阿里云镜像，确保 `settings.xml` 中：

```xml
<!-- 如果有 mirrorOf 配置，确保不是通配符拦截 -->
<mirror>
    <id>aliyunmaven</id>
    <mirrorOf>*,!spring-snapshots,!central-portal-snapshots</mirrorOf>
    <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```

关键：`mirrorOf` 必须排除 `spring-snapshots` 和 `central-portal-snapshots`。

### 第四步：验证依赖能下载

新建一个空项目测试：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>1.0.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-openai-spring-boot-starter</artifactId>
    </dependency>
</dependencies>
```

运行 `mvn dependency:resolve`，如果能下载成功，说明环境OK，可以开始Day 1了。

## Day 1：跑通第一个AI对话接口

### 目标
写一个REST接口，前端传问题，返回AI回答。跑通这一步就证明Spring AI环境OK。

### 第一步：创建项目

通过Spring Initializr创建，或手动创建Spring Boot项目，核心依赖：

```xml
<dependencies>
    <!-- Spring Boot Web -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    
    <!-- Spring AI OpenAI兼容（用于接入DeepSeek） -->
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-openai-spring-boot-starter</artifactId>
    </dependency>
</dependencies>
```

### 第二步：配置application.yml

```yaml
server:
  port: 8080

spring:
  ai:
    openai:
      api-key: sk-你的DeepSeek-API-Key
      base-url: https://api.deepseek.com
      chat:
        options:
          model: deepseek-chat
          temperature: 0.7
```

**获取API Key：**
1. 访问 https://platform.deepseek.com 注册
2. 进入"API Keys"页面创建
3. 复制到上面的配置中

### 第三步：写Controller

```java
package com.example.ai.controller;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ChatController {

    private final ChatClient chatClient;

    public ChatController(ChatClient.Builder chatClientBuilder) {
        this.chatClient = chatClientBuilder.build();
    }

    // 最简单的对话接口
    @GetMapping("/chat")
    public String chat(@RequestParam String message) {
        return chatClient.prompt()
                .user(message)
                .call()
                .content();
    }
}
```

### 第四步：验证

启动项目，访问：
```
http://localhost:8080/chat?message=你好，请介绍一下你自己
```

看到AI回复就说明环境OK了。

### 第五步：加入System Prompt（系统角色）

实际项目中，你需要让AI扮演特定角色：

## Day 2-3：RAG知识库问答系统

### 什么是RAG

```
用户提问 → 向量检索相关文档片段 → 把片段+问题一起发给大模型 → 返回答案
```

RAG解决的核心问题：大模型不知道你公司的私有数据（业务文档、产品手册、规章制度等）。
通过RAG，大模型可以基于你的私有文档回答问题。

### RAG 原理流程图（面试必画）

```
┌─────────────────────────────────────────────────────────────┐
│                      离线阶段（入库）                         │
│                                                             │
│  PDF文档 → PagePdfDocumentReader按页读取                      │
│       → TokenTextSplitter分段（每段300~500字）                 │
│       → Ollama nomic-embed-text（文本→768维向量）              │
│       → PgVectorStore 存入 PostgreSQL（文本+向量+元数据）        │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                      在线阶段（问答）                         │
│                                                             │
│  用户问题 → Ollama nomic-embed-text（问题→768维向量）          │
│       → PgVectorStore 余弦相似度检索（找最相关的3~5个片段）      │
│       → 拼装上下文（片段1 + 片段2 + ... + 用户问题）            │
│       → DeepSeek 基于上下文生成回答                             │
└─────────────────────────────────────────────────────────────┘
```

#### Embedding 与向量数据库怎么交互的？（面试高频）

**1. Embedding（文本转向量）**
- 输入一段文本，输出一个浮点数数组（如768个数字）
- 语义相近的文本，向量之间的距离也近（余弦相似度高）
- 本项目用 Ollama 本地运行 nomic-embed-text 模型，免费、不调API

```
"退货政策是什么？"  → [0.12, -0.34, 0.56, 0.78, ..., 0.23]  // 768个数字
"如何退换货？"      → [0.11, -0.32, 0.55, 0.76, ..., 0.21]  // 和上面很接近
"今天天气如何？"    → [0.89, 0.45, -0.12, 0.33, ..., -0.67] // 和上面差距很大
```

**2. 向量数据库存储**
- PostgreSQL + pgvector 扩展，每个文档片段存为一条记录
- 记录内容：原始文本 + 768维向量 + 元数据（文件名、页码等）
- pgvector 扩展提供了向量索引（IVFFlat/HNSW）和余弦相似度计算函数

**3. 向量检索**
- 用户问题 → 同样转向量 → 在数据库中找余弦相似度最高的片段
- 余弦相似度范围 0~1，越接近1表示越相关
- 本项目用相对分数过滤（top1<0.45拦截，top1-top2<0.08拦截）

#### 两个 AI 模型的分工

| 阶段 | 模型 | 作用 | 为什么不用同一个 |
|------|------|------|---------------|
| Embedding | Ollama nomic-embed-text | 文本→向量，语义匹配 | 专用 Embedding 模型更小更快，本地运行免费 |
| Chat | DeepSeek-V3 | 基于上下文生成回答 | 通用大模型，理解和生成能力更强 |

**关键点**：Embedding 模型不需要很大，但需要"语义理解"能力强。nomic-embed-text 只有几百MB，本地运行即可。

### 第二步：文档加载服务

```java
package com.example.ai.service;

import org.springframework.ai.document.Document;
import org.springframework.ai.reader.pdf.PagePdfDocumentReader;
import org.springframework.ai.transformer.splitter.TextSplitter;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.stereotype.Service;
import org.springframework.web.multipart.MultipartFile;

import java.io.File;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

@Service
public class RagService {

    private final VectorStore vectorStore;

    public RagService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    /**
     * 上传PDF文档并处理
     * 流程：PDF → 分段 → 向量化 → 存储
     */
    public String uploadDocument(MultipartFile file) throws IOException {
        // 1. 保存临时文件
        Path tempFile = Files.createTempFile("upload-", ".pdf");
        file.transferTo(tempFile.toFile());

        try {
            // 2. 读取PDF（按页读取）
            PagePdfDocumentReader reader = new PagePdfDocumentReader(tempFile.toString());
            List<Document> documents = reader.get();

            // 3. 文本分段（按Token切分，避免单段过长）
            TextSplitter splitter = new TokenTextSplitter();
            List<Document> chunks = splitter.apply(documents);

            // 4. 向量化并存储（自动调用Embedding模型 + 存入向量库）
            vectorStore.add(chunks);

            return "文档处理完成，共 " + chunks.size() + " 个文档片段已入库";
        } finally {
            // 清理临时文件
            Files.deleteIfExists(tempFile);
        }
    }
}
```

### 第三步：RAG对话接口

```java
package com.example.ai.controller;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.document.Document;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.multipart.MultipartFile;

import java.util.List;
import java.util.stream.Collectors;

@RestController
@RequestMapping("/rag")
public class RagController {

    private final ChatClient chatClient;
    private final VectorStore vectorStore;

    public RagController(ChatClient.Builder chatClientBuilder, VectorStore vectorStore) {
        this.chatClient = chatClientBuilder.build();
        this.vectorStore = vectorStore;
    }

    /**
     * 上传文档
     */
    @PostMapping("/upload")
    public String upload(@RequestParam("file") MultipartFile file) throws Exception {
        // 实际项目中注入RagService，这里简化
        Path tempFile = Files.createTempFile("upload-", ".pdf");
        file.transferTo(tempFile.toFile());

        try {
            PagePdfDocumentReader reader = new PagePdfDocumentReader(tempFile.toString());
            List<Document> documents = reader.get();
            TokenTextSplitter splitter = new TokenTextSplitter();
            List<Document> chunks = splitter.apply(documents);
            vectorStore.add(chunks);
            return "成功入库 " + chunks.size() + " 个文档片段";
        } finally {
            Files.deleteIfExists(tempFile);
        }
    }

    /**
     * RAG问答接口
     * 流程：用户提问 → 向量检索 → 拼装上下文 → AI回答
     */
    @GetMapping("/ask")
    public String ask(@RequestParam String question) {
        // 1. 向量检索：从文档中找出与问题最相关的片段
        List<Document> relevantDocs = vectorStore.similaritySearch(
            SearchRequest.builder()
                .query(question)
                .topK(5)  // 返回最相关的5个片段
                .build()
        );

        // 2. 把检索到的文档片段拼装为上下文
        String context = relevantDocs.stream()
                .map(Document::getText)
                .collect(Collectors.joining("\n\n---\n\n"));

        // 3. 让AI基于上下文回答问题
        return chatClient.prompt()
                .system("你是一个专业知识库助手。请严格基于以下参考资料回答用户问题。" +
                        "如果参考资料中没有相关信息，请明确告知用户。" +
                        "不要编造参考资料之外的内容。\n\n" +
                        "参考资料：\n" + context)
                .user(question)
                .call()
                .content();
    }
}
```

> **注意：** 上面的RagController中需要import以下包，请确保正确引入：
> ```java

> import org.springframework.ai.transformer.splitter.TokenTextSplitter;

> import java.nio.file.Path;
> ```

### RAG 调参经验（实测总结）

#### 1. Document.score 的本质

`Document.score` 是余弦相似度，范围 0~1，越高越相关。  
但 nomic-embed-text 作为通用模型，**完全无关的内容也可能得到 0.5~0.65 的分数**（如"天气"这类领域外问题），不能用分数高低简单判断"有没有答案"。

#### 2. 为什么一个 threshold 无法适配所有问题

| 情况 | 分数范围（nomic-embed-text 中文） |
|------|--------------------------------|
| 高度相关 | 0.65 ~ 0.85 |
| 主题相近但不是答案 | 0.45 ~ 0.65 |
| 完全无关（同语言噪声） | **0.35 ~ 0.62** ← 问题所在 |

不同问题的分数分布区间不同，"退货时限"真答案分数 0.68，用 threshold=0.6 就够；"如何申请专利"无关 chunk 也达 0.62，需要 threshold=0.7 才能拦住。无法对所有问题设一个统一阈值。

#### 3. 文档切割才是根本

> **切割质量决定检索质量的上限，参数调优只是在上限范围内微调。**

| 文档类型 | 推荐粒度 | chunk 大小 |
|---------|---------|-----------|
| FAQ / 规则类 | 每条规则一个 chunk | 100~200 字 |
| 技术文档 | 每个小节（h3 级别） | 300~500 字 |
| 长文 / 报告 | 每段 + overlap | 300 字 + 50 字重叠 |

**核心原则：一个 chunk = 一个语义单元**（自包含、语义聚焦、被问到时能完整回答）

#### 4. 相对分数过滤（进阶方案，适合生产）

绝对阈值的替代方案：先宽网捞候选（topK=5, threshold=0.3），再用相对判断：

```java
private List<Document> filterByRelativeScore(List<Document> docs) {
    if (docs.isEmpty()) return docs;
    double top1 = docs.get(0).getScore() != null ? docs.get(0).getScore() : 0.0;

    // 绝对值兜底：top1 不到 0.45，整体无相关内容
    if (top1 < 0.45) return Collections.emptyList();

    // 无区分度检测：top1 vs top2 差距不足，说明所有 chunk 得分相近（无明确答案）
    if (docs.size() >= 2) {
        double top2 = docs.get(1).getScore() != null ? docs.get(1).getScore() : 0.0;
        if ((top1 - top2) < 0.08 && top1 < 0.70) return Collections.emptyList();
    }

    // 只保留与 top1 分差在 15% 以内的 chunk
    double minScore = top1 * 0.85;
    return docs.stream()
        .filter(d -> d.getScore() != null && d.getScore() >= minScore)
        .collect(Collectors.toList());
}
```

> **注意**：相对过滤也有误杀风险——知识库里只有一个勉强相关的 chunk 时，top1 偏低但差值大，可能被漏掉。无银弹，需结合业务场景评估。

#### 5. 面试怎么说

> "我们发现 nomic-embed-text 在中文场景下，领域外问题的 chunk 分数也会虚高到 0.6+，单靠全局 threshold 不稳定。最终采用相对分数过滤：先宽网捞候选，再看 top1 和 top2 的差值判断是否有明确答案，比单纯调参更鲁棒。根本上还是要优化文档切割质量。"

## Day 3-4：结构化输出（Structured Output）

### 是什么

让 LLM 返回的不是一段文字，而是 **Java 对象（JSON）**。

```
用户："帮我查一下订单ORD-001的物流"
     ↓
LLM 返回：{"intent":"query_order","params":"{\"orderId\":\"ORD-001\"}","confidence":0.95}
     ↓
Java 反序列化：IntentRecord(intent=query_order, params={"orderId":"ORD-001"}, confidence=0.95)
```

### 为什么需要

| 场景 | 文字回复 | 结构化输出 |
|------|---------|-----------|
| 意图识别 | "我想查订单" | `IntentRecord(intent=query_order)` |
| 表单填充 | "我叫张三，住深圳" | `FormRecord(name=张三, city=深圳)` |
| 路由分发 | 需要正则匹配 | 直接用 intent 字段 switch |

**核心价值：前端 / 下游系统不需要解析自然语言，直接拿到结构化数据。**

### Spring AI 1.0.5 的做法

> **注意**：Spring AI 1.1.0 才引入 `BeanOutputConverter` + `entity(Class)` API。
> 1.0.5 里这些 API 不存在，需要手动处理。

最稳妥的方案：**让 LLM 返回 JSON 字符串，用 Jackson 手动反序列化**。

#### 第一步：定义 record

```java
// IntentRecord.java
public record IntentRecord(
    String intent,       // 意图类型
    String params,       // 提取的参数（JSON 字符串）
    double confidence,   // 置信度 0~1
    String userMessage   // 原始用户消息
) {}
```

#### 第二步：Controller 中使用

```java
@GetMapping("/analyzeIntent")
public IntentRecord analyzeIntent(@RequestParam String message) {
    // 1. 构造 system prompt，明确要求返回 JSON
    String systemPrompt = "你是意图识别模块。分析用户消息，返回严格的 JSON 对象。"
            + "只返回 JSON，不要有任何其他文字。";

    // 2. 调用 LLM，拿到 JSON 字符串
    String jsonResponse = chatClient.prompt()
            .system(systemPrompt)
            .user(message)
            .call()
            .content();

    // 3. 清洗（LLM 可能返回 ```json ... ``` 包装）
    String cleaned = jsonResponse.trim();
    if (cleaned.startsWith("```")) {
        cleaned = cleaned.substring(cleaned.indexOf('{'));
        cleaned = cleaned.substring(0, cleaned.lastIndexOf('}') + 1);
    }

    // 4. Jackson 反序列化为 Java 对象
    ObjectMapper mapper = new ObjectMapper();
    return mapper.readValue(cleaned, IntentRecord.class);
}
```

#### 第三步：调用验证

```
GET http://localhost:8080/agent/analyzeIntent?message=帮我查一下订单ORD-001的物流

返回（Spring Boot 自动转为 JSON）：
{
  "intent": "query_order",
  "params": "{\"orderId\":\"ORD-001\"}",
  "confidence": 0.95,
  "userMessage": "帮我查一下订单ORD-001的物流"
}
```

### 结构化输出 vs Tool Calling 的区别

| 维度 | 结构化输出 | Tool Calling |
|------|-----------|-------------|
| 谁决定输出格式 | 开发者定义 | LLM 根据 @Tool 定义自动生成 |
| 适用场景 | 返回值给调用方 | 返回值给 LLM 自己继续处理 |
| 可靠性 | 中（LLM 可能不按格式） | 高（框架强制 JSON Schema） |
| 代码位置 | Controller / Service 层 | @Tool 方法内 |

> **一句话**：Tool Calling 是"AI 调你的方法"，结构化输出是"AI 返回数据给你"。

### 面试怎么说

> "结构化输出本质是 Prompt Engineering + JSON 反序列化。在 prompt 里明确要求返回 JSON，然后用 Jackson 解析。需要处理 LLM 不规范输出的边界情况（如 markdown 包装）。Spring AI 1.1.0 有 `entity(Class)` API 自动处理，但 1.0.x 需要手动做。另外要注意，做结构化输出必须用纯净的 ChatClient（不挂载工具），否则 LLM 会优先调工具而不返回 JSON。"

### ⚠️ 踩坑记录：Tool Calling 导致 JSON 格式失效

#### 现象

`/agent/analyzeIntent` 调用 DeepSeek 后返回的是完整客服回复（含表格、emoji、物流信息），不是 JSON。

#### 根因

`ChatClient` 挂载了 `OrderTools` 后，**Tool Calling 的优先级高于 system prompt 指令**。

不是 DeepSeek 不听话，是 LLM 的推理链路决定的：
1. 收到用户消息 + 可用工具列表
2. 判断：这个问题用工具能解决 → **直接调工具**
3. 拿到工具结果 → 生成最终回答
4. **根本不会去管 system prompt 里写的"只返回JSON"**

##### 底层原理：为什么 tools 优先级最高？

这是 OpenAI 在 2023 年定义 Function Calling 时确定的协议规范，所有兼容模型（DeepSeek/GPT/Claude）都遵循：

```
tools 声明存在 > system prompt 指令 > user prompt 指令
```

当 API 请求中包含 `tools` 字段，模型推理时会**先评估是否需要调用工具**，这个决策发生在 prompt 文本理解之前。如果 prompt 能阻止工具调用，整个 Tool Calling 机制就失效了——所以这不是 bug，是设计。

#### ChatClient.Builder 是可变对象（重要）

`ChatClient.Builder` 的 `.defaultTools()` **修改的是自身**，不是创建新对象：

```java
// defaultTools() 源码本质：
public Builder defaultTools(Object... tools) {
    this.defaultToolNames = resolveToolNames(tools);
    return this; // ← 返回自身，不是新对象！
}
```

所以**不是两个 build 互相干扰，而是 Builder 被第一次配置污染了，后续所有 build 都继承了这个配置**：

```java
ChatClient.Builder builder = chatClientBuilder; // Spring 注入的同一个实例

// 第一次 build：给 builder 加了工具
this.chatClient = builder
    .defaultTools(orderTools)   // ← 修改了 builder 自身的状态
    .build();

// 第二次 build：builder 上已经有工具了！
this.jsonOnlyClient = builder.build(); // ← 等同于 builder.defaultTools(orderTools).build()
```

而 `ChatClient.builder(chatModel)` 是**工厂方法**，每次调用都创建全新 Builder 实例，完全隔离。

#### 两种构造方式的底层区别

| 维度 | `builder.defaultTools().build()` | `ChatClient.builder(chatModel).build()` |
|------|--------------------------------|----------------------------------------|
| Builder 来源 | Spring 容器注入的**同一个**实例 | 工厂方法每次创建**全新**实例 |
| 内部状态 | 共享（可变对象） | 独立（全新对象） |
| 构造出的 ChatClient | 携带 Builder 上的所有配置 | 只携带 `ChatModel`（最底层），无任何装饰 |
| 底层调用链 | Builder → (有 tools + advisors) → ChatModel → HTTP → DeepSeek | Builder → (无任何配置) → ChatModel → HTTP → DeepSeek |

**最终区别 = 发给 DeepSeek 的 HTTP 请求体不同：**

```json
// chatClient 的请求（带 tools 字段，触发工具调用模式）
{
  "model": "deepseek-chat",
  "messages": [{"role": "system", "content": "..."}],
  "tools": [{"type": "function", "function": {"name": "queryOrder", "parameters": {...}}}]
}

// jsonOnlyClient 的请求（无 tools 字段，纯文本生成模式）
{
  "model": "deepseek-chat",
  "messages": [{"role": "system", "content": "..."}]
}
```

DeepSeek API 收到带 `tools` 的请求，推理模式切换为"工具调用模式"；没收到 `tools`，就是普通文本生成模式。**这就是最底层的区别。**

#### 关键名词解释

| 名词 | 全称 | 解释 |
|------|------|------|
| **LLM** | Large Language Model | 大语言模型。本项目用 DeepSeek-V3（通过 API 调用），本质是一个概率模型，根据输入文本预测下一个 token |
| **intent（意图类型）** | - | 用户这句话想做什么。如"查订单"→ query_order，"退货"→ after_sale。是路由分发的依据 |
| **confidence（置信度）** | - | LLM 对自己判断的把握程度，0~1 的浮点数。0.95 = 很确定，0.3 = 不太确定。生产中低于阈值走兜底逻辑 |
| **Tool Calling** | - | 让 LLM 返回"调用某个函数"的指令（JSON Schema 格式），框架自动反射调用 Java 方法，把结果喂回 LLM 继续生成 |

#### 两种 ChatClient 方式对比

| | `chatClient`（带工具） | `jsonOnlyClient`（纯净） |
|---|---|---|
| 构造方式 | `builder.defaultTools(orderTools).build()` | `ChatClient.builder(chatModel).build()` |
| 有无工具 | 有 OrderTools | 无 |
| LLM 行为 | 优先判断是否调工具 | 只做文本生成，不调工具 |
| 适用场景 | Agent / `/agent/chat` | 结构化输出 / `/agent/analyzeIntent` |
| prompt 遵从度 | 低（工具优先级高） | 高（只做文本任务） |

**核心结论：做结构化输出，必须用纯净 Client，不能挂工具。**

#### 怎样提高 LLM 对 prompt 指令的遵从度

| 手段 | 效果 | 说明 |
|------|------|------|
| **不用工具（最有效）** | ★★★★★ | 根本解决，发给 DeepSeek 的请求里没有 `tools` 字段 |
| **system prompt 放第一条** | ★★★★ | LLM 对第一条 system message 的权重最高 |
| **JSON Schema 示例** | ★★★★ | 直接在 prompt 里给出完整 JSON 示例，比说"返回JSON"强10倍 |
| **明确禁止事项** | ★★★ | "禁止调用工具/禁止解释/只返回JSON" |
| **降低 temperature** | ★★★ | temperature=0 时输出更确定性，减少发散 |
| **多次重试** | ★★ | 第一次返回不规范就重试，但不治本 |

#### LLM 返回格式不可控的 6 种常见原因

| # | 原因 | 说明 | 解决方案 |
|---|------|------|---------|
| 1 | ChatClient 挂载了工具 | LLM 优先调工具，忽略格式指令 | 用 `ChatClient.builder(chatModel)` 创建纯净 client |
| 2 | system prompt 约束不够强 | LLM 自作主张加解释、表格、emoji | prompt 中明确列出 JSON Schema + 禁止事项 |
| 3 | 返回被 markdown 包裹 | ` ```json ... ``` ` | 清洗：去掉 ` ``` ` 标记 |
| 4 | 返回带前后文 | `"结果是：{...}"` | 截取：第一个 `{` 到最后一个 `}` |
| 5 | ChatMemory 污染 | 历史对话影响本轮格式 | 结构化输出不用 ChatMemory |
| 6 | 模型遵从度差 | 早期模型更明显 | 换用更强的模型（DeepSeek-V3 > GPT-3.5） |

#### 面试怎么说

> "我们遇到过结构化输出失效的问题。根因是 ChatClient.Builder 是可变对象，defaultTools() 会污染 Builder，导致所有 build() 出来的 Client 都带工具。而 DeepSeek 收到带 tools 的 HTTP 请求后，会进入工具调用模式，此时 tools 的优先级高于 system prompt，所以'只返回JSON'的指令被忽略了。解决方案是用 `ChatClient.builder(chatModel)` 工厂方法创建全新隔离的纯净 Client。本质上两种 Client 发给 DeepSeek 的 HTTP 请求体不同——一个有 tools 字段，一个没有。"

## Day 4-6：Tool Calling智能体

### 什么是Tool Calling

让大模型能**调用你写的Java方法**。

```
用户："帮我查一下订单 ORD-001 的状态"
     ↓
第1次请求 DeepSeek：用户消息 + 工具定义（JSON Schema）
     ↓
DeepSeek 返回 tool_calls（不是文本）：调用 queryOrder("ORD-001")
     ↓
Spring AI 自动反射调用本地 Java 方法 OrderTools.queryOrder("ORD-001")
     ↓
第2次请求 DeepSeek：工具执行结果（JSON）作为 tool 角色消息
     ↓
DeepSeek 生成自然语言回答："订单 ORD-001 已发货，顺丰速运..."
```

这就是智能体的核心能力：AI自主决定何时调用什么工具。

### ⚠️ 重要：Spring AI 1.0.x Tool Calling API 重大变更

网上大量教程（含B站徐庶那套）使用的是 0.x 旧写法，**在 1.0.x 中已废弃**。

| 维度 | 旧写法（0.x，会报错） | 新写法（1.0.x，正确） |
|------|------------------------|---------------------|
| 类注解 | `@Configuration` | `@Component` |
| 方法声明 | `@Bean @Description("...") public Function<Req, Resp>` | `@Tool(description="...") public Resp` |
| 注册工具 | `defaultTools("beanName")` | `defaultTools(toolInstance)` |
| 参数方式 | 必须包装成 Request record | 直接写方法参数 |

> 旧写法报错：`No @Tool annotated methods found in xxx. Did you mean to pass a ToolCallback?`

### 第一步：定义Tool（1.0.x 新写法）

```java
package com.example.ai.tool;

import org.springframework.ai.tool.annotation.Tool;
import org.springframework.stereotype.Component;

/**
 * 订单相关工具集
 * @Tool 的 description 是 AI 决定是否调用的依据，要写清楚"什么情况下用"
 */
@Component
public class OrderTools {

    @Tool(description = "根据订单号查询订单的当前状态、收货地址、物流信息。当用户询问订单状态、物流进度、订单详情时调用此工具。")
    public OrderQueryResponse queryOrder(String orderId) {
        // 直接写逻辑，实际项目中注入 Service 调用业务层
        OrderQueryResponse response = new OrderQueryResponse();
        response.setOrderId(orderId);
        if ("ORD-001".equals(orderId)) {
            response.setStatus("已发货");
            response.setLogistics("顺丰速运 SF1234567890");
            response.setEstimatedDelivery("明天14:00前");
            response.setAddress("深圳市南山区科技园XX号");
        } else {
            response.setStatus("未找到该订单");
        }
        return response;
    }
}
```

### 第二步：定义响应对象

```java
// 用普通类或 record 都行，AI会自动序列化/反序列化
public class OrderQueryResponse {
    private String orderId;
    private String status;
    private String logistics;
    private String estimatedDelivery;
    private String address;
    // getter/setter 省略

### 第三步：在Controller中注册Tool

```java
package com.example.ai.controller;

import com.example.ai.tool.OrderTools;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/agent")
public class AgentController {

    private final ChatClient chatClient;

    // 注入 OrderTools 实例
    public AgentController(ChatClient.Builder chatClientBuilder, OrderTools orderTools) {
        this.chatClient = chatClientBuilder
                .defaultTools(orderTools)   // 传实例，Spring AI 自动扫描 @Tool 方法
                .build();
    }

    @GetMapping("/chat")
    public String chat(@RequestParam String message) {
        return chatClient.prompt()
                .system("你是一个电商智能客服助手。" +
                        "你可以帮助用户查询订单状态、推荐商品、处理售后问题。" +
                        "当用户提到订单号或订单相关问题时，使用工具查询订单信息后再回答。")
                .user(message)
                .call()
                .content();
    }
}
```

## Advisor 原理与链路

### 是什么

Advisor 是 Spring AI 的**拦截器机制**，类似 Servlet Filter 或 Spring Interceptor。在 LLM 调用前后插入自定义逻辑。

### 类比理解（重要！）

**类比1：Servlet Filter（Java Web 开发者最熟悉）**
```
浏览器请求 → Filter1.doFilter() → Filter2.doFilter() → Servlet → Filter2 → Filter1 → 响应
每个 Filter 可以修改 request/response，也可以选择不调 chain.doFilter() 拦截请求
```

**类比2：Express Middleware（Node.js）**
```javascript
app.use((req, res, next) => { console.log('请求来了'); next(); });
app.use((req, res, next) => { req.user = '张三'; next(); });
app.get('/api', (req, res) => { res.json({ user: req.user }); });

**Advisor = ChatClient 的 Filter/中间件**
```
用户请求 → Advisor1.before → Advisor2.before → ChatModel(调LLM) → Advisor2.after → Advisor1.after → 返回用户
```

**关键区别**：Servlet Filter 拦截 HTTP 请求，Advisor 拦截 LLM 调用。本质一样，都是**在主逻辑前后插入自定义处理**。

### Spring AI 1.0.5 的 Advisor API（踩坑记录）

> **注意**：网上大量教程用的是 0.x 旧 API（`RequestAdvisor`、`ResponseAdvisor`），在 1.0.x 中**已改名**。

| 概念 | 旧 API（0.x，会报错） | 新 API（1.0.x，正确） |
|------|------------------------|---------------------|
| 拦截器接口 | `RequestAdvisor` / `ResponseAdvisor` | `CallAdvisor`（阻塞模式）/ `StreamAdvisor`（流式） |
| 基类 | 无 | `BaseAdvisor`（同时支持阻塞和流式） |
| 包路径 | 无 | `org.springframework.ai.chat.client.advisor.api` |
| 实现方法 | `before()` / `after()` | `before(request, chain)` / `after(response, chain)` |
| 必须实现 | `before()` | `before()` + `after()` + `getOrder()` |

**正确的做法**：实现 `BaseAdvisor` 接口，它继承自 `CallAdvisor` + `StreamAdvisor`，默认的 `adviseCall()` 方法已经帮你编排了 `before → chain.nextCall → after` 链路，你只需要实现 `before()` 和 `after()` 即可。

### 自定义 RAG Advisor 完整代码

```java
package com.example.ai.advisor;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.ai.chat.client.ChatClientRequest;
import org.springframework.ai.chat.client.ChatClientResponse;
import org.springframework.ai.chat.client.advisor.api.AdvisorChain;
import org.springframework.ai.chat.client.advisor.api.BaseAdvisor;
import org.springframework.ai.document.Document;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.VectorStore;

import java.util.Collections;
import java.util.List;
import java.util.stream.Collectors;

/**
 * 自定义 RAG Advisor
 * 实现 BaseAdvisor 接口（框架已默认编排 before → chain.nextCall → after）
 * 在 before 阶段做向量检索，把相关文档片段注入 system prompt
 */
@Slf4j
@RequiredArgsConstructor
public class CustomRagAdvisor implements BaseAdvisor {

    private final VectorStore vectorStore;
    private final int topK;
    private final double threshold;

    @Override
    public ChatClientRequest before(ChatClientRequest request, AdvisorChain chain) {
        // 1. 从 prompt 拿到用户消息
        String userMessage = request.prompt().getUserMessage() != null
                ? request.prompt().getUserMessage().getText() : "";
        if (userMessage.isBlank()) return request;

        // 2. 向量检索
        List<Document> docs = vectorStore.similaritySearch(
                SearchRequest.builder()
                        .query(userMessage)
                        .topK(topK)
                        .similarityThreshold(threshold)
                        .build()
        );
        if (docs == null || docs.isEmpty()) return request;

        // 3. 相对分数过滤
        docs = filterByRelativeScore(docs);
        if (docs.isEmpty()) return request;

        // 4. 用 augmentSystemMessage() 追加上下文到 system prompt
        String context = docs.stream()
                .map(Document::getText)
                .collect(Collectors.joining("\n\n---\n\n"));

        return request.mutate()
                .prompt(request.prompt().augmentSystemMessage(
                        "\n\n参考资料：\n" + context))
                .build();
    }

    @Override
    public ChatClientResponse after(ChatClientResponse response, AdvisorChain chain) {
        return response;
    }

    @Override
    public int getOrder() {
        return 0;
    }

    /** 相对分数过滤（同 RagService.filterByRelativeScore） */
    private List<Document> filterByRelativeScore(List<Document> docs) { /* ... */ }
}

// 构造函数：注册完整 Advisor 链
public AgentController(ChatClient.Builder chatClientBuilder,
                      OrderTools orderTools,
                      ChatMemory chatMemory,
                      ChatModel chatModel,
                      VectorStore vectorStore) {

    // 纯净 Client（无工具/无记忆，专用于结构化输出）
    this.jsonOnlyClient = ChatClient.builder(chatModel).build();

    // 带 Advisor 链的 Client（Tool Calling + ChatMemory + RAG）
    this.chatClient = chatClientBuilder
            .defaultTools(orderTools)
            .defaultAdvisors(
                    MessageChatMemoryAdvisor.builder(chatMemory).build(),
                    new CustomRagAdvisor(vectorStore, 3, 0.3)
            )
            .build();
}

@GetMapping("/chat")
public String chat(@RequestParam String conversationId,
                   @RequestParam String message) {
    return chatClient.prompt()
            .system("你是一个电商智能客服助手。")
            .user(message)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
            .call()
            .content();
}

### 关键 API 速查

| API | 作用 | 示例 |
|-----|------|------|
| `request.prompt()` | 获取 Prompt 对象 | `prompt.getUserMessage()` |
| `prompt.getUserMessage()` | 获取用户消息 | `.getText()` 拿文本 |

### 原生写法 vs Advisor 链对比

| 维度 | 原生写法（手动编排） | Advisor 链（封装后） |
|------|---------------|-----------------|
| RAG 检索 | Controller 手动调用 `ragService` | Advisor 自动检索并注入 |
| 代码复杂度 | Controller 30+ 行 | Controller 5 行 |
| 可复用性 | 每个接口都要写一遍 | 注册一次全局生效 |
| 相对分数过滤 | 每次手动调用 | Advisor 内部自动处理 |
| 灵活性 | 可以针对不同接口定制 | 统一处理，特殊需求需绕过 |

**建议**：两种写法都要会。面试时先说原生写法（证明你懂底层），再说 Advisor 链（证明你懂框架设计）。

> "Advisor 是 Spring AI 的拦截器机制，类似 Servlet Filter。它可以在 LLM 调用前后插入自定义逻辑。
>
> Spring AI 1.0.5 的 Advisor API 需要实现 `BaseAdvisor` 接口（在 `org.springframework.ai.chat.client.advisor.api` 包下），它继承自 `CallAdvisor` 和 `StreamAdvisor`。只需要实现 `before(request, chain)` 和 `after(response, chain)` 两个方法。框架的默认 `adviseCall()` 会自动编排 `before → chain.nextCall → after` 链路。

## ChatMemory 对话记忆

### 是什么

让 AI 能记住之前的对话内容，实现多轮对话。用户说"到哪了"，AI 能理解是问上一个订单。

### 两种策略对比

| 维度 | 滑动窗口（当前实现） | 摘要压缩（进阶方案） |
|------|-------------------|-------------------|
| 策略 | 保留最近 N 条，丢弃最早的 | 把旧消息用 LLM 压缩为摘要 |
| 代码 | `MessageWindowChatMemory.builder().maxMessages(20).build()` | 需自研：定时触发 LLM 压缩 |
| Token 消耗 | 固定（最多 N 条历史） | 更低（摘要比原文短很多） |
| 信息保留 | 早期上下文完全丢失 | 保留早期关键信息（摘要） |
| 额外成本 | 无 | 每次压缩需调 LLM（有 API 成本） |
| Spring AI 原生 | ✅ `MessageWindowChatMemory` | ❌ 不支持，需自研 |
| 适用场景 | 短对话（客服、命令执行） | 长对话（项目讨论、知识问答） |

### 当前实现：Redis + 滑动窗口

```
Redis Key: chat:memory:{conversationId}
Redis Value: List<Message>（JSON 序列化）

每次请求：
1. Advisor 从 Redis 加载最近 20 条消息 → 注入 Prompt
2. DeepSeek 生成回复
3. Advisor 把用户消息 + AI 回复 追加到 Redis
4. 如果超过 20 条，最早的被丢弃（FIFO）
```

### 进阶方案：摘要压缩（代码实现）

#### 设计思路

```
消息数超过 MAX_MESSAGES（如20）时触发压缩：
  旧消息（第1~10条）→ jsonOnlyClient → LLM 压缩 → 摘要（1条 SystemMessage）
  摘要 + 最近10条原始消息 → 继续保留在 Redis

效果：
  压缩前：20条消息 × 平均 50 token = 1000 token
  压缩后：1条摘要（约100 token）+ 10条消息（500 token）= 600 token
```

**关键设计决策**：

| 决策 | 选择 | 原因 |
|------|------|------|
| 摘要用什么 Client | `jsonOnlyClient`（纯净，无工具） | 避免 Tool Calling 干扰文本生成 |
| 摘要用什么角色 | `SystemMessage` | 摘要是背景信息，不是对话轮次 |
| 压缩时机 | 消息入库后超阈值即压缩 | 下次请求前历史已就绪，不影响响应延迟 |
| 是否异步 | 可选异步（`@Async`） | 压缩耗时约200~500ms，建议异步不阻塞主链路 |

#### 第一步：SummarizingChatMemory（核心类）

```java
package com.example.ai.memory;

import lombok.extern.slf4j.Slf4j;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.ai.chat.messages.Message;
import org.springframework.ai.chat.messages.MessageType;
import org.springframework.ai.chat.messages.SystemMessage;
import org.springframework.scheduling.annotation.Async;

import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;

/**
 * 带摘要压缩的 ChatMemory（装饰器模式）
 * 当对话历史超过 MAX_MESSAGES 时，把前半段消息用 LLM 压缩成摘要
 */
@Slf4j
public class SummarizingChatMemory implements ChatMemory {

    // 最大消息数，超过触发压缩
    private static final int MAX_MESSAGES = 20;
    // 保留最近消息数
    private static final int KEEP_RECENT = 10;

    // 被装饰的底层对象（MessageWindowChatMemory，底层是 Redis 存储）
    private final ChatMemory delegate;
    // 纯净 ChatClient（无工具，专门用于 LLM 压缩）
    private final ChatClient summaryClient;

    public SummarizingChatMemory(ChatMemory delegate, ChatClient summaryClient) {
        this.delegate = delegate;
        this.summaryClient = summaryClient;
    }

    @Override
    public void add(String conversationId, List<Message> messages) {
        // 先写入底层存储
        delegate.add(conversationId, messages);
        // 写入后检查是否需要压缩
        triggerCompressionIfNeeded(conversationId);
    }

    /**
     * ChatMemory 接口 get() 只接收 conversationId，不接收 lastN。
     * 消息条数限制由底层 MessageWindowChatMemory 在 saveAll 时已裁剪好。
     */
    @Override
    public List<Message> get(String conversationId) {
        return delegate.get(conversationId);
    }

    @Override
    public void clear(String conversationId) {
        delegate.clear(conversationId);
    }

    /**
     * 触发压缩：超过 MAX_MESSAGES 时，把前半段消息压缩为摘要
     * 加 @Async 可让压缩异步执行，不阻塞主链路（需在启动类加 @EnableAsync）
     */
    @Async
    protected void triggerCompressionIfNeeded(String conversationId) {
        // 取全部消息（delegate 的 maxMessages = MAX_VALUE，返回全量）
        List<Message> all = delegate.get(conversationId);

        if (all.size() <= MAX_MESSAGES) {
            return; // 未超过阈值，不压缩
        }

        log.info("[ChatMemory] conversationId={} 消息数={}，触发摘要压缩", conversationId, all.size());

        // 需要压缩的旧消息（前半段）
        int toCompressCount = all.size() - KEEP_RECENT;
        List<Message> toCompress = all.subList(0, toCompressCount);
        // 需要保留的近期消息（后半段）
        List<Message> recent = all.subList(toCompressCount, all.size());

        // 用 LLM 生成摘要
        String summary = summarize(conversationId, toCompress);
        if (summary == null) {
            log.warn("[ChatMemory] 摘要生成失败，跳过压缩");
            return;
        }

        // 重建消息列表：摘要（1条 SystemMessage）+ 最近 N 条
        List<Message> compressed = new ArrayList<>();
        compressed.add(new SystemMessage("[对话摘要] " + summary));
        compressed.addAll(recent);

        // 清空 Redis 中旧的历史，写入压缩后的版本
        delegate.clear(conversationId);
        delegate.add(conversationId, compressed);

        log.info("[ChatMemory] 压缩完成：{}条 → {}条（摘要1条 + 近期{}条）",
                all.size(), compressed.size(), recent.size());
    }

    /**
     * 调用 LLM 生成对话摘要
     * @param messages 需要压缩的消息列表
     * @return 摘要文本，失败返回 null
     */
    private String summarize(String conversationId, List<Message> messages) {
        // 把消息列表转为文本，方便 LLM 理解
        String historyText = messages.stream()
                .map(msg -> {
                    String role = msg.getMessageType() == MessageType.USER ? "用户" : "助手";
                    return role + "：" + msg.getText();
                })
                .collect(Collectors.joining("\n"));

        String systemPrompt = """
                你是对话摘要助手。将以下对话历史压缩为简洁的摘要，保留关键信息点。
                要求：
                1. 摘要控制在100字以内
                2. 保留用户的核心诉求、已确认的事项、重要的上下文
                3. 只输出摘要文本，不要有任何前缀或解释
                """;

        try {
            String result = summaryClient.prompt()
                    .system(systemPrompt)
                    .user("请压缩以下对话历史：\n" + historyText)
                    .call()
                    .content();
            log.info("[ChatMemory] conversationId={} 摘要结果：{}", conversationId, result);
            return result != null ? result.trim() : null;
        } catch (Exception e) {
            log.error("[ChatMemory] LLM 摘要生成失败", e);
            return null;
        }
    }
}
```

#### ⚠️ 注意事项

| 问题 | 说明 |
|------|------|
| LLM 压缩成本 | 每次压缩消耗约 500~1000 token（输入旧消息 + 输出摘要）。DeepSeek 费用极低，约 ¥0.001 |
| 并发安全 | 同一会话并发请求时可能触发多次压缩。生产环境需加分布式锁（Redis `SETNX`）|
| 摘要质量 | temperature 建议设为 0（确定性输出），摘要更准确 |
| 调试 | 日志级别设 DEBUG 可看到每次压缩前后的消息数和摘要内容 |

#### 会话摘要的本质

> 摘要生成本质上就是一次普通的大模型对话调用（`summaryClient.prompt().call()`），跟 `/chat` 接口里调用 DeepSeek 没有区别。区别只在于：用的是纯净 Client（无工具、无 Advisor），system prompt 要求"压缩对话为摘要"，输入是旧消息拼接成的文本，输出是一段自然语言摘要。

#### 装饰器模式（Decorator Pattern）

对这个设计模式不熟悉？一张图说清楚。

**核心思想：不改原有代码，套一层外壳增加新功能。**

```
         调用方（AgentController）
                   │
                   │ ChatMemory 接口（add/get/clear）
                   ▼
     ┌─────────────────────────────┐
     │  SummarizingChatMemory      │  ← 外壳（装饰器）
     │  新增能力：触发摘要压缩         │
     │  ┌────────────────────────┐ │
     │  │ delegate（被装饰的对象）│ │
     │  │ MessageWindowChatMemory│ │  ← 原有对象
     │  │   └── Redis 存储        │ │
     │  └────────────────────────┘ │
     └─────────────────────────────┘
```

**类比：USB 读卡器**
- 原来的 SD 卡（`MessageWindowChatMemory`）只能存取消息
- USB 读卡器（`SummarizingChatMemory`）套在外面，多了"触发压缩"的能力
- 外部设备（`AgentController`）只认 USB 接口（`ChatMemory`），不用管里面是什么

**为什么不用继承？**

```java
// 错误方式：继承
public class SummarizingChatMemory extends MessageWindowChatMemory {
    // 问题：MessageWindowChatMemory 没有 public 构造方法（只有 Builder），无法继承
    // 而且继承绑死了具体实现，换存储就得改代码
}

// 正确方式：装饰器（面向接口编程）
public class SummarizingChatMemory implements ChatMemory {
    private final ChatMemory delegate;  // ← 持有接口引用，不关心具体实现
    // 好处：把 MessageWindowChatMemory 换成 InMemoryChatMemory，这里零改动
}
```

**三层分工**：

| 层 | 类 | 职责 |
|----|-----|------|
| 装饰器层 | `SummarizingChatMemory` | 摘要压缩触发逻辑（只干这一件事） |
| 窗口管理层 | `MessageWindowChatMemory` | 消息条数限制、滑动窗口 |
| 存储层 | `RedisChatMemoryRepository` | Redis 读写（只干持久化这一件事） |

**单一职责**：每层只干一件事，互不耦合。这就是装饰器模式的价值。

### 面试怎么说

> "ChatMemory 用于多轮对话记忆。我们实现了两种方案：
>
> **第一种是滑动窗口**，用 `MessageWindowChatMemory` 保留最近20条消息，超过就丢弃最早的。好处是简单无额外成本，缺点是早期上下文完全丢失。存储用 Redis，自定义了 `ChatMemoryRepository` 接口，因为 Spring AI 原生不支持 Redis 存储。
>
> **第二种是摘要压缩**——自研了 `SummarizingChatMemory`，实现了 `ChatMemory` 接口，用装饰器模式包装了 Redis 存储。当消息数超过20条时，触发 LLM 压缩：把前10条消息发给纯净 ChatClient，生成一段100字以内的摘要，用摘要替换旧消息，保留摘要 + 最近10条原始消息。压缩逻辑用 `@Async` 异步执行，不阻塞主对话链路。Spring AI 没有内置支持，这块是我们自研的。
>
> 另一个踩坑是结构化输出不能用带 ChatMemory 的 ChatClient，历史对话会污染 JSON 格式输出。所以维护了两个 ChatClient：带 Memory 的用于 Agent 对话，纯净的 `jsonOnlyClient` 用于结构化输出。"

## 多格式文档支持

### 问题

目前知识库只支持 PDF，但实际业务中文档格式多样：Word、Excel、PPT、HTML、Markdown、TXT 等。

### 核心概念：DocumentReader 统一接口

Spring AI 提供了 `DocumentReader` 接口，所有文档解析器都实现这个接口，返回统一的 `List<Document>`。

```
DocumentReader（接口）
├── PagePdfDocumentReader    → PDF（按页读取，中文排版保留好）
├── ParagraphPdfDocumentReader → PDF（按段落读取，适合纯文本文档）
├── TikaDocumentReader       → Word/Excel/PPT/TXT/HTML 等（Apache Tika 通用解析）
├── JsonReader               → JSON
└── TextReader               → 纯文本 / Markdown
```

**所有 Reader 的返回值都是 `List<Document>`**，后续的 TokenTextSplitter 分段和 VectorStore 入库完全不用改。

### 为什么 PDF 不用 Tika？

| 对比 | PagePdfDocumentReader | TikaDocumentReader |
|------|----------------------|-------------------|
| 按页切割 | ✅ 天然按页 | ❌ 纯文本流，丢失页面结构 |
| 中文排版 | ✅ 表格、标题保留 | ⚠️ 可能丢失格式 |
| 表格解析 | ⚠️ 文本保留但非结构化 | ❌ 直接丢失表格结构 |
| 多格式支持 | ❌ 仅 PDF | ✅ 几十种格式 |

**结论**：PDF 单独用 PagePdfDocumentReader，其他格式走 Tika。

### Maven 依赖

```xml
<!-- PDF 专用 Reader（已有） -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-pdf-document-reader</artifactId>
</dependency>

<!-- Tika 通用 Reader（新增） -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-tika-document-reader</artifactId>
</dependency>
```

> 版本由 `spring-ai-bom` 统一管理，不需要写 `<version>`。

### Tika 是什么？

Apache Tika 是一个内容检测和提取工具包，能自动识别文件类型并提取文本内容。

```
TikaDocumentReader 内部流程：
文件输入 → Tika 检测 MIME 类型 → 选择对应解析器 → 提取纯文本 → 返回 List<Document>

支持的格式（部分）：
.doc  .docx  .xls  .xlsx  .ppt  .pptx
.txt  .html  .htm  .md   .csv   .json   .xml
.rtf  .odt   .ods  .odp
```

### 代码实现：RagService 多格式支持

```java
// 根据文件扩展名选择 Reader
private DocumentReader createReader(Path file, String extension) {
    if ("pdf".equals(extension)) {
        // PDF：PagePdfDocumentReader（按页读取，中文排版保留好）
        return new PagePdfDocumentReader(new FileSystemResource(file.toFile()));
    } else {
        // 其他格式：TikaDocumentReader（Apache Tika 通用解析）
        return new TikaDocumentReader(new FileSystemResource(file.toFile()));
    }
}
```

完整的 `uploadDocument` 流程：

```
1. 提取文件扩展名 → 校验是否在支持列表
2. 保存到临时目录
3. 根据扩展名选择 DocumentReader（PDF → PagePdf，其他 → Tika）
4. reader.get() → List<Document>
5. OverlappingTextSplitter 分段（带重叠，避免语义丢失） → List<Document> chunks
6. vectorStore.add(chunks) → 向量化存入 PgVector
7. 清理临时文件
```

### 文本切片：为什么需要 overlap？

**问题**：`TokenTextSplitter` 切片时没有重叠，相邻 chunk 的边界处语义会断裂。

```
无 overlap：
[chunk 1: "订单满99元包邮"] [chunk 2: "未满99元收取8元运费"]
                                    ↑ 断裂处："包邮"和"未满"被拆开，检索"运费"可能漏掉"包邮"这个前提

有 overlap（10%）：
[chunk 1: "订单满99元包邮"] [chunk 2: "满99元包邮，未满99元收取8元运费"] [chunk 3: "收取8元运费..."]
                             ↑ 重叠50 token：包含"包邮"上下文
```

**实现方案**：`OverlappingTextSplitter`（自定义 `DocumentTransformer`）

```java
// 两层切片法：粗切保语义边界，细切加 overlap
OverlappingTextSplitter splitter = new OverlappingTextSplitter(500, 0.10);
// chunkSize=500 token, overlap=10%（50 token）

// 原理：
// 第一层：TokenTextSplitter 粗切（chunkSize*2），保留句子/段落边界
// 第二层：滑动窗口细切，相邻 chunk 有 50 token 重叠
```

**参数建议**：
| 参数 | 建议值 | 说明 |
|------|--------|------|
| chunkSize | 500 | 每段最大 token 数（中文约 1000 字符） |
| overlap 比例 | 10% | 50 token 重叠，兼顾语义和存储成本 |
| 字符/token 比 | 2 | 中文保守估算（1 token ≈ 2 字符） |

> **面试怎么说**："TokenTextSplitter 不支持 overlap，切片边界会丢失上下文。
> 我实现了 OverlappingTextSplitter，用两层切片法：先用 TokenTextSplitter 粗切保语义边界，
> 再滑动窗口细切加 10% overlap，确保每个 chunk 都有前后文上下文，提高检索召回率。"

## Spring Boot 3.x 与 JDK 17

### 为什么 Spring Boot 3.x 只支持 JDK 17+？

| 原因 | 说明 |
|------|------|
| **Jakarta EE 迁移** | `javax.*` 全部改为 `jakarta.*`（如 `javax.servlet` → `jakarta.servlet`）。这是 Java EE 移交给 Eclipse 后的命名空间变更 |
| **Records** | Spring AI 的 `IntentRecord` 等 Java 14+ 特性需要 JDK 14+ |
| **Sealed Classes** | 框架内部用密封类限制继承，JDK 15+ 预览，JDK 17 正式 |
| **Pattern Matching** | `instanceof` 模式匹配（JDK 16+ 正式），减少强制转换代码 |
| **Text Blocks** | 多行字符串（JDK 15+ 正式），system prompt 写法更简洁 |
| **虚拟线程** | JDK 21 引入的 Project Loom，Spring Boot 3.2+ 支持 |

### 面试怎么说

> "Spring Boot 3.x 最低要求 JDK 17，核心原因是 Jakarta EE 命名空间迁移——javax 全改成了 jakarta。另外也用到了 Records、Sealed Classes、Pattern Matching 等 JDK 17+ 的语言特性。如果公司还在 JDK 8，只能用 Spring Boot 2.x。不过 JDK 17 是 LTS 版本，升级是大势所趋。"

## 面试高频问题速查

### Spring AI相关

**Q1：Spring AI是什么？和LangChain什么关系？**
> Spring AI是Spring生态的AI应用框架，类似Spring Data对数据库的封装，它封装了大模型调用、RAG、Tool Calling等能力。LangChain是Python生态的同类框架。Spring AI的优势是与Spring Boot无缝集成，Java开发者零学习成本接入AI能力。

**Q2：RAG的原理是什么？为什么需要RAG？**
> RAG（Retrieval-Augmented Generation）检索增强生成。
> 问题：大模型训练数据有截止日期，不知道你的私有数据，还会编造信息（幻觉）。
> 解决：先从知识库中检索相关文档片段，把片段作为上下文提供给大模型，让它基于真实数据回答。
> 流程：文档切片 → 向量化存储 → 用户提问 → 向量检索 → 上下文拼装 → 大模型回答。

**Q3：什么是Embedding？什么是向量数据库？**
> Embedding：把文本转换成一组数字（向量），语义相近的文本向量距离也近。
> 向量数据库：专门存储和检索向量的数据库，支持"找最相似的K个向量"这种查询。
> 常见向量数据库：PGVector（PostgreSQL扩展，推荐）、Chroma（轻量级）、Milvus（大规模）、Elasticsearch（也支持向量检索）。

**Q4：什么是Tool Calling？它解决了什么问题？**
> Tool Calling让大模型能调用外部工具/API。
> 大模型本身不能查数据库、调接口，但它能理解用户意图并决定"现在需要查订单"。
> 我们预先定义好工具函数，大模型生成结构化的工具调用请求，框架自动执行并返回结果给大模型，大模型再组织自然语言回答用户。
> 这是构建AI Agent（智能体）的核心能力。

**Q5：System Prompt是什么？有什么用？**
> System Prompt是给大模型设定的"系统角色指令"，在整个对话中持续生效。
> 通过System Prompt可以：定义AI的角色身份、规定回答风格、限制回答范围、注入业务规则。
> 举例："你是一个电商客服，只能回答本平台相关问题，不能推荐竞品。"

**Q6：Spring AI如何实现多模型切换？**
> Spring AI通过抽象层统一了不同模型的调用接口。
> 只需更换starter依赖和配置即可切换模型，代码几乎不用改。
> 比如从DeepSeek切换到通义千问：换spring-ai-openai为spring-ai-dashscope，改base-url和model，Controller代码不变。

### 通用AI概念

**Q7：大模型的幻觉问题怎么解决？**
> 1. RAG：让模型基于真实文档回答，减少编造
> 2. System Prompt约束：明确告知模型"不知道就说不知道"
> 3. Temperature调低：降低创造性，提高确定性
> 4. 人工审核：关键场景增加人工确认环节

**Q8：Token是什么？和成本有什么关系？**
> Token是大模型处理文本的基本单位，大约1个汉字=1-2个Token。
> 模型收费按Token计算：输入Token（你的问题+上下文）+ 输出Token（AI的回答）。
> 优化方向：减少不必要的上下文长度、控制回答长度、选择性价比高的模型。

**Q9：如何选择大模型？**
> - DeepSeek：性价比之王，通用能力强，API便宜
> - GPT-4o：综合最强，但贵，网络不稳定
> - 通义千问：阿里系，国内访问快，中文能力强
> - 策略：非核心场景用便宜模型，核心场景用强模型，通过Spring AI统一抽象快速切换

**Q10：你在实际工作中怎么用AI的？**
> （结合你真实经验回答）
> "日常开发中主要用IDE的AI插件辅助编码，遇到报错先让AI分析再自行验证。
> 目前在通过WorkBuddy学习Spring AI，计划把AI能力落地到业务场景，
> 比如基于RAG做客服知识库，基于Tool Calling做智能工单处理。"

## 踩坑记录

（详细踩坑记录见 `docs/踩坑记录_202604281750.md`，共9个坑）

### 环境类（致命，不解决项目跑不起来）

- **Maven使用的JDK版本不是17会导致Spring AI依赖全部下载失败**，必须先运行 `mvn -version` 确认Java version是17.x。如果你的JAVA_HOME指向JDK 8，Maven就会用JDK 8编译，Spring Boot 3.x和Spring AI完全不兼容JDK 8
- **Maven 3.6.x 太旧**，Spring AI 1.0.x 需要 Maven 3.8.6+，否则POM解析报错
- **阿里云镜像 mirrorOf=* 会拦截Spring仓库**，必须改成 `mirrorOf=*,!spring-snapshots,!central-portal-snapshots`
- **groupId 不要搞错！** `org.springframework.ai` 是Spring官方的，`io.springboot.ai` 是第三方封装库，两者完全不一样。B站上有些教程用的是第三方库，和官方API对不上

### 依赖类

- DeepSeek API 兼容 OpenAI 协议，在 Spring AI 中使用 spring-ai-openai starter，只需修改 base-url 为 https://api.deepseek.com
- SimpleVectorStore 是内存版，项目重启后数据丢失，仅用于学习验证。已切换为 PgVectorStore ✅
- **JDK 17 是最低要求**，Spring Boot 3.x 不支持 JDK 8
- 如果 Maven 下载依赖超时，检查 settings.xml 的 mirror 配置是否拦截了 Maven Central

### Spring AI 1.0.x 专项

- **Tool Calling 旧写法已废弃**：`@Bean + @Description + Function<>` + `defaultTools("beanName")` 在 1.0.x 中报错，必须用 `@Component + @Tool` + `defaultTools(实例)`
- **Ollama starter 会自动配置 ChatModel**：与 DeepSeek 冲突，需用 spring-ai-ollama 核心 jar（非 starter）+ 手动 @Bean
- **PgVectorStore 需要 @Primary 消歧义**：OpenAI starter 自动注册了 EmbeddingModel，手动加 @Primary 解决
- **pgvector 扩展需手动创建**：`initialize-schema: true` 只建表不装扩展，需先执行 `CREATE EXTENSION IF NOT EXISTS vector;`
- **OllamaEmbeddingModel 4参数构造**：后两个参数不能传 null，必须传 `ObservationRegistry.NOOP` + `ModelManagementOptions.builder().build()`
- **TikaDocumentReader 依赖较大**：Apache Tika 会引入约 50MB 的传递依赖（PDFBox、POI 等），首次下载耗时较长。如果只需要支持 PDF，不必引入 Tika
- **Tika 对 PDF 表格解析弱**：Tika 提取 PDF 时是纯文本流，会丢失表格结构。中文 PDF 推荐 PagePdfDocumentReader，不要用 Tika
- **TikaDocumentReader 返回单个 Document**：Tika 解析整个文件为一个 Document（不像 PDF 按页切割），所以后续 TokenTextSplitter 分段更重要

### 1. Advisor 链执行顺序确认（断点调试验证）

| Advisor | Order 值 | 执行阶段 |
|---------|----------|-----------|
| `MessageChatMemoryAdvisor` | `-2147482648`（= `Integer.MIN_VALUE + 1000`） | 先执行，加载历史消息 |
| `CustomRagAdvisor` | `0` | 后执行，此时 `request.prompt()` 已含历史 |
| ChatModel（DeepSeek） | — | 最后执行 |

- 常量名：`Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER`
- 接口：`BaseAdvisor`（非 `CallAdvisor` / `StreamAdvisor` 单独实现）
- `augmentSystemMessage()` 是**追加**到 system prompt 末尾，非替换；如需完全控制应使用 `withSystemMessage()`

### 2. OverlappingTextSplitter 已知问题（FIXME）

当前 `slidingWindowWithOverlap()` 中，若粗切块（coarseChunk）本身小于 `chunkSizeChars`，直接返回整个粗切块，**粗切块之间没有 overlap**，边界处仍可能丢失语义。

已在源码 `OverlappingTextSplitter.java` 中标注 FIXME 注释，修复方向：
1. 即使粗切块较小，也让它与前一个 fineChunk 做尾部 overlap
2. 或在第一层粗切时也引入 overlap 机制

### 3. 双 ChatClient 架构（Builder 陷阱）

`ChatClient.Builder` 是**可变对象**，`.defaultTools()` 修改自身（return this），非创建新对象。
因此同一 Builder 先 build 带 tools 的、再 build 不带 tools 的 → 第二个也被污染。

正确做法：`ChatClient.builder(chatModel)` 是**工厂方法**，每次创建全新 Builder 实例，完全隔离。
两种 Client 对比：

|  | `chatClient`（带工具） | `jsonOnlyClient`（纯净） |
|---|---|---|
| 构造 | `builder.defaultTools(...)` | `ChatClient.builder(chatModel).build()` |
| HTTP 请求 | 含 `tools` 字段 → LLM 工具调用模式 | 无 `tools` → 纯文本生成模式 |
| 适用 | Agent 对话 | 结构化输出 / 意图识别 |
