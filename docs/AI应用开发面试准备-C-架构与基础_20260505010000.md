## 一、双 ChatClient 架构

### 1.1 面试官问："为什么需要两个 ChatClient？"

**3 分钟版回答：**

> **痛点：** 做意图识别时需要 LLM 返回 JSON，但 ChatClient 挂载了 Tool Calling 后，DeepSeek 直接调工具去了。根因是 **OpenAI 协议规范 `tools > system > user`**——HTTP 请求有 `tools` 字段时，LLM 优先进入工具调用模式，忽略"只返回 JSON"的指令。
>
> **怎么做：** 用 `ChatClient.builder(chatModel)` 工厂方法创建两个完全隔离的 Client：
> - `chatClient`：带 Tool Calling + ChatMemory + RAG → 正常 Agent 对话
> - `jsonOnlyClient`：纯净，什么都不挂 → 结构化输出 / 意图识别
>
> **关键踩坑：** `ChatClient.Builder` 是**可变对象**，`.defaultTools()` 修改自身（return this）不是创建新对象。如果复用同一个 Builder 先 build 带 tools 的，再 build 不带 tools 的 → 第二个也被污染。必须用工厂方法 `ChatClient.builder()` 每次创建全新 Builder。
>
> **底层区别：** 两种 Client 发给 DeepSeek 的 HTTP 请求体不同——一个有 `tools` 字段，一个没有。

**追问预判：**

- **Q："除了工具调用优先级，还有哪些 LLM 行为开发者无法控制？"** A："温度参数影响随机性但具体选哪个词是模型内部决定。'模型什么时候调工具、什么时候返回文本' 这个决策，除了去掉 tools 字段，没办法在 tools 存在时强制阻止。"
- **Q："结构化输出的 JSON 清洗怎么做的？"** A："三步：(1) 去掉 markdown 代码块标记 (2) 找第一个 { 和最后一个 } 提取中间内容 (3) Jackson ObjectMapper 反序列化。实测 DeepSeek 大部分返回干净 JSON，偶尔加前缀，清洗逻辑能覆盖。"
- **Q："两个 ChatClient 可以共享 ChatModel 吗？"** A："可以且应该共享。ChatModel 是底层 HTTP 客户端，线程安全。区别在 Builder 上挂载的 advisor 和 tools 配置。"
- **Q："Spring AI 1.1.0 的 entity(Class) 怎么解决？"** A："1.1.0 加了 BeanOutputConverter，可以直接 `.call().entity(IntentRecord.class)`。但双 Client 隔离仍然适用——底层仍然发 HTTP 请求，带了 tools 字段同样有工具调用优先级问题。"

### 1.2 设计模式：工厂方法 + 建造者模式

**工厂方法模式：**

> **哪里用：** `ChatClient.builder(chatModel)` 工厂方法
> **为什么用：** 每次调用返回全新 Builder，不受之前配置影响。解决双 Client 隔离问题。
> **类比：** `Calendar.getInstance()`、`LocalDate.now()`

**建造者模式：**

> **哪里用：** `ChatClient.Builder` 流式配置（.system() / .defaultTools() / .defaultAdvisors() / .build()）
> **注意：** `ChatClient.Builder` 是**可变 Builder**（.defaultTools() 修改自身 return this），不是 Effective Java 推荐的不可变 Builder。
> **类比：** `StringBuilder`、Lombok @Builder

## 二、多格式文档管道

### 2.1 面试官问："知识库支持哪些文档格式？"

**3 分钟版回答：**

> **怎么做：** 策略模式，根据文件扩展名路由到不同 Reader。支持 pdf/doc/docx/xls/xlsx/ppt/pptx/txt/html/md/csv/json/xml 等格式。所有 Reader 返回统一的 `List<Document>`，后续切片和向量化不用改。
>
> **为什么 PDF 不全部用 Tika：**
> - Tika 对 PDF 表格解析弱（纯文本流，丢失表格结构）
> - Tika 返回单个 Document（不像 PDF 按页切割）
> - Tika 依赖约 50MB
> - `PagePdfDocumentReader` 按页切割，中文排版和表格保留更好

**追问预判：**

- **Q："扫描件 PDF 怎么处理？"** A："扫描件是图片，PDFBox 提取出来是空的。需要先 OCR（Tesseract / 云服务 OCR / unstructured.io）。目前没做，计划接入。"
- **Q："大文件（100MB PDF）怎么处理？"** A："三个问题：(1) Spring Boot 默认 1MB 大小限制 (2) Tika 解析大文件可能 OOM (3) 切片后需分批入库。"
- **Q："文档更新后怎么处理？"** A："当前全量重新入库。生产可优化为增量更新：文档 hash 判断变化，只处理变化的文档。"

---

### 2.2 设计模式：策略模式（文档路由）

**哪里用：** 文件扩展名 → DocumentReader 路由

**类结构：**

```
DocumentReader（策略接口）
  ├── PagePdfDocumentReader（PDF 专用）
  ├── TikaDocumentReader（通用）
  └── 自定义路由逻辑（根据扩展名选择 Reader）
```

**好处：** 新增格式只需加一个新的 Reader，路由逻辑不用改。所有 Reader 返回统一的 `List<Document>`，下游（切片、向量化）完全解耦。

## 三、Spring AI 核心概念（初学必备）

### Q1：Spring AI 是什么？和 LangChain 什么关系？

> Spring AI 是 Spring 生态的 AI 应用框架，封装了大模型调用、RAG、Tool Calling、结构化输出等能力。
>
> **优势：** 与 Spring Boot 无缝集成，Java 开发者零学习成本；统一抽象换模型只需换 starter。
> **劣势：** 生态不如 LangChain 丰富；版本迭代快，API 变化大。

### Q2：Spring AI 1.0.x 和 0.x 有什么重大变更？

> | 功能 | 0.x（旧） | 1.0.x（新） |
> |------|-----------|-------------|
> | Tool Calling | `@Bean + @Description + Function<>` | `@Component + @Tool` |
> | Advisor | `RequestAdvisor / ResponseAdvisor` | `CallAdvisor / StreamAdvisor / BaseAdvisor` |
> | ChatClient | API 不同 | Builder 模式 |

### Q3：ChatClient 和 ChatModel 有什么区别？

> `ChatModel` 是底层模型调用接口（类似 DataSource），负责发 HTTP 请求。
> `ChatClient` 是高层 API（类似 JdbcTemplate），封装了 Prompt 组装、Advisor 链、Tool Calling。
>
> **使用原则：** 业务代码只用 ChatClient，不直接用 ChatModel。

### Q4：什么是 Advisor？和 Servlet Filter 区别？

> Advisor 是 Spring AI 的拦截器机制，在 LLM 调用前后插入逻辑。类似 Servlet Filter 拦截 HTTP 请求，Advisor 拦截 LLM 调用。
>
> **本项目 Advisor 链：** MemoryAdvisor(order=-21亿) → CustomRagAdvisor(order=0) → ChatModel

### Q5：Tool Calling 工作原理？

> 1. @Tool 注解定义工具方法，框架自动生成 JSON Schema
> 2. HTTP 请求带 tools 字段 → DeepSeek 判断需要调工具 → 返回 tool_calls
> 3. 框架自动反射调用 Java 方法 → 结果作为 ToolResponseMessage 喂回 → LLM 生成回答
>
> 整个过程是多轮 HTTP 请求，延迟是普通对话的 2~3 倍。

### Q6：怎么选 Embedding 模型？

> | 模型 | 维度 | 部署 | 特点 |
> |------|------|------|------|
> | nomic-embed-text | 768 | Ollama 本地 | 免费、中等质量 |
> | bge-large-zh | 1024 | Ollama 本地 | 中文效果好 |
> | text-embedding-3-small | 1536 | OpenAI API | 付费、高质量 |
>
> 离线入库和在线检索必须用同一个模型。

### Q7：向量化存储选什么？为什么 PgVector？

> PostgreSQL + pgvector 扩展。选型理由：中小企业最常用，不需要额外运维向量数据库；支持 IVFFlat/HNSW 索引；业务数据和向量数据在同一个数据库，运维简单。
>
> 其他选项：Chroma（纯内存不适合生产）、Milvus（大规模但运维成本高）、ES（支持向量但不是专精）。

## 四、LLM / AI 基础概念

### Q1：大模型的幻觉问题怎么解决？

> RAG + Prompt 约束 + 分数过滤三件套。RAG 提供真实上下文，Prompt 告诉 LLM 只基于参考资料回答，分数过滤确保参考资料相关。幻觉不可能完全消除，只能缓解。

### Q2：Token 是什么？和成本什么关系？

> 大模型处理文本的基本单位，1 汉字 ≈ 1~2 Token。API 计费 = 输入 Token + 输出 Token。
> 优化方向：控制上下文长度、压缩对话历史、选性价比高的模型。

### Q3：Prompt Engineering 常用技巧？

> 1. 角色设定 2. 上下文注入 3. 输出格式约束 4. Few-shot 示例 5. 禁止事项 6. Chain-of-Thought 思维链
>
> System Prompt 五要素：角色定义 + 能力边界 + 行为规则 + 输出格式 + 禁止事项（我们的项目已实现）

### Q4：怎么选大模型？

> | 模型 | 特点 | 适用场景 |
> |------|------|---------|
> | DeepSeek-V3 | 性价比之王 | 通用、成本敏感 |
> | GPT-4o | 综合最强但贵 | 核心业务 |
> | 通义千问 | 中文强、国内快 | 国内业务、合规 |
> | Claude | 长文本、安全对齐好 | 长文档、审核 |

## 五、Java 后端转型 AI 的面试策略

> **定位：** 不是 AI 算法工程师，是 **AI 应用工程师**——用 Java/Spring 生态把 AI 能力落地到业务系统。
>
> **核心话术：** "我理解 RAG 的原理（检索→注入→生成），也理解 Tool Calling 的多轮交互机制。我能在 Spring AI 框架上做工程化增强（自定义 Advisor、自定义 Repository、自定义 Splitter），不只是调 API。"
>
> **加分方向：**
> - 能讲清楚 Spring AI 框架的设计模式（策略、装饰器、责任链）
> - 能说清 LLM 的局限（幻觉、Token 限制、工具调用优先级）
> - 能对 RAG 全链路提出优化思路（切片、检索、过滤、Reranking）
> - 有成本意识（Token 监控、摘要压缩、分批入库）

## 七、术语字典（简历/面试 AI 新词速查）

| 术语 | 英文 | 一句话解释 |
|------|------|-----------|
| RAG | Retrieval-Augmented Generation | 检索增强生成，先检索文档再让 LLM 回答 |
| Embedding | Word Embedding | 把文本转成数字向量，机器能理解语义 |
| Token | Token | 大模型处理文本的基本单位，1汉字≈1~2 Token |
| Tool Calling | Function Calling | LLM 主动调用外部工具/API |
| Advisor | - | Spring AI 的拦截器，类似 Servlet Filter |
| Prompt | - | 发给大模型的指令 |
| System Prompt | - | 系统级指令，定义 AI 角色和行为规则 |
| Hallucination | - | LLM 编造不存在的信息 |
| Temperature | - | 控制 LLM 输出随机性的参数（0~2） |
| Chunk | - | 文档切片后的一段文本 |
| Overlap | Overlapping | 相邻 chunk 的重叠部分 |
| Vector Store | - | 向量数据库，存储 Embedding 向量 |
| Cosine Similarity | - | 余弦相似度，衡量两个向量方向的一致性 |
| Reranking | Re-ranking | 对检索结果重新精排 |
| BM25 | - | 经典关键词检索算法 |
| RRF | Reciprocal Rank Fusion | 多路检索结果融合算法 |
| Cross-Encoder | - | 精排模型，同时看 query 和文档 |
| Bi-Encoder | - | 粗排模型，分别编码 query 和文档 |
| HNSW | Hierarchical Navigable Small World | 高性能向量索引算法 |
| Semantic Chunking | - | 语义切片，按语义相似度断开 |
| DTO | Data Transfer Object | 数据传输对象 |
| SSE | Server-Sent Events | 服务器推送事件，用于流式输出 |
