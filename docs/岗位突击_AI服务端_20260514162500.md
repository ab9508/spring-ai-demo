## 二、必考高频题 + 标准答案

### 🔥 Q1. 你是怎么实现 RAG 检索的？遇到过什么问题？

**结论：** 两阶段检索 + 相对分数过滤，核心解决了固定阈值不稳定的问题。

**展开：**

我的 RAG 链路分三步：

第一步，**文本切片**：用自定义的 `OverlappingTextSplitter`，500 token 分块、10% overlap（50 token 重叠），避免语义在 chunk 边界断裂。

第二步，**向量召回**：`PgVectorStore` Top-K=5 余弦相似度检索，Embedding 用本地 `nomic-embed-text` 模型，零延迟零费用。

第三步，**相对分数过滤**：不用固定阈值，改用排名差距判断：
- Top1 < 0.45 → 拦截（最佳匹配太弱）
- Top1 - Top2 < 0.08 → 拦截（候选结果太接近，容易张冠李戴）

**收尾：** 这套过滤逻辑是我观察到检索结果异常、打出分数分布日志后自己摸索出来的，实际幻觉率明显下降。

### 🔥 Q2. 你的记忆库是怎么设计的？怎么防止内存膨胀？

**结论：** Redis List 存储 + TTL 过期 + 消息窗口截断，三层防线。

**展开：**

实现了 Spring AI 的 `ChatMemoryRepository` 接口，底层用 Redis List：
- Key：`chat:memory:{conversationId}`
- Value：JSON 序列化的消息列表，`RPUSH` 追加，`LRANGE` 读取

**防膨胀三层：**
1. `MessageWindowChatMemory.maxMessages=20`：读取时只取最近20条，LLM 看到的上下文有上限
2. Key TTL=24h：每次写入刷新过期时间，非活跃会话自动清理
3. LTRIM 裁剪（可选）：写入时 trim List 只保留最新 N 条，彻底控制存储大小

**踩坑：** Spring AI 1.0.x 不支持 Redis ChatMemory，Spring AI Alibaba 的 Redis 方案要求 Spring Boot 3.5.x，与我的 3.4.5 版本冲突，所以自己实现了 `ChatMemoryRepository` 接口，接入成本为零，Controller 无需改动。

### 🔥 Q3. 你对接大模型 API 的经验，遇到过哪些异常？怎么处理的？

**展开：**

**主要异常及处理：**

| 异常现象 | 根因 | 解决 |
|---------|------|------|
| 结构化输出失败，LLM 不返回 JSON | ChatClient 挂载了工具，请求体含 tools 字段，LLM 进入工具调用模式，忽略 prompt 指令 | 用 `ChatClient.builder(chatModel)` 创建全新隔离的纯净 ChatClient，HTTP 请求体无 tools 字段 |

### 🔥 Q4. 怎么解决大模型调用的高并发问题？

**结论：** 三层保护：限流 + 线程池隔离 + 本地模型兜底。

**展开：**

1. **接口限流**：Sentinel 针对 LLM 调用接口单独设限流规则，QPS 上限根据 API 套餐配置（如 DeepSeek 10 QPS），超限直接返回"系统繁忙"而不是排队等待。

2. **线程池隔离**：LLM 调用是 IO 密集型，用独立线程池（非 Tomcat 默认池），避免慢调用把 Web 线程耗尽。线程池参数：核心线程 10，最大线程 50，队列 200，拒绝策略 CallerRuns（降级返回）。

3. **本地模型兜底**：配置了双模型切换，`app.chat.provider=ollama` 时用本地 Ollama 运行 deepseek-r1:8b，云端 API 不可用时切本地，保证服务不中断。

4. **流式输出**：LLM 首 Token 延迟 2-3s，用 SSE 流式推送，用户看到"正在输出"感知更好，超时率下降。

### 🔥 Q5. 说说你做过的 MCP 实战经验

**结论：** 完整实现了 MCP Server + Client 的 SSE 通信，把业务工具封装成跨进程 MCP 服务。

**展开：**

**什么是 MCP：** Model Context Protocol，Anthropic 开源，AI 工具调用的"USB-C 标准"。让 AI 能跨进程调用外部工具，Host-Client-Server 三层架构，Client 与 Server 通过 SSE 长连接通信，协议是 JSON-RPC 2.0。

**我的实现：**
- MCP Server：Spring Boot 独立服务（端口 8081），用 `@Tool` 注解暴露订单查询、库存查询、售后工单三个业务工具，spring-ai-starter-mcp-server-**webmvc** 自动注册 SSE 端点
- MCP Client：主服务通过 SSE 长连接接入 Server，`McpSyncClient` 调用工具

**关键踩坑：**

Spring Boot 用 Tomcat（Spring MVC），必须用 **webmvc 版** Starter：
- ✅ `spring-ai-starter-mcp-server-webmvc`
- ❌ `spring-ai-starter-mcp-server`（默认 webflux 版，SSE 路由在 Tomcat 下不注册，连接 404）

Client 配置：`url` 只填根地址 `http://localhost:8081`，不要加 `/sse` 或 `/mcp/message`，框架自己拼路径。

### 🔥 Q6. 你用过 Milvus 吗？跟 PgVector 怎么选？

> ⚠️ 你目前没用过 Milvus，用以下话术诚实作答并展现理解深度

**回答：**

Milvus 我了解过架构和原理，生产实践用的是 PgVector。

**选型逻辑是这样的：**

| 维度 | PgVector | Milvus |
|------|---------|--------|
| 适用规模 | < 500 万向量，中小规模 | 亿级向量，大规模 |
| 运维复杂度 | 低（PG 扩展，DBA 已有） | 高（需部署 etcd + MinIO + Milvus 三组件） |
| 事务一致性 | 强（和业务数据同一 PG 事务） | 弱（需自己做补偿） |
| 查询延迟 | 10-50ms（IVFFlat 索引） | 1-5ms（HNSW，内存索引） |
| Spring AI 集成 | 原生 Starter | 需要自定义适配 |

**我选 PgVector 的主要原因：** 项目是中小企业知识库场景，数据量 < 50 万，运维团队已有 PG 基础，PgVector 直接复用，不需要引入新的存储中间件。

**如果场景变了怎么办：** 如果数据量上亿、对查询延迟要求 < 5ms，我会切换到 Milvus，Spring AI 的 `VectorStore` 接口是标准化的，切换向量数据库只需要换一个实现 Bean，业务代码不用改。

### 🔥 Q7. 如何快速排查大模型调用线上异常？

**结论：** 四步排查：看日志 → 看请求体 → 复现 → 定位层次。

**展开：**

大模型调用异常主要分三类：

**第一类：网络/API 层异常**
- 表现：`ConnectTimeoutException`、`429 Too Many Requests`、`503 Service Unavailable`
- 排查：看错误码，429 是限速，指数退避重试；503 是 API 服务问题，切备用模型
- 预防：配置 Resilience4j 熔断器，连续失败 5 次自动切换备用

**第二类：LLM 输出异常**
- 表现：返回空内容、JSON 格式错误、工具调用失败
- 排查：打印完整请求体（含 system prompt / messages / tools），在 Playground 里手动复现
- 常见根因：prompt 有歧义、tools 字段干扰输出格式（见 Q3）

**第三类：向量检索异常**
- 表现：RAG 答案和问题不相关、检索结果为空
- 排查：打印 Top-K 候选文档的分数，看是召回问题还是过滤过于严格
- 常用手段：临时调高 Top-K、临时放宽过滤阈值，缩小问题范围

**监控埋点（提前准备）：**
- 每次 LLM 调用记录：耗时、Token 数、是否走缓存、异常类型
- RAG 检索记录：Top1 分数、最终入 Context 的文档数
- 告警阈值：平均延迟 > 5s 告警，错误率 > 5% 告警

### 🔥 Q8. 你理解的 Tool Calling 是什么？和 MCP 什么区别？

**Tool Calling（工具调用）：**
LLM 在生成回答时，判断需要调用外部工具，在回复里返回"调用哪个函数、传什么参数"的结构化指令，应用程序解析后执行真实逻辑，把结果喂回 LLM 再生成最终回复。本质是"LLM 控制流程，Java 执行操作"。

**MCP（Model Context Protocol）：**
工具调用的"跨进程标准化"版本。Tool Calling 是同进程直接调 Java 方法；MCP 是通过 JSON-RPC + SSE 跨进程调用，工具可以部署在独立服务，实现工具能力的复用和解耦。

**类比：** Tool Calling 像调本地函数，MCP 像调微服务接口。

**实际选型建议：**
- 工具和 AI 服务同属一个项目 → 直接 Tool Calling，简单
- 工具需要被多个 AI 服务复用 / 工具有独立部署需求 → MCP

### 🔥 Q9. 你项目里是怎么做双模型切换的？为什么这样设计？

**结论：** `@ConditionalOnProperty` 条件注入，通过配置项一键切换，Embedding 模型固定不随之切换。

**展开：**

`ChatClientConfig.java` 里：
```java
@Bean
@ConditionalOnProperty(name = "app.chat.provider", havingValue = "ollama")
public ChatClient ollamaClient(OllamaChatModel model) { ... }

@Bean
@ConditionalOnProperty(name = "app.chat.provider", havingValue = "openai")
public ChatClient openAiClient(OpenAiChatModel model) { ... }
```

`application.yml` 里切换：
```yaml
app:
  chat:
    provider: openai  # 改成 ollama 切本地
```

**为什么 Embedding 不跟着切换：**
向量一旦入库就固定在某个向量空间里了。如果 Embedding 模型换了，原来入库的所有向量都要重新计算，否则语义空间不一致，检索结果会错乱。所以 Embedding 始终用本地 `nomic-embed-text`，不随 ChatModel 切换。

**排除 OpenAI Embedding 自动配置：**
同时引入 OpenAI 和 Ollama 依赖时，Spring Boot 会同时注册两个 EmbeddingModel Bean，发生冲突。解决：在 `application.yml` 里 exclude `OpenAiEmbeddingAutoConfiguration`，强制只用 Ollama Embedding。

### 🔥 Q10. 项目中如何保证 AI 系统的高可用？

**结论：** 四个层次：模型降级 + 熔断限流 + 异步解耦 + 监控告警。

**展开：**

1. **模型层降级**：主模型（DeepSeek API）不可用时，自动切换本地 Ollama 兜底，保证 AI 功能不中断

2. **熔断限流**：
   - Sentinel 对 LLM 接口设 QPS 限流（防止打爆 API 配额）
   - Resilience4j 熔断器：连续 5 次失败触发熔断，30 秒后半开探测恢复
   - 熔断期间返回预设的兜底回答，而不是直接报错

3. **异步解耦**：非核心 AI 任务（如批量文档 Embedding 入库）走 MQ 异步处理，不影响在线请求链路

4. **监控告警**：
   - Spring Boot Actuator + Prometheus 采集 LLM 调用延迟、Token 消耗、错误率
   - 告警规则：P99 延迟 > 8s 或错误率 > 3% 触发钉钉告警
   - 每次 LLM 调用记录完整日志，方便事后分析

## 三、补课清单（面试前必须过一遍）

### 📚 Milvus 架构速记（30分钟速通）

```
Milvus 核心组件：
├── Proxy：接收请求，路由分发
├── Root Coord：元数据管理（Collection、Partition）
├── Data Coord：数据节点协调
├── Query Coord：查询节点协调
├── Data Node：向量数据持久化（依赖 MinIO）
├── Query Node：向量索引加载+检索（内存）
└── Index Node：构建向量索引（HNSW/IVFFlat）

依赖：
- etcd：元数据一致性存储
- MinIO：向量数据对象存储
- Pulsar/Kafka（可选）：消息总线

关键概念：
- Collection ≈ 表
- Partition ≈ 分区（按时间/业务维度分）
- Segment：内部数据分片单位
- IVFFlat：快速构建，精度略低，适合 <1亿
- HNSW：查询更快（内存图索引），内存占用大，适合高并发
```

**面试时可以说：**
> "Milvus 我了解过架构，是 etcd + MinIO + Milvus 三组件部署，内部用 HNSW 或 IVFFlat 索引，适合亿级向量的高并发检索。我实际生产用的是 PgVector，数据量在 50 万以内，PgVector 运维成本更低。如果规模更大，我会选 Milvus，Spring AI 的 VectorStore 接口是统一的，切换成本很低。"
